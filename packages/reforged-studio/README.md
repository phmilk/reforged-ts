# reforged-studio

The Studio of reforged-ts: a local app that edits a Map project's Object data through `reforged-map`, taking turns with the World Editor ([#829](https://github.com/phmilk/reforged-ts/issues/829)). A Map project made from the Template runs `pnpm studio` once the Template takes the package up ([reforged-ts-template#145](https://github.com/phmilk/reforged-ts-template/issues/145)); until then, any Map project runs [the bin](#starting-the-studio). Either opens `http://localhost:<port>/objects` in the browser: the Object Editor's layout, a global search, a Table mode for bulk edits, icons and live model previews read from the developer's own install, an explicit save, session-wide undo and a real diff. The guide for a Map project author is [The Studio](https://phmilk.github.io/reforged-ts/docs/next/guides/studio) on the docs site.

It holds two parts: the Studio's server and page ([#831](https://github.com/phmilk/reforged-ts/issues/831)), and the reader of the developer's own Warcraft III install ([#830](https://github.com/phmilk/reforged-ts/issues/830)), which the Studio reads the game through and which the `reforged-builtins` generator imports through the workspace root's dev dependency: the workspace's one copy of each reader.

**For AI agents:** the documentation of this version as Markdown: [llms.txt](https://phmilk.github.io/reforged-ts/docs/next/llms.txt) links each page, and [llms-full.txt](https://phmilk.github.io/reforged-ts/docs/next/llms-full.txt) holds them all in one file.

**Build phase.** Until 1.0.0, every version is an alpha (`1.0.0-alpha.N`) published under the `next` dist-tag. Install with `@next`, beside its peer `reforged-map`: `pnpm add -D reforged-studio@next reforged-map@next`. npm gives `latest` to the first alpha, so `latest` stays on `1.0.0-alpha.0` until 1.0.0 is published, and moves to 1.0.0 then.

**Supported Patch: 3.0.1.24370.** The `reforged.patch` field of `package.json` carries the same Build. The Studio reads the game from the developer's own install of that Patch, and the install's own files only: it needs the game installed ([What needs the game](#what-needs-the-game)).

## The decisions it builds on

- [#467](https://github.com/phmilk/reforged-ts/issues/467), [ADR 0015](https://github.com/phmilk/reforged-ts/blob/master/docs/adr/0015-map-folder-owns-object-data-and-any-faithful-editor-may-edit-it.md) and its two amendments: the map folder owns Object data, and any faithful editor may edit it; the Studio is a local page first and a VS Code host later; it creates, edits and deletes any object, reloads on a change on disk, reloads the World Editor with `-launch -loadfile`, offers to apply again the edits a World Editor save put back, shows Object definitions read-only and holds no file open.
- [#476](https://github.com/phmilk/reforged-ts/issues/476), the prototype: the layout (tabs per Object kind, the tree, one field table, with the global search, "Differs from <base>" and the Table mode), the flows and the turns with the World Editor.
- [#481](https://github.com/phmilk/reforged-ts/issues/481), the research of model previews: `mdx-m3-viewer-th` with a patch for MDX 1800, the order of path resolution and its limits.
- [#482](https://github.com/phmilk/reforged-ts/issues/482), the research of placed objects whose type was deleted: the game skips them and the World Editor drops them at its next save, so the Studio only reads the placement files.
- [#468](https://github.com/phmilk/reforged-ts/issues/468) and [#595](https://github.com/phmilk/reforged-ts/issues/595): the hover of a Rawcode links to `/objects/<rawcode>`, which [the runtime file](#the-runtime-file) makes possible.
- [#632](https://github.com/phmilk/reforged-ts/issues/632), the writer of `reforged-map`, in the Editor form: every edit and every save is its own, so the Studio writes no Object data file of its own.
- [#700](https://github.com/phmilk/reforged-ts/issues/700), Object definitions and Object sync: an object the Object manifest gives to the code is read-only here, and adoption is `objects:adopt`'s.

What the Spec settled on top of them: the server's binding and request rules, the runtime file's name, format and lifetime, the first port, 5476, the state shape of a session and its undo across saves, the merge field by field after a change on disk and the detection of a World Editor revert, the free-Rawcode rule across the seven kinds, the placement reader that only reads, the art layer from the World Editor's Asset Mode, and the thumbnail cache on the developer's machine. Each is described below.

## Starting the Studio

`startStudio({ projectRoot, mapFolder, gameExecutable, worldEditorExecutable, port, open })` starts it and returns `{ url, started, close }`, or, when a live Studio already holds the map folder ([the runtime file](#the-runtime-file)), opens that one's page when `open` is true and returns its URL with `started` false, starting nothing; `url` is `http://localhost:<port>`, the page `<url>/objects`, an object `<url>/objects/<rawcode>`. It runs in Node from the Map project's own installation: `reforged-map` is its peer, and `reforged-builtins` and `typescript` are resolved from `projectRoot` through it, as the lookup resolves them. It never depends on `reforged-ts`.

- `projectRoot`: the Map project's root, under which its Object definitions (`src/objects`) and Object manifest (`object-manifest.json`) are.
- `mapFolder`: the map folder, saved as a folder by the World Editor.
- `gameExecutable`: the game's executable, or any path inside its install; else the one `WC3_EXECUTABLE` names, else the Battle.net app's default folders. Not found, it throws `InstallNotFoundError`, whose one-line message names the setting to fix.
- `worldEditorExecutable`: the World Editor the reload after a save starts, `World Editor.exe` beside the game's; without it, a save the reload would follow says the executable is missing.
- `port`: the first port tried, 5476 when left out; the next free one above it is taken when it is not free, and 0 takes any.
- `open`: whether to open the page in the system's browser.
- `worldEditorPreferences`: the World Editor's preferences file, whose Asset Mode [the art layer](#the-art-layer) defaults to; `WorldEditPreferences.txt` of the game's user folder when left out.
- `cacheFolder`: the folder of [the thumbnail cache](#the-thumbnail-cache); the user's cache folder when left out.
- `worldEditorCheck`, `worldEditorReload` and `env`, for tests and tools: `reforged-map`'s World Editor check options and reload options (a stand-in for the windows' titles, a stand-in launcher), and the environment "Open in editor" reads.

The bin is a thin wrapper over it, for a Map project not made from the Template, whose `pnpm studio` is to call `startStudio` itself ([reforged-ts-template#145](https://github.com/phmilk/reforged-ts-template/issues/145)):

```sh
reforged-studio --map maps/my-map.w3m [--project <root>] [--game <executable>] [--world-editor <executable>] [--port <port>] [--no-open]
```

It prints the URL, opens the page unless `--no-open`, and stops on Ctrl+C; when a Studio already runs on the map folder, it opens and prints that one's URL, and ends.

## The server

The server is Node's `http`, no framework. It listens on `127.0.0.1` only. It answers only a request whose `Host` is `localhost:<port>` or `127.0.0.1:<port>`, against DNS rebinding, and accepts a write, any method but `GET`, only with an `Origin` of its own, `http://localhost:<port>` or `http://127.0.0.1:<port>`: anything else is a 403.

It opens the map folder once with `reforged-map`'s `openObjectData(mapFolder, { projectRoot })`, and its Rawcode lookup with `openRawcodeLookup`, so the Studio, the hover and the lint rule agree on what a Rawcode names. The session keeps the saved state (what the map folder held at the last read), the working state (the saved state plus the unsaved edits), the states before and after its last save, and the undo and redo stacks, in the shape of the prototype of [#476](https://github.com/phmilk/reforged-ts/issues/476). An edit is one of the editor's, `setField`, `removeField`, `addObject` or `removeObject`, checked at once: a refused edit answers the editor's `ObjectDataWriterError` reason and message, which the page shows on the field. The edits of one request are one undo step, applied all or none: the list of its edits, each with the edits that restore its before value, applied in reverse by an undo. Undo and redo span the whole session, saves included, until a reload of the map folder empties them (an undo after a save makes the map dirty again), and are never persisted. A localizable field's edit sets its default text; its translations, which the writer keeps, are read-only. A reset puts a field back to its base (a `removeField`), a Custom object's fields back to its base's, and a modified Built-in object back to the Built-in object (a `removeObject`).

Nothing is written before a save. A save is the editor's `save()`, with the World Editor check on. Refused with `"modified-in-world-editor"` (the World Editor shows unsaved edits for the map folder) or `"changed-on-disk"` (a file it would rewrite changed since the Studio read it), it keeps every unsaved edit; after `"changed-on-disk"` it reads the map folder again and replays the unsaved edits on top, field by field, as [Taking turns with the World Editor](#taking-turns-with-the-world-editor) says, naming any the editor refuses there, and sends `reloaded`. While a conflict is left to choose, a save is refused with `"conflicts"`. Saved, it reads the map folder again so the next save compares with what it wrote, and when the World Editor holds the map folder without unsaved edits (`"open"`) and files were written, it offers "Reload in the World Editor", `reforged-map`'s `reloadWorldEditor(mapFolder, worldEditorExecutable)`, or sends it at once when the page's setting asks. A reload is never sent while the check says `"modified"`.

Adoption, "Adopt into code" on a Custom object or a modified Built-in object, is `reforged-map`'s Object adoption, `adoptObjects`, the function `pnpm objects:adopt` runs, with the same World Editor check: refused with `"modified-in-world-editor"` while the World Editor shows unsaved edits for the map folder, and with `"unsaved-edits"` while the Studio holds unsaved edits, since it adopts the object as the map folder holds it on disk. It writes the object's definition file and its entry in the Object manifest, and leaves the map folder byte for byte as it was, so the World Editor needs no reload. The definition file is formatted with the Map project's own Prettier, as `objects:adopt` formats it, and left as written when the Map project has none. The Studio then reads the map folder again, its undo and redo stacks emptied, and the object shows as an Object definition.

The diff of unsaved changes is the text of `reforged-map`'s `textconv` function (`objectDataText`) on the working state's encoded files against the saved state's, in `git diff`'s hunks; `war3map.wts` and the locales' tables show as their own text. The diff since the last commit compares each file at `HEAD` (`git show HEAD:<path>`) with the working state; a map folder outside a git repository has none.

It polls, once a second with `stat` and holding no file open, the files the lookup reads (the Object data files and their Skin files, `war3map.wts`, `war3map.w3i`, the Object definitions and the Object manifest) and the placement files, `war3map.doo` and `war3mapUnits.doo`. On a change with no unsaved edit it opens the map folder again, replaces the saved state and sends `reloaded`; with unsaved edits it keeps them and sends `changed-on-disk`, and reads the map folder again only when the author asks, "Reload and keep my edits on top".

### Taking turns with the World Editor

The merge and the revert are field-by-field comparisons of the session's states ([#837](https://github.com/phmilk/reforged-ts/issues/837)). A place is one field of an object (at its level and data pointer), or the whole object when one state adds or removes it or gives it another base; a Built-in object a state does not modify counts as modified without fields, so its fields compare one by one.

- **Merging after a change on disk.** "Reload and keep my edits on top", or a save refused with `"changed-on-disk"`, reads the map folder again and replays each unsaved edit on the new saved state. At each place the working state changes from the saved state (the edits' base): when the new saved state still holds the base's value there, the unsaved value is applied; when it holds the unsaved value, nothing is left to do; when it holds a third value, the place is a conflict. A conflict is listed with mine (the unsaved value) and theirs (the map folder's); the working state holds mine until the author chooses, a save is refused with `"conflicts"` until each conflict has a side, and a conflict left from a merge stays one through the next change on disk. Taking theirs is one undo step. The merge empties the undo and redo stacks, as any reload does: their steps restore values of the old saved state, which an undo would write over the map folder's new ones without a choice.
- **Detecting a World Editor revert.** At each read of the map folder, the places where the states before and after the Studio's last save differ are compared with the new saved state: a place that now differs from the state after that save and equals the state before it is put back, as a World Editor that never reloaded saves it. A field of an object the new saved state removed or gave another base is not put back; the whole object is compared instead. The page offers "Apply them again", which sets them to what the Studio saved as unsaved edits in one undo step, "Show", and "Keep the World Editor's"; either answer ends the comparison with that save until the next one.

## The runtime file

While it runs, the Studio writes `.reforged-studio.json` at the Map project's root, which a Map project git-ignores: one per Map project, so a Studio started on another map folder of the project replaces it. It is UTF-8 JSON, whose name, format and reader are `reforged-map`'s (`STUDIO_RUNTIME_FILE`, `StudioRuntimeFile`, `readLiveStudio`):

```json
{
  "format": 1,
  "url": "http://localhost:5476",
  "pid": 12345,
  "mapFolder": "<absolute path>",
  "startedAt": "<ISO 8601>"
}
```

It is written once the server listens, and removed on a clean stop: `close()`, the process's normal end, Ctrl+C and a termination signal, after which a signal nothing else listens to ends the process as it would have. A Studio stopping removes the file only while it is still its own. A crash may leave it, so every reader takes it as live only when `pid` is a running process (a synchronous signal-0 check) and `mapFolder` is the folder it reads, through links and, on Windows, without regard to case: `reforged-map`'s `readLiveStudio(projectRoot, mapFolder)` applies that rule for the Studio and the hover alike. A second Studio on the same map folder opens the first one's URL instead of starting, and the hover of `reforged-map`'s TypeScript plugin links to `<url>/objects/<rawcode>` from it ([its README](../reforged-map/README.md#the-typescript-plugin)).

The bodies' types are exported (`ObjectsAnswer`, `RawcodeAnswer`, `StudioEvents` and the others). A refusal is `{ error: { reason, message } }`.

An object's field table has a row per field of its kind the install knows, one per level for a field of levels, with its base's value as the game's files hold it under the map's Game data set, and the working state's value and raw value where the object modifies it; then a row per modification of a field the install does not know. Each value comes as the file holds it and as the editor shows it (`display`, `baseDisplay`): an enumeration's label (`Normal` for `normal`), a `WESTRING_` key resolved. Each row says whether an unsaved edit changed it (`unsaved`), and the input it edits with (`input`), from `reforged-builtins`' field table, which `reforged-map`'s `loadFieldTable` reads: `integer` or `real` for a number, `text`, `select` for an enumeration with its `options`, `toggle` for a boolean, `rawcodes` for a Rawcode list with its `references` (each Rawcode's kind and name), `icon` for an icon; with its value type, and a localizable field's translations, read-only. An Object definition is read-only, with its file and the line of its Rawcode.

A Built-in object the install holds, modified or not, comes with its group in the World Editor's tree, outermost first: its race through the editor data's `unitRace`, an item's class through its `itemClass`, then Melee or Campaign and Units, Buildings, Heroes or Special for a unit, Units, Heroes or Items for an ability, Buffs or Effects for a buff; a destructable's or a doodad's category as its data writes it. An object's icon is its kind's icon field (`uico`, `iico`, `aart`, `fart`, `gar1`), its own modification over its base's value; destructables and doodads have none.

- chips: the origin (an Object definition's with its lock and its file), a warning on a Rawcode another kind shares, and "not in this map's Game data set";

- one object's header, its "Differs from <base>" section with each modified field's base value, and its field table: each field's label, id, display and raw values, the levels of a field grouped and collapsible, the objects pinned with Compare as extra columns of the same kind, and a toggle that hides the fields at their base's value;
- icons in the tree, the header and every icon field, decoded in the page from the BLP and DDS files `GET /api/files` serves, with the readers of `mdx-m3-viewer-th`, the previews' viewer; a placeholder for one found nowhere;
- the pages of a link that selects nothing: `/objects/B000` with no `?kind=` asks which object, saying `FourCC` has no typed overload for it; an unknown Rawcode is "neither in this map nor Built-in", with the lookup's suggestions, the lint rule's.

### Previews

The page renders models with [`mdx-m3-viewer-th`](https://github.com/cipherxof/mdx-m3-viewer) 5.13.4, bundled into the page at the package's build with a patch of its MDX parser (`page/mdx-1800.ts`): the viewer reads versions 800 to 1000 only, and every model of 3.0 is version 1800, as [#481](https://github.com/phmilk/reforged-ts/issues/481) measured. The patch replaces the reading of six parser files, in place on their classes, with the layouts HiveWE's and WhiteoutLib's readers give, read for facts only: `material.js` (no shader name from 1100; an HD layer's six textures become the six layers the viewer draws as HD), `layer.js` (the shader type and the textures with their slots), `geoset.js` (`SKIN` in 16 bits from 1400), `camera.js` (the size's variant of 1800), `light.js` (the fields of 1200, 1300 and 1600) and `animationmap.js` (their tracks). The tests read synthetic models of version 1800 (`test/support/models.ts`); reading the install's own models across the SD, HD and DE layers is a check for a machine with the game, not run yet. [#842](https://github.com/phmilk/reforged-ts/issues/842) checked the editor's previewer, imports by mode, DE-only models and missing textures in the game itself ([research](https://github.com/phmilk/reforged-ts/blob/master/docs/research/world-editor-screen-checks.md)). Its MIT notice is in [NOTICES.md](NOTICES.md).

The viewer reads every file a model asks for (its textures, the team colours, the event objects' tables and the models they spawn) through `GET /api/files`, in the session's art layer. A texture found nowhere, as 2 to 5 % of Blizzard's own references are, never stops a preview: the model is drawn with the viewer's empty white texture in its place. One live renderer, one canvas moved into whichever preview is open, draws the open preview; thumbnails come from one shared renderer, off screen, one model at a time and the latest asked first (a row in view), since Chrome keeps at most 16 live WebGL contexts per page.

Its limits are taken as they are:

- **WebGL 1**: the viewer needs WebGL 1 with float textures and instanced arrays, which every browser and a VS Code webview have.
- **The HD shader is Lambert shading** with the normal, ORM and emissive maps, not the game's PBR: HD and DE models look flatter than in the game. An SD-on-HD or crystal layer is drawn as SD, and a model with more than 255 bones keeps its bone indices up to 255.
- **PopcornFX (`CORN`) is not drawn**: about 30 % of HD and DE models use it, most spell effects among them, which show little or nothing in HD and DE; their SD layer shows the classic particles.

[`whiteout-js-viewer`](https://github.com/FernandoS27/WhiteoutFlakes), which reads 1300 to 1800 with the game's shaders and PopcornFX but needs WebGPU, is to be re-evaluated later.

### The thumbnail cache

A thumbnail is a 128 by 128 PNG the page's shared renderer draws the first time a model field or the picker shows the model, which the server keeps on disk: `<cache folder>/<Build>/<art layer>/<hash>.png`, the hash of the model's path (without regard to case) and, for a map's import, of the file's bytes, so a changed import is drawn again. The cache folder is the user's: `%LOCALAPPDATA%\reforged-studio\thumbnails` on Windows, `~/Library/Caches/reforged-studio/thumbnails` on macOS, `$XDG_CACHE_HOME/reforged-studio/thumbnails` (else `~/.cache/…`) elsewhere, WSL included; `cacheFolder` moves it. The cache is generated on the developer's machine from their own install and never shipped, since it is Blizzard's art; deleting the folder only means the thumbnails are drawn again.

## Notices

The page bundles third-party code under its own licences, whose notices are in [NOTICES.md](NOTICES.md): `mdx-m3-viewer-th` (MIT), patched as [Previews](#previews) says, with what it brings into the page, and React.

## The placement reader

`readPlacements(mapFolder)` counts the placements of each Rawcode on the terrain: `war3mapUnits.doo` for units and items (start locations included) and `war3map.doo` for destructables and doodads (the terrain's special doodads included), each read whole, once, with no handle kept. It reads the layouts of the World Editor: version 7, 8 and 13, the 3.0 World Editor saving version 13 (sub-version 9 or 11 for units, 11 for doodads), field by field as HiveWE reads them; a record of version 7 or 8 with or without a skin id, whichever reads the whole file to its last byte. A missing file places nothing; a file that reads in no layout gives a warning and no placement. `readUnitPlacements` and `readDoodadPlacements` read one file's bytes, and `placementCount` gives an object's count in its kind's file.

It only reads: the Studio writes no placement file, since terrain and placed units stay the World Editor's (ADR 0015, ADR 0006). The delete's confirmation uses its count, and the free Rawcode skips a Rawcode it finds, so that a placement a deleted object left (the game skips it, the World Editor drops it at its next save, [#482](https://github.com/phmilk/reforged-ts/issues/482)) never comes back as a new object.

## The reader of the install

- **The CASC reader** (`openStorage`): the local storage of an install, read-only, in TypeScript with no native code and no dependency. It lists the root's paths and reads a file by its path, matched without regard to case, each checked against its content key.
- **The SLK and profile readers** (`parseSlk`, `Profile`): the tables and the `.txt` profile files of the game's object data.
- **The install** (`findInstall`): the folder that holds `.build.info`, found from an argument, else the executable `WC3_EXECUTABLE` names, else the Battle.net app's default folders (drive C under WSL), as the Probe runner finds the game.
- **The layers of a Game data set** (`GAME_DATA_SETS`, `layeredPath`): `_Balance/<Set>_V<version>.w3mod:` where the install has a kind's file, else the base layer `War3.w3mod:`, and no unit, item or ability of a later Game Data Version, as Probe runs measured them ([#575](https://github.com/phmilk/reforged-ts/issues/575), [`docs/research/builtins-layers.md`](../../docs/research/builtins-layers.md)).

## The game data model

`readGameData(storage, { gameDataSet })` gives, for one Game data set:

- each Object kind's label (its tab in the Object Editor) and fields, from its `*MetaData.slk`: where the field is (its table or the profile files, its index, its levels, its data column), its type and category, its enUS label (`UI/WorldEditStrings.txt`, `UI/WorldEditGameStrings.txt`, the second file's value winning), and the raw values and labels of the enumeration it reads (`UI/UnitEditorData.txt`);
- each Built-in object of the set, with its base values as the files hold them (one per level for a field of levels) and its group in the World Editor's tree: race, Melee or Campaign, then Units, Buildings, Heroes or Special for a unit; the class of an item; race, then Units, Heroes or Items for an ability; race, then Buffs or Effects for a buff; the category of a destructable or a doodad; the race of an upgrade;
- each Built-in object's values under an art layer's own keys (`layerValues`), which that layer reads over its base values: `Art:hd=` and `Art:sd=` give the Priest's icon, which has no `Art=`;
- `text(value)`: a `WESTRING_` key resolved through the editor strings, and through each key a value is in turn (`WESTRING_UE_UNITRACE_HUMAN=WESTRING_RACE_HUMAN`); none for a key that leads back to itself.

The profile files are every `.txt` file of `Units/` and `Doodads/` in the base layer, each from the set's layer where it has one, then those of the enUS layer, each group in the code-point order of its paths; a key set twice keeps its first value, the rule measured for the names files ([#564](https://github.com/phmilk/reforged-ts/issues/564)) taken for every key. A set's own value (`Name:custom,V1=`) wins over the shared one, under an art layer's key too (`Art:hd:custom,V0=` over `Art:hd=`). An art layer reads its own keys (`:sd`, `:hd`, `:de`), and DE reads HD's where it has none of its own: the install gives `Art:de` only where DE's icon is not HD's (the Priest has `Art:hd=…BTNPriestV1.blp` and no `Art:de`, and `BTNPriestV1` is a file of the HD and DE layers only), a rule read from the install's files ([#874](https://github.com/phmilk/reforged-ts/issues/874)) that no Probe run has measured in the game.

The model shows; it does not decide what is written. `reforged-builtins`' field table stays the source of where a field goes and of its value type, which `reforged-map`'s writer reads.

## Path resolution

`createPathResolver(storage, { artLayer, mapFolder })` resolves an icon's or a model's path as [#481](https://github.com/phmilk/reforged-ts/issues/481) measured it, in this order:

1. the map folder, layered like the game: `_hd.w3mod/<path>` then `<path>` in HD, `_de.w3mod/<path>` then `<path>` in DE, `<path>` in SD, each part matched without regard to case; the World Editor's Asset Manager writes an import marked HD or DE under `_HD.w3mod/` or `_DE.w3mod/`, as [#842](https://github.com/phmilk/reforged-ts/issues/842) observed;
2. the chosen art layer, `War3.w3mod:_HD.w3mod:` or `War3.w3mod:_DE.w3mod:`;
3. the base layer, `War3.w3mod:`;
4. `War3.w3mod:FileAliases.json`, whose destination goes through the three steps again.

Each layer, of the map folder or the storage, reads its enUS sub-layer (`_Locales/enUS.w3mod`) first, whatever the install's locale: the Studio shows enUS, as the names of `reforged-builtins` are; the tileset and `_teen` sub-layers HiveWE also reads are not: a preview has no tileset, and which art the World Editor shows from `_teen` was not checked. In each place a `.blp` or `.tif` path falls back to its `.dds`. A model's `.mdl`, or a path with no extension as the skin files write it, is read as its `.mdx`. A path that resolves nowhere is reported as missing, never thrown.

## The art layer

`readArtLayer({ preferencesFile, supportedModes })` chooses the art layer: the World Editor's Asset Mode preference (`[Misc] assetMode` of `WorldEditPreferences.txt`, 0 SD, 1 HD, 2 DE, and SD for -1 (Default)), limited by the map's Supported Modes, and HD when the preference cannot be read. [#842](https://github.com/phmilk/reforged-ts/issues/842) saw the World Editor run in SD under 0 and under Default, whatever the section's `hd` ([research](https://github.com/phmilk/reforged-ts/blob/master/docs/research/world-editor-asset-mode.md)); 1 and 2 follow the order of the editor's strings. The Supported Modes are a bit mask, 1 SD, 2 HD and 4 DE, which #842 read back from saved maps: a new map's default, 3, allows SD and HD.

The Studio reads the preferences file `findWorldEditorPreferences` finds: `WorldEditPreferences.txt` of the folder `WC3_USER_FOLDER` names (the Probe runner's variable), else of `Warcraft III` in the Documents known folder, which Windows may redirect to OneDrive and so is asked of Windows through PowerShell, under WSL through interop, rather than built from the home folder. The map's Supported Modes are `reforged-map`'s `readSupportedModes(mapFolder)`, and `allowedArtLayers` the layers they allow: the header's switch offers those, and changes the art layer for the session (`POST /api/art-layer`).

## What needs the game

The Studio needs the game installed: the field tables, the base values, the icons and the models are read from the developer's own install at run time, as ADR 0015 says, and never from the CDN. Without an install, `startStudio` throws `InstallNotFoundError`, naming the setting to fix. The thumbnail cache is the one file it writes from the install, on the developer's machine.

Every test runs on synthetic storages the tests write in a temporary folder, with no byte of Blizzard's; the previews' tests draw a synthetic MDX 1800 cube (`test/support/models.ts`), its texture found nowhere, and check that its canvas is not blank, not what it draws pixel by pixel. The server's tests (the Spec's Seam 1) drive its HTTP API on fixture map folders. The page's end-to-end tests (the Spec's Seam 2) drive the built page in headless Chromium with [Playwright](https://playwright.dev) over the same server: they need `pnpm build` and the browser, which `pnpm --filter reforged-studio exec playwright install --only-shell chromium` installs once per machine and CI installs in its own step. They cover, end to end:

- opening `/objects/<rawcode>`, a shared Rawcode and an unknown one (`test/page.test.ts`);
- editing a field and seeing it highlighted as unsaved, Ctrl+S and the counter of unsaved changes, and undo after the save (`test/page-editing.test.ts`);
- the banner after a change on disk, the merge and its conflicts, and a World Editor revert (`test/page-turns.test.ts`);
- the delete confirmation with the placement count, and creating an object (`test/page-create-delete.test.ts`);
- the Table mode and bulk edits (`test/page-bulk.test.ts`), and the model previews (`test/page-models.test.ts`).

On a machine with the game, `pnpm --filter reforged-studio studio:check-install [--install <folder>]` finds the install as `pnpm builtins:generate` does and reads the Footman's base values, its icon and its HD model.
