# reforged-test

Runs TypeScript tests for Warcraft III Reforged map code on real Lua 5.3, with the game's Natives stubbed in Lua, and reports every test to [vitest](https://vitest.dev/).

**Supported Patch: 3.0.1.24370.** The `reforged.patch` field of `package.json` carries the same Build.

<!-- The release's version step (release:version) stamps the docs version of each release into these links: docs/release.md. -->

**For AI agents:** the documentation of this version as Markdown: [llms.txt](https://phmilk.github.io/reforged-ts/docs/next/llms.txt) links each page, and [llms-full.txt](https://phmilk.github.io/reforged-ts/docs/next/llms-full.txt) holds them all in one file.

**Build phase.** Until 1.0.0, every version is an alpha (`1.0.0-alpha.N`) published under the `next` dist-tag. Install with `@next`: `pnpm add -D reforged-test@next`. npm gave `latest` to the first alpha, so `latest` stays on `1.0.0-alpha.0` until 1.0.0 is published, and moves to 1.0.0 then.

The tests are compiled by [typescript-to-lua](https://typescripttolua.github.io/) exactly like map code, then run on Lua 5.3.6 compiled to WebAssembly ([lua-wasm-bindings](https://www.npmjs.com/package/lua-wasm-bindings), the VM typescript-to-lua's own suite uses). What a test observes is the Lua your code emits, the Native calls it makes and the objects it returns.

The package has five parts:

| Part                                 | Reached as            | What it is                                                                                                                                                                                  |
| ------------------------------------ | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The runner                           | `reforged-test/lua`   | `describe`, `it`, `expect`, `beforeEach`, `afterEach`, `fn` and `calls` for the test files, compiled to Lua.                                                                                |
| The map entry point                  | `reforged-test/map`   | `describe`, `it`, `expect`, `beforeEach`, `afterEach`, `startGame`, `fn`, `calls`, `stubNative` and `newHandle` for a Map project's tests, each in a Test game of its own, over the runner. |
| The glue                             | `reforged-test`       | The Node entry point a vitest file calls. It runs every compiled test file in a fresh Lua state and registers the results with vitest.                                                      |
| The stubs                            | `stubs/*.lua`         | Plain Lua files that define the Natives and globals the code under test calls. The glue loads them by path.                                                                                 |
| The declarations of the stub helpers | `reforged-test/stubs` | The TypeScript declarations of the `__stub_*` helpers the stubs define, for the `types` of a test's tsconfig.                                                                               |

## Testing a map

A Map project's test imports everything it needs from `reforged-test/map`, and each of its tests runs in a Test game of its own:

```ts
import { expect, it, startGame } from "reforged-test/map";
import "../../src/main";

it("greets the players", () => {
  const game = startGame();
  expect(game.printed).toContain("Welcome!");
});
```

The guide [Testing your map](https://phmilk.github.io/reforged-ts/docs/next/guides/testing-your-map) is the page to read: from a first test to what the harness cannot tell you. The Template sets the tests up in every Map project.

Every export of `reforged-test/map` carries its doc comment, shown on hover and in the `reforged-test` section of the docs site's API reference, with an example: a test file of [`examples/`](examples), which the package's own tests compile and run, each `it` as a test.

A Native no Stub answers gets its answer in the test, in TypeScript: `stubNative("GetUnitName", (unit) => "Footman")`, typed from the Typings and recorded as a Shipped stub records its calls, with `newHandle(kind)` for an answer that creates a Handle. `game.setLocalPlayer(player)` makes the test act as another client. A Lua stub file listed in the `stubs` option still loads, after the shipped ones.

`stubNative` takes the name of a Native of `common.j`, and `newHandle` the name of one of its Handle types: `runner/map/natives.ts` lists both, generated from the Typings of their newest Patch by `pnpm --filter reforged-test natives:generate`. The same command generates `stubs/unstubbed.lua`, the shipped stub file that makes a Native without a Stub throw a message naming `stubNative`. `test/natives.test.ts` is the Drift check of both: it fails, naming the command, when a committed file is not what the generator emits, as on a new Patch.

An error the library caught from a Map project's callback, a Caught error, fails the test at its end unless the test expected it with `game.expectError(text)`; with Dev mode off, which the Test game does not force on, a handler's error is not caught and fails the test at once. [The Caught error contract](#the-caught-error-contract) is how the library tells the harness.

`it.skip`, `it.only`, `it.todo(name)`, `describe.skip` and `describe.only` are Vitest's: the glue registers each in Vitest's native form, so a test skipped, todo or out of focus opens no Test game, and a forgotten `only` fails the run under `CI`. `only` reaches every Lua test of the Map project, not its file's only.

A helper a map's test needs that has no import in `reforged-test/map` is a gap of the package: [file it as an issue](https://github.com/phmilk/reforged-ts/issues/new), rather than reaching for the helpers of the part below. Sync, the preload file and `os.clock` have no form in `reforged-test/map`.

## Testing a library

A Map project does not use this part: it is the harness level the library's own tests are written at, `reforged-test/lua` with its call log, the `__stub_*` helpers the Shipped stubs define, the glue and the Shipped stubs themselves.

### Writing a test

A test file is TypeScript, named `*.test.ts`, and imports the runner from `reforged-test/lua`:

```ts
/** @noSelfInFile */
import { describe, expect, it, stubCalls } from "reforged-test/lua";
import { MapPlayer, Unit } from "../src/index";

describe("Unit", () => {
  it("passes the recorded arguments to CreateUnit", () => {
    const owner = MapPlayer.fromIndex(0)!;
    const unit = Unit.create(owner, FourCC("hfoo"), 10, 20, 270)!;
    expect(stubCalls()).toContainCall(
      "CreateUnit(player#1048577, 1751543663, 10, 20, 270)",
    );
    expect(unit.getOwner()).toBe(owner);
  });
});
```

The runner exports:

- `describe(name, body)`: groups the `it` blocks registered by `body`. Nesting is allowed.
- `it(name, fn)`: registers one test. Tests run after the file has loaded, in registration order. The tests of one file share its Lua state, and so its stub call log and handle ids.
- `it.skip(name, fn)`, `it.only(name, fn)`, `it.todo(name)`, `describe.skip(name, body)` and `describe.only(name, body)`: Vitest's focus and skip forms, which `runLuaTests` registers in Vitest's native form, so Vitest reports them and a forgotten `only` fails the run under `CI`. The body of a skip or todo test, or of a test in a skipped `describe`, does not run, nor do its hooks. `only` hides the report of the other tests only: they still run, in the file's Lua state, at load. `it.todo` takes no body. There is no `skipIf`, `runIf`, `fails`, `concurrent` or `each`.
- `beforeEach(fn)` and `afterEach(fn)`: register a function that runs before, or after, each test of the current `describe`, its nested ones included, or of the whole file at the top, wherever in the `describe` it is registered. They fail as Vitest's do:
  - the `beforeEach` hooks run from the outer `describe` inwards, in registration order within one, and the `afterEach` hooks from the inner outwards, the last registered first within one;
  - a `beforeEach` that throws fails the test, and the remaining `beforeEach` hooks and the test's body are skipped;
  - the `afterEach` hooks run even when the body or a `beforeEach` failed; one that throws fails a test that had passed, and the remaining `afterEach` hooks are skipped;
  - a function a `beforeEach` returns runs after the `afterEach` hooks, the last returned first, as Vitest's cleanup does, unless an `afterEach` threw;
  - the test reports its first error;
  - a `beforeEach` or `afterEach` called inside a running test throws. There is no `beforeAll` or `afterAll`.
  - `BeforeEachCallback` is the type of the function `beforeEach` takes.
- `expect(value)`, with Vitest's matchers where typescript-to-lua compiles them. `.not` negates each one: `expect(n).not.toBe(0)`.
  - `toEqual(expected)`: strict equality (`==`) on primitives, deep equality on tables. Metatables are ignored.
  - `toBe(expected)`: identity (`rawequal`), so two equal tables are not the same.
  - `toBeTruthy()` and `toBeFalsy()`: Lua truthiness, where only `nil` and `false` are falsy (`0` and `""` are truthy).
  - `toBeUndefined()` and `toBeDefined()`: the value is `nil`, or is not.
  - `toContain(item)`: a list holds this very item (`rawequal`), or a string holds this part as plain text.
  - `toContainEqual(item)`: a list holds an item deeply equal to this one.
  - `toHaveLength(length)`: the length `#` gives of a string or a list.
  - `toMatchObject(subset)`: a table holds every key of `subset` with a matching value, nested tables matched the same way; a list in `subset` matches a list of the same length only. An empty list is an empty table in Lua, so `{}` matches any table.
  - `toBeGreaterThan`, `toBeGreaterThanOrEqual`, `toBeLessThan` and `toBeLessThanOrEqual`: comparisons of two numbers.
  - `toBeCloseTo(expected, digits?)`: the difference is below half of 10 to the power of `-digits`, `digits` being 2 when omitted.
  - `toBeInstanceOf(cls)`: an instance of a typescript-to-lua class or of one that extends it.
  - `toMatch(part)`: a string holds this part as plain text.
  - `toThrow(message?)`: the value is a function that throws when called. With `message`, the error's message contains it as plain text. It takes no error class.
  - `toContainCall(call)`: the value is a call log that holds exactly this line.
  - The spy matchers, on a Native or a Spy alike: `toHaveBeenCalled()`, `toHaveBeenCalledTimes(times)`, `toHaveBeenCalledWith(...args)`, `toHaveBeenLastCalledWith(...args)` and `toHaveBeenNthCalledWith(n, ...args)`, `n` counted from 1. Every Native is already a Spy: `expect(TimerStart)` reads the Recorded calls its Stub keeps, the arguments typed from the Native's parameters, with nothing replaced on `_G` and nothing to restore. The arguments compare as `toEqual` compares, their number included, so a trailing `nil` counts. Any other value, a function of the map or of the Lua library included, fails the matcher, saying so.
- The asymmetric matchers, which stand on the expected side of `toEqual`, `toMatchObject` and `toContainEqual`: `expect(call).toEqual([expect.anything(), 60])`.
  - `expect.anything()`: any value but `nil`. A field holding `nil` is absent in Lua, so it fails there too.
  - `expect.any(kind)`: a value of a Lua type, by its name (`"number"`, `"string"`, `"boolean"`, `"table"`, `"function"`), or an instance of a class. `Number`, `String` and the other built-in constructors are `nil` in Lua, so `expect.any(Number)` raises, naming the type name to write.
  - `expect.objectContaining(part)`: a table holding every key of `part` with a deeply equal value.
  - `expect.arrayContaining(items)`: a list holding, in any order, an item deeply equal to each of `items`; with no items, any value, as Vitest's.
  - `expect.stringContaining(part)`: a string holding this part as plain text.
- `fn(impl?)`: a Spy, a real function that keeps the arguments of each of its calls apart from every other function's, then calls `impl`, when given, and returns what it returned. It has no `mock` member and nothing resets it.
- `calls(spy)`: the arguments of each call of a Spy or of a Native, oldest first, one list per call typed as the function's parameters: `calls(TimerStart)[0][3]` is the handler of the first `TimerStart`. A list ends at its last argument that is not `nil`.
- `stubCalls()`: the stub call log, one `Name(arg, arg)` line per Native call.
- `run(position?)`: runs the registered tests and returns the JSON results; in a file that loads `reforged-test/map`, lists them, or runs the one at `position`. The glue calls it through the global `__reforged_test_run`, so a test file never calls it.

A failed expectation fails its test with a message such as `Expected {a = {1, 2}} to deeply equal {a = {1, 3}} (first difference at .a[2]: 2 vs 3)`, with no file and line of the TypeScript, Handles rendered as `kind#id` and constants by their name, as the call log renders them. A spy matcher's message ends with the calls received, one per line, `1: TimerStart(timer#1048577, 30, false, <function>)`. `toEqual`, `toBe`, `toMatchObject` and the three spy matchers that compare arguments hand Vitest the two values compared, so it draws their diff. Any other error fails it with the Lua message, location included, a thrown table's read from its `message`.

`toMatch`, `toThrow(message)` and `expect.stringContaining` take plain text, never a pattern: typescript-to-lua compiles no regular expression, and a Lua pattern would read `.` or `%` as no Vitest test means them. There is no `toBeNull` (`null` is `nil`, so `toBeUndefined`), `toBeNaN`, `toStrictEqual`, `toHaveProperty`, snapshot, `resolves` or `rejects`. Why each matcher reads as it does, and what typescript-to-lua compiles of Vitest's: [How test libraries phrase a test](https://github.com/phmilk/reforged-ts/blob/master/docs/research/test-phrasing.md).

Compile the tests with a typescript-to-lua project of their own: `luaTarget` `5.3`, `moduleResolution` `bundler`, the language extensions and `lua-types/5.3` (or `reforged-types/3.0.1`) in `types`. typescript-to-lua copies the runner's Lua into the output folder under `lua_modules/reforged-test/lua/`, and the map entry point's under `lua_modules/reforged-test/map/`.

### Running the tests with vitest

Add one vitest file that calls the glue with the output folder of that compile:

```ts
// test/lua.spec.ts
import { runLuaTests } from "reforged-test";

runLuaTests({
  outDir: "dist-test",
  stubs: ["test/stubs/units.lua"],
});
```

`runLuaTests(options)` registers one vitest `describe` per compiled test file, named after its TypeScript file (`handles/unit.test.ts`). Inside it, each `it` becomes one vitest `test`, and nested `describe`s are kept. A failed test shows the Lua message and no JavaScript stack.

The options are:

- `outDir`: the folder typescript-to-lua emitted the tests and the code they import to.
- `stubs`: extra stub files, executed after the shipped ones, in the order given.

Relative paths in both options resolve against the current working directory.

Each compiled test file runs in a fresh Lua state, in this order:

1. The standard libraries are opened.
2. The shipped stub files run: `base.lua` first, then the others by name, then `unstubbed.lua`, which defines every Native of `common.j` the others left out as a function that throws (under Error messages).
3. The stub files listed in `stubs` run, in the order given.
4. Every global function the stub files defined becomes the Stub of the Native it is named after (`__stub_seal`), what a spy matcher reads the Recorded calls of, so a function of a stub file that records no call reads as never called.
5. Every `.lua` file under `outDir` is preloaded into `package.preload` under its module name.
6. The test module is required, which registers its tests.
7. The runner runs the tests and returns the results.

A file that loads `reforged-test/map` stops at step 7 with the list of its tests, and each test then runs in a fresh state of its own, the seven steps again with that test alone at step 7, inside its vitest `test`. A file of N tests costs N+1 states, less the tests Vitest does not run: a skip or todo test, or one out of focus, opens no state. A test is known across loads by its position, its full name checked: when a load registers another name there, the test fails with a message saying the file registers different tests on each load.

A fresh state costs a few milliseconds: about 9 ms with the whole reforged-ts library preloaded. lua-wasm-bindings loads once per process.

Other exports of the glue:

- `runLuaTestFiles(options)`: runs the same files and returns their results without registering anything with vitest. Each result carries the Lua `moduleName` (`handles.unit_test`), the `testFile` it was compiled from (`handles/unit.test.ts`), its `tests` and, when the module failed to load, its `error`. It runs every test but a skip or todo one, which it reports with the status `skip`; `only` is reported in a test's `mode`, and hides nothing.
- `compileLuaProject(tsconfigPath)`: compiles a typescript-to-lua project and returns its errors as text, or `""` when it compiled. A Map project's vitest global setup calls it to build the tests before they run. `typescript` and `typescript-to-lua` are peer dependencies for it.
- `MARKER_32_BIT`: the `[32-bit]` marker described under the integer width policy.
- `LOAD_TEST_NAME`: the name of the one failing test that stands for a file that failed to load, for example on a Native called at module load that no stub defines. The other files still run.
- The types `LuaTestOptions`, `LuaTestFile`, `LuaTestResult`, `LuaTestStatus`, `LuaTestMode` and `LuaSuiteMode`.

#### Error messages

A Native without a Stub throws a message that names it and `stubNative`, at the line that called it:

```text
LuaError: handles/unit_test.lua:12: GetUnitName is a Native reforged-test does not stub: give it an answer with stubNative("GetUnitName", …)
```

When that call is a tail call (`return GetUnitLevel(unit)`, as many members of a Wrapper compile), it leaves no frame of its caller: the line is then the nearest caller's still on the stack, the one that called the member, and there is no line when that caller is not Lua (`pcall`). The fix in a Map project's test is `stubNative`, from `reforged-test/map`; in the library's tests, a stub for the Native in a stub file. The function that throws is defined for every Native of `common.j` in the Typings that no Shipped stub covers, by `stubs/unstubbed.lua`, which `pnpm --filter reforged-test natives:generate` generates from the Typings of their newest Patch and `test/natives.test.ts` holds to them, as it does `runner/map/natives.ts`. So a Native without a Stub is a function, not `nil`: `__stub_unstubbed(name)` tells whether the global `name` still is that function. A stub file of the `stubs` option defines over it. `_G` gets no metatable, and a function of `blizzard.j` or `common.ai` stays undefined: the glue rewrites the VM's `attempt to call a nil value (global 'X')` for it into `Native X is not stubbed`.

Every error the VM raises is caught and reported with its Lua message only.

### The module naming contract

- typescript-to-lua replaces the dots in a file name with underscores, so `unit.test.ts` is emitted as `unit_test.lua`.
- The glue discovers test modules by the `_test.lua` suffix, anywhere under `outDir` except `lua_modules/`.
- It reports each module under its TypeScript name: `handles/unit_test.lua` is shown as `handles/unit.test.ts`.
- A module's name is its path relative to `outDir` without the extension, with separators turned into dots. That is the name typescript-to-lua emits in `require` (`handles.unit`).
- A file whose name ends in `_test.lua` is always treated as a test module, so keep that ending for test files.

### The results contract

The runner and the glue share nothing but this JSON string, returned by the global `__reforged_test_run`:

```json
{
  "tests": [
    {
      "message": "Expected 2 to equal 3",
      "name": "adds",
      "status": "fail",
      "suite": ["arithmetic"]
    }
  ]
}
```

- `suite` lists the enclosing `describe` names, outermost first.
- `status` is `pass`, `fail` (an expectation did not hold), `error` (anything else was thrown, or, in a Test game, a test that threw nothing left a Caught error unexpected) or `skip` (the body did not run: a skip or todo test, or one in a skipped `describe`).
- `message` is present on `fail` and `error`. In a Test game it starts with the lines of the Caught errors the test left unexpected, when there are any ([The Caught error contract](#the-caught-error-contract)).
- `actual` and `expected`, together, on a `fail` whose matcher compared two values: each rendered as text, which the glue hands to Vitest as the error's `actual` and `expected` for its diff, and `runLuaTestFiles` returns on the result.
- `mode` is `skip`, `only` or `todo` for a test registered with `it.skip`, `it.only` or `it.todo`, and absent for a plain `it`.
- `suiteModes` lists the mode of each enclosing `describe`, one per `suite` name (`run`, `skip` or `only`), and is absent when every one is a plain `describe`.

In a file that loads `reforged-test/map`, the call without an argument answers the list of the tests, `{"isolated":true,"tests":[{"name":"adds","suite":["arithmetic"]}]}`, each with its `mode` and `suiteModes` when it has them, and the glue calls the global again in a fresh state for each test, with its position counted from 0 as a string (`"2"`); that call answers the form above with the one test's result, or with an empty `tests` when the file registered no test there.

The runner writes it with its own encoder, with keys sorted, because the game's Lua has no JSON library. The glue rejects results of any other shape.

### The Caught error contract

`reforged-test` and `reforged-ts` depend on nothing of each other: the global `__reforged_caught_error(origin, message)` is the whole contract between them ([ADR 0028](https://github.com/phmilk/reforged-ts/blob/master/docs/adr/0028-the-library-reports-a-caught-error-to-a-global-the-harness-defines.md)).

- **The library calls it.** Each of the library's places that catch an error of a Map project's callback (an Init stage's callback, and in Dev mode a protected callback or `MapPlayer.runLocal`) calls it on every failure, a repeat the library only counts included, after printing its line `reforged-ts: <origin> failed: <message>`, and goes on as in the game. It reads the global raw, and only when it is defined: the game defines none, and the Typings do not declare it. A warning does not go through it.
- **The harness defines it.** `reforged-test/map` assigns it raw on `_G` in every Test game, when it loads. It keeps each call, `origin` and `message` as strings. At the end of the test, after the last `afterEach` and the cleanups a `beforeEach` returned, the runner fails the test for every one `game.expectError` did not expect, listed as `<origin> failed: <message>`, `×N` after a repeat, before the test's own failure when it has one. A file on `reforged-test/lua` alone defines no such global, so the library only prints there.
- **What it holds.** `origin` is where the callback was registered or ran, `Timer#1048577 Timer.start` or `globals callback "spawn"`; `message` is the Lua error text, as `pcall` returned it. Renaming the global, or changing what its two arguments hold, is a breaking change of both packages.

### Stubs

#### The shipped baseline

`stubs/base.lua` defines the baseline every test can rely on, before any test runs:

- the globals `bj_MAX_PLAYER_SLOTS` (28), `bj_MAX_PLAYERS` (24) and `bj_UNIT_FACING` (270.0), which the library reads when its modules load;
- the slot-state constants `PLAYER_SLOT_STATE_EMPTY`, `PLAYER_SLOT_STATE_PLAYING` and `PLAYER_SLOT_STATE_LEFT`, and the controller constants `MAP_CONTROL_USER`, `MAP_CONTROL_COMPUTER`, `MAP_CONTROL_RESCUABLE`, `MAP_CONTROL_NEUTRAL`, `MAP_CONTROL_CREEP` and `MAP_CONTROL_NONE`: opaque values a test compares by identity (`toBe`), rendered by name in the call log;
- the Natives `Player`, `GetPlayerId`, `GetHandleId` and `CreateTrigger`: what the library's `globals` stage calls to fill `Players` and create the sync Trigger once a test runs `InitGlobals`, and what every Wrapper reads its ids with;
- `FourCC`, a Lua helper of the game rather than a Native.

The editor's entry points (`config`, `main`, `InitGlobals`, `InitCustomTriggers`, `RunInitializationTriggers`, `MarkGameStarted`) stay nil, until a test defines them or enters the globals stage with `__stub_init_globals` (under Test controls). The library wraps the ones that exist when it loads and captures the others on their first assignment, so it loads with none of them defined, and a test defines the ones it drives, in the load position it stands in for. The library makes no Handle-creating Native call when it loads: requiring it adds no `Player`, `CreateTrigger` or `CreateTimer` line to the call log. The glue does not make an undefined global an error either: which entry points exist is the test's decision.

It also holds the shared machinery the other stub files use:

- `__stub_calls` is the call log, a list of strings.
- `__stub_record(name, ...)` appends one line, `Name(arg, arg)`, to the call log. Handles are rendered as `kind#id`, constants by their name, strings are quoted and functions are shown as `<function>`. It also keeps the arguments themselves, which `__stub_args` hands back.
- `__stub_new_handle(kind)` returns a new handle. A handle is a table carrying `__kind` and `__handleId`, whose `tostring` begins with its kind and a colon as the game's does (`timer: 1048577`, where the game writes an address). Ids are sequential from a fixed base, so the first handle of a state is `1048577`.
- `__stub_constant(kind, name)` returns a constant of the game: a table carrying `__kind` and `__name` and no handle id, so defining one leaves the handle sequence alone.
- `__stub_constants(kind, names)` defines one global constant of `kind` per name in the list, each named after itself: a family of constants in one call.
- `__stub_format(value)` renders one argument as `__stub_record` does.
- `__stub_seal()` takes every global function the stub files defined, but the standard library's and the `__stub_*` helpers, as the Stub of the Native it is named after; the glue calls it after the last stub file. `__stub_define(name, stub)` defines the global Native `name` as `stub`, a Stub too, as `stubNative` does, and `__stub_native_name(value)` answers the name of the Native whose Stub `value` is, or `nil`.
- `__stub_player(number)` returns the player handle of a slot, the one `Player` returns, without a call-log line. Stubs that return a player use it.
- `__stub_response(name)` defines the event response Native `name` (`GetTriggerUnit`, `GetExpiredTimer`): it records its call and answers with the firing context's value for its name, nil when the context has none or outside a firing. A Map project's stub file uses it for a response Native the shipped families leave out.
- `__stub_with_context(context, body)` runs `body` with `context` as the firing context and returns what `body` returned. The previous context comes back afterwards, also when `body` throws, so a firing inside a firing hands the outer context back when it ends. The firing helpers use it.

The baseline also replaces the standard library's `os.clock` with a clock the test sets: it answers 0.0 until `__stub_set_clock(seconds)` sets a value, keeps that value until the next set, and `__stub_set_clock` returns the value it replaced. The game's `os.clock` is a local, async value (it differs between clients), so a test controls lobby and start times exactly. `os.clock` is not a Native: reading it adds no call-log line.

A timer or trigger never fires on its own, and a sent sync packet reaches no one: a test fires or delivers it with the helper. The helpers are not Natives, so they add no call-log line. A TypeScript test gets their declarations, and those of every other `__stub_*` helper of the shipped stubs with the types they take (the firing context `StubContext` among them), by adding `reforged-test/stubs` to the `types` of its tsconfig, next to the Typings it names; nothing is copied, and a test of the package fails when the declarations stop matching the Lua.

#### Constants and converters

A constant of the game is an opaque value made with `__stub_constant` (a whole family with `__stub_constants`): it carries its kind and its name, no handle id, and renders by name in the call log (`PLAYER_COLOR_BLACK`, `CAMERA_FIELD_ZABSOLUTE`). A test compares constants by identity (`toBe`), and defining them leaves the handle sequence alone. Besides the event constants (below), the shipped stubs define the `PLAYER_COLOR_*`, `RACE_PREF_*`, `ITEM_TYPE_*`, `CAMERA_FIELD_*`, `MOUSE_BUTTON_TYPE_*` and `PATHING_TYPE_*` families. A constant the Patch converts from the same integer as another is that other value: `ITEM_TYPE_TOME` is `ITEM_TYPE_POWERUP`.

**The sentinel rule.** The equipment converters `ConvertEquipmentType`, `ConvertItemTag` and `ConvertLoadoutSlot` are recorded, and each returns one cached value, a sentinel, per integer: the same integer gives the same object on every call, as in the game. The named constants are those sentinels, so `ConvertEquipmentType(1)` is `EQUIPMENT_TYPE_HEAD`, and a value the code under test converts compares by identity with the constant it names.

| Converter              | Named constants, by integer                                                                                              |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `ConvertEquipmentType` | `EQUIPMENT_TYPE_NONE` (0) to `EQUIPMENT_TYPE_ANY` (9), in the Patch's order                                              |
| `ConvertItemTag`       | `ITEMTAG_TYPE_UNDEFINED` (0) to `ITEMTAG_TYPE_ANY` (8)                                                                   |
| `ConvertLoadoutSlot`   | `EQUIPMENT_LOADOUT_SLOT_HEAD` (0) to `EQUIPMENT_LOADOUT_SLOT_TRINKET` (8), `EQUIPMENT_LOADOUT_SLOT_RINGALT` (5) included |

An integer with no named constant gets a sentinel of its own, distinct from every named constant and rendered as the call that made it, `ConvertEquipmentType(42)`. That is how a test builds a value the code under test does not know, one a later Patch might add: it converts an unnamed integer and makes the Native under test return it.

```ts
expect(ConvertEquipmentType(1)).toBe(EQUIPMENT_TYPE_HEAD);
const unknown = ConvertEquipmentType(42); // no EQUIPMENT_TYPE_* is this value
```

No sentinel takes a handle id. The older converters `ConvertEffectType` and `ConvertFogState` do not follow the rule yet: each call returns a new handle, which takes an id.

#### Triggers, conditions and the firing context

**Registrations.** The triggers family defines all 26 `TriggerRegister*` Natives of the Patch, the `Blz` ones included: `TriggerRegisterVariableEvent`, `TriggerRegisterTimerEvent`, `TriggerRegisterTimerExpireEvent`, `TriggerRegisterGameStateEvent`, `TriggerRegisterDialogEvent`, `TriggerRegisterDialogButtonEvent`, `TriggerRegisterGameEvent`, `TriggerRegisterEnterRegion`, `TriggerRegisterLeaveRegion`, `TriggerRegisterTrackableHitEvent`, `TriggerRegisterTrackableTrackEvent`, `TriggerRegisterCommandEvent`, `TriggerRegisterUpgradeCommandEvent`, `TriggerRegisterPlayerEvent`, `TriggerRegisterPlayerUnitEvent`, `TriggerRegisterPlayerAllianceChange`, `TriggerRegisterPlayerStateEvent`, `TriggerRegisterPlayerChatEvent`, `TriggerRegisterDeathEvent`, `TriggerRegisterUnitStateEvent`, `TriggerRegisterUnitEvent`, `TriggerRegisterFilterUnitEvent`, `TriggerRegisterUnitInRange`, `BlzTriggerRegisterFrameEvent`, `BlzTriggerRegisterPlayerSyncEvent` and `BlzTriggerRegisterPlayerKeyEvent`. Each records the trigger and one argument per parameter of the Native, so an omitted filter shows as `nil`, and returns a new `event` handle:

```text
TriggerRegisterPlayerUnitEvent(trigger#1048578, player#1048577, EVENT_PLAYER_UNIT_DEATH, filterfunc#1048579)
TriggerRegisterEnterRegion(trigger#1048578, region#1048581, nil)
```

No stub decides which event fires: the test does, by firing one trigger or dispatching one event, or by calling a Dispatching Native (below), which fires its event as the game would. A registration of a Native that names its event (`TriggerRegisterPlayerUnitEvent`, `TriggerRegisterUnitEvent`, `TriggerRegisterFilterUnitEvent`, `TriggerRegisterPlayerEvent`, `TriggerRegisterGameEvent`, and `TriggerRegisterDeathEvent` for `EVENT_WIDGET_DEATH`) also remembers its trigger, its event, its subject (the player, the unit or the widget it watches; none for a game event) and its filter, so that an Event dispatch finds the triggers the game would fire (below). The other exceptions are `BlzTriggerRegisterPlayerSyncEvent`, which also remembers its trigger, player and prefix, because a delivery must find the triggers the game would fire for a packet (below), and a registration for a damage event (`EVENT_UNIT_DAMAGED`, `EVENT_UNIT_DAMAGING` through `TriggerRegisterUnitEvent`, their `EVENT_PLAYER_UNIT_` twins through `TriggerRegisterPlayerUnitEvent`), which also remembers its trigger, its unit or player, its event and its filter, because `UnitDamageTarget` dispatches damage to the triggers the game would fire for it (under Test controls).

**The event constants.** The constants these Natives take and the response Natives answer with are defined, in the order the Typings declare them, as opaque values rendered by name: every `playerunitevent`, `unitevent`, `playerevent`, `gameevent`, `widgetevent`, `dialogevent` and `frameeventtype` (`EVENT_PLAYER_UNIT_DEATH`, `EVENT_UNIT_EQUIP_ITEM`, `EVENT_PLAYER_MOUSE_DOWN`, `FRAMEEVENT_CONTROL_CLICK`), the `limitop`s, the game, player and unit states, the `alliancetype`s, and the `attacktype`, `damagetype`, `weapontype`, `mousebuttontype` and `oskeytype` values. A test compares them by identity.

**Conditions.** `Condition(func)` and `Filter(func)` are recorded and return a handle, of kind `conditionfunc` or `filterfunc`, that remembers `func`: a test sees whether the code under test wrapped a plain function, and with which factory. As JASS caches one `boolexpr` per code, a second call with the same function returns the same handle, until `DestroyCondition` destroys it; a new function gets a new handle. `DestroyCondition` is recorded and marks the handle destroyed. `TriggerAddCondition` stores the condition on the trigger and returns a `triggercondition` handle; `TriggerAddAction` stores the action and returns a `triggeraction` handle. `TriggerRemoveCondition` and `TriggerRemoveAction` remove the one with that handle, `TriggerClearConditions` and `TriggerClearActions` remove them all. `TriggerEvaluate` runs every condition and returns their conjunction; `TriggerExecute` and `TriggerExecuteWait` run the actions without the conditions. Both run at once, in the current firing context.

**Trigger state.** `DisableTrigger` and `EnableTrigger` set what `IsTriggerEnabled` answers (enabled until disabled), `TriggerWaitOnSleeps` what `IsTriggerWaitOnSleeps` answers (false until set). The stubs count nothing: `GetTriggerEvalCount` and `GetTriggerExecCount` answer 0 and `ResetTrigger` only records. `DestroyTrigger` and `DestroyTimer` are recorded and mark the handle destroyed, as `RemoveUnit`, `DestroyGroup`, `DestroyEffect` and `BlzDestroyFrame` do.

**Firing a trigger.** `__stub_fire_trigger(trigger, context)` fires the trigger as one event would. `context` is an optional table keyed by response Native name: for the length of the firing, every response Native answers with the context's value for its name, and nil for a name the context leaves out. Every condition runs first, in added order, even after one returned false; the actions run, in added order, only if every condition returned true. It returns whether the actions ran. A disabled trigger does not fire (it returns false), and firing a destroyed trigger is an error. Outside a firing, every response Native answers nil.

```ts
const ran = __stub_fire_trigger(trigger.handle, {
  GetTriggerUnit: dying.handle,
  GetKillingUnit: killer.handle,
});
```

A firing inside a firing (an action that fires another trigger) has its own context, and the outer one is back when it ends. Actions or conditions added or removed while the trigger runs take effect at its next firing.

**Dispatching an event.** `__stub_dispatch(event, subject, context)` is the Event dispatch: it delivers `event` on `subject` to every trigger registered for it, as the game would, once per registration and in registration order. A disabled or destroyed trigger is skipped, checked when its turn comes; a registration's filter runs with `GetFilterUnit` answering the context's `GetTriggerUnit`; then the trigger fires as `__stub_fire_trigger` fires it, its conditions before its actions, before the next registration. The Firing context is `context`, with the trigger as `GetTriggeringTrigger` and, unless `context` gives one, `event` as `GetTriggerEventId`. No registration is no error. It reaches the registrations of `TriggerRegisterPlayerUnitEvent`, `TriggerRegisterUnitEvent`, `TriggerRegisterFilterUnitEvent`, `TriggerRegisterPlayerEvent`, `TriggerRegisterGameEvent` and `TriggerRegisterDeathEvent`, none of another registration Native: a registration of `TriggerRegisterTimerEvent` is reached by the Game clock alone, and one of `TriggerRegisterTimerExpireEvent` by the expiry of its timer (both below). It returns how many triggers ran their actions. On `reforged-test/map`, `game.fire(event, context)` calls it, the subject derived from the context ([the guide](https://phmilk.github.io/reforged-ts/docs/guides/testing-your-map#making-the-game-happen)).

**The Dispatching Natives.** Six Natives of `units.lua` dispatch their events through the Event dispatch inside the call, on `reforged-test/lua` and `reforged-test/map` alike, as two Probes measured the game firing them ([Which unit Natives fire their event inside the call](https://github.com/phmilk/reforged-ts/blob/master/docs/research/unit-event-timing.md), [Five facts of the Dispatching Natives](https://github.com/phmilk/reforged-ts/blob/master/docs/research/dispatching-natives.md)); a player unit event reaches the registrations of the unit's owner (the new owner for a change of owner), before the unit event, as in the game, whichever was registered first. They fire nothing where the game fires nothing:

- `KillUnit(unit)` marks the unit dead, then dispatches the widget death (`TriggerRegisterDeathEvent`), `EVENT_PLAYER_UNIT_DEATH` and `EVENT_UNIT_DEATH`; `GetKillingUnit` answers nil. A dead unit fires nothing. `__stub_kill_unit(unit, killer?)` is that death without the Native: it records no call, checks nothing, a unit already dead included, and answers `killer` as `GetKillingUnit` in the two death events of the unit, never in the widget death. On `reforged-test/map`, `game.kill(unit, { by })` calls it, after refusing what the game refuses.
- `SetUnitOwner(unit, player, changeColor)` sets the owner, then dispatches `EVENT_PLAYER_UNIT_CHANGE_OWNER` of the new owner and `EVENT_UNIT_CHANGE_OWNER`; `GetChangingUnitPrevOwner` answers the previous owner. The same owner fires nothing.
- `UnitAddItem(unit, item)` and `UnitAddItemById(unit, itemId)` put the item in the inventory, then dispatch `EVENT_PLAYER_UNIT_PICKUP_ITEM` and `EVENT_UNIT_PICKUP_ITEM`. For an item the unit carries, `UnitAddItem` dispatches the two drop events first. A unit whose `UnitInventorySize` answers 0 gets nothing and fires nothing: `UnitAddItem` returns false, and `UnitAddItemById` returns nil, as the game leaves the item it made on the ground and returns nothing; the stub makes that item too, and no Shipped stub reads it back.
- `UnitRemoveItem(unit, item)` dispatches `EVENT_PLAYER_UNIT_DROP_ITEM` and `EVENT_UNIT_DROP_ITEM`, the item still carried in the handler, then takes it out. An item the unit does not carry fires nothing and stays where it is.
- `UnitRemoveItemFromSlot(unit, slot)` is that drop for the item in the slot, which it returns: the item is still in its slot in the handler. An empty slot fires nothing and returns nil.

The guide's [table of Dispatching Natives](https://phmilk.github.io/reforged-ts/docs/guides/testing-your-map#making-the-game-happen) lists what a handler reads under each. `RemoveUnit` dispatches nothing, and a lethal `UnitDamageTarget` no death.

```ts
__stub_dispatch(EVENT_PLAYER_UNIT_SPELL_EFFECT, Player(0), {
  GetTriggerUnit: caster.handle,
  GetSpellAbilityId: FourCC("AHtb"),
});
```

**Delivering a sync packet.** `__stub_deliver_sync(packet, options)` delivers a packet as the game would: it fires every trigger registered with `BlzTriggerRegisterPlayerSyncEvent` for the packet's prefix and sender, once per registration and in registration order, with the context `{ BlzGetTriggerSyncPrefix = prefix, BlzGetTriggerSyncData = data, GetTriggerPlayer = from, GetTriggeringTrigger = trigger }`. A disabled or destroyed trigger is skipped. `packet` is a table `{ prefix, data, from }`: one `__stub_sync_packets()` recorded, or one the test builds, which is how a packet from another library or a corrupted one is simulated. Packets are delivered in whatever order the test chooses, each as often as it chooses. With `{ cString = true }` as `options`, the data is cut at its first zero byte, as the game cuts a C string. It returns how many triggers ran their actions.

```ts
BlzSendSyncData("P", "payload"); // recorded, from the local player
const [packet] = __stub_sync_packets();
__stub_deliver_sync(packet, { cString: true });
```

`BlzSendSyncData` returns true; a test that needs a network failure overrides it to return false for the length of that test.

**The Game clock.** The timers family keeps the game time of the Lua state: it starts at 0, nothing expires on its own, and only `__stub_advance_time(seconds)` moves it, on `reforged-test/lua` and `reforged-test/map` alike (`game.advanceTime(seconds)` calls it, [the guide](https://phmilk.github.io/reforged-ts/docs/guides/testing-your-map#time)). It is not `os.clock`, which `__stub_set_clock` sets. An advance runs every expiry inside the window:

- in the order of their instants, ties in the order of `TimerStart`, the clock standing at each instant while its handler runs, with the timer as `GetExpiredTimer`'s answer;
- the Triggers of a timer's expire event (`TriggerRegisterTimerExpireEvent`) at each expiry of that timer, before its handler, through the Event dispatch, with `EVENT_GAME_TIMER_EXPIRED` as `GetTriggerEventId`'s answer and the timer as `GetExpiredTimer`'s ([the findings](https://github.com/phmilk/reforged-ts/blob/master/docs/research/timer-expire-event.md#the-expire-event));
- a periodic timer once per period, armed again from the instant it was started, without drift;
- a timer a handler starts in the same advance, when it expires inside the window;
- a one-shot timer of timeout 0 on the next advance, one of 0 seconds included, never inside `TimerStart`; a periodic one every 0.0001 s, the period the game runs it at ([the findings](https://github.com/phmilk/reforged-ts/blob/master/docs/research/timer-answers.md#a-timer-of-timeout-0));
- a Trigger of `TriggerRegisterTimerEvent` through the Event dispatch, once or once per `timeout`, so a disabled or destroyed one is skipped and its conditions run before its actions.

The advance ends with the clock at its start plus `seconds`. An error a handler throws leaves it, the clock stopped at that instant. `DestroyTimer`, `PauseTimer` and a new `TimerStart` cancel the pending expiry, so a destroyed or paused timer is skipped silently. A negative or an endless advance is an error, and so are an advance inside a handler and more than 100000 expiries at one instant, which is a handler that starts a timer of timeout 0 every time it runs.

**What a timer reads.** `TimerGetElapsed`, `TimerGetRemaining` and `TimerGetTimeout` answer what the Probes measured in the game ([the findings](https://github.com/phmilk/reforged-ts/blob/master/docs/research/timer-answers.md)), by one model ([its rule](https://github.com/phmilk/reforged-ts/blob/master/docs/research/timer-resume-cases.md#one-rule-that-fits-every-case)). A timer keeps one stored remaining: 0 at first, written only when `PauseTimer` stops a running timer, and kept across `TimerStart`.

| Timer                                       | `TimerGetElapsed`                        | `TimerGetRemaining`       |
| ------------------------------------------- | ---------------------------------------- | ------------------------- |
| running                                     | the time since `TimerStart`              | the timeout minus it      |
| periodic, in its handler                    | the timeout                              | 0                         |
| periodic, once its handler returned         | 0, counting again                        | the timeout, counting     |
| not running: never started, paused, expired | the timeout minus the stored remaining   | the stored remaining      |
| resumed, counting                           | the time since `ResumeTimer` or its fire | what is left of the count |

So a timer never started reads 0 and 0, a paused one what it read at the pause, and a one-shot timer the timeout and 0 from its handler on. A one-shot timer started again after a pause reads, once it expired, the remaining of that pause and a negative elapsed time, as in the game. Right after its start a timer of timeout 0 has 0.0001 s left, while `TimerGetTimeout` answers 0. `PauseTimer` on a timer that is not running writes nothing.

**`ResumeTimer`** copies the game, which does not take the countdown up where the pause left it ([the findings](https://github.com/phmilk/reforged-ts/blob/master/docs/research/timer-resume-cases.md)):

- on a timer that is not running, it counts the stored remaining, fires, counts the timer's current timeout, fires once more and stops, one-shot or periodic alike, with the handler of the last `TimerStart`. In both handlers, and once stopped, the timer reads the values of the pause;
- on a running timer, resumed or not, it does nothing;
- a count of 0 (an expired one-shot timer, resumed) ends on the next advance, one of 0 seconds included, never inside the call;
- `TimerStart` is always an ordinary start, and drops what a resume had left to do;
- a timer never started, resumed, fires the Triggers of its expire event once, on the next advance, and that is all;
- in the first of its two fires the timer is not running, and its second count starts when the handler returns, whatever a `ResumeTimer` or `PauseTimer` in the handler did; a `TimerStart` or `DestroyTimer` there ends the resume ([the findings](https://github.com/phmilk/reforged-ts/blob/master/docs/research/timer-expire-event.md#a-call-a-handler-makes-on-its-own-timer));
- a Trigger of the expire event runs before the handler of its expiry, which then runs whatever the Trigger did to the timer, a `DestroyTimer` included, and is the handler of a `TimerStart` the Trigger made ([the findings](https://github.com/phmilk/reforged-ts/blob/master/docs/research/timer-expire-event.md#a-call-a-trigger-of-the-expire-event-makes-on-its-timer)).

**Firing a timer.** `__stub_fire_timer(timer)` runs the handler `TimerStart` stored with the context `{ GetExpiredTimer = timer }`, so `GetExpiredTimer` answers the fired timer inside the handler and nil after. It moves no clock, arms nothing and fires no expire event: the timer's pending expiry stays as it was, and inside the handler the timer reads and answers as in the handler of an expiry, until the handler starts it again: the timeout and nothing left, a one-shot timer not running. Firing a timer that was never started, or was destroyed, is an error.

#### Test controls

The controls a test uses to observe what a Map project observes, beyond firing triggers and timers. None is a Native, so none adds a call-log line. `reforged-test/stubs` declares them, as it does the firing helpers.

**The local player.** `GetLocalPlayer` answers the player in slot 0 until `__stub_set_local_player(slot)` makes another slot the local player; it returns the slot it replaced, so a test puts it back. `__stub_local_player()` returns the local player's handle. A test runs the same code as the matching client and as another one:

```ts
const previous = __stub_set_local_player(1); // run as the client of slot 1
runTheCodeUnderTest(); // GetLocalPlayer() is Player(1) here
__stub_set_local_player(previous);
```

**Output capture.** The baseline replaces the standard `print`: it writes to a capture instead of the terminal, one line per call with its arguments converted by `tostring` and joined by a tab. `__stub_printed()` returns the lines so far, oldest first. The display family (`display.lua`) keeps each message `DisplayTextToPlayer`, `DisplayTimedTextToPlayer` and `DisplayTimedTextFromPlayer` showed, and `__stub_displayed()` returns them, oldest first, as `{ native, player, x, y, duration, text }` (`duration` nil for `DisplayTextToPlayer`, `text` as given, `%s` included). The capture keeps the player each message was sent to, local or not: which client sees it is the test's comparison with the local player. `ClearTextMessages` is recorded and clears nothing from the capture. Both lists grow for the whole Lua state, so a test takes their length before the code under test runs and reads what came after it.

**The globals Init stage.** `__stub_init_globals()` enters the globals Init stage as the editor's `main` does: it calls the global `InitGlobals`, after defining it as an empty function when nothing defined it yet. The definition is a plain assignment, so the library's interception of `_G` wraps it as it wraps the editor's, and the library's globals stage runs (its `Player` and `CreateTrigger` lines are in the call log). A test that drives the whole editor script defines the entry points itself instead.

**Nested damage dispatch.** `UnitDamageTarget(source, target, amount, attack, ranged, attackType, damageType, weaponType)` is recorded, dispatches the damage at once with `__stub_dispatch_damage`, and returns true; the target is unchanged (no life, no armor). A test dispatches a damage event of its own with `__stub_dispatch_damage(damage)`, `damage` being `{ source, target, amount, attack?, attackType?, damageType?, weaponType? }`. A dispatch fires every trigger registered for a damaging event on the target, then every one registered for a damaged event, once per matching registration and in registration order, skipping a disabled or destroyed trigger. A registration matches when it was made on the target (`TriggerRegisterUnitEvent`) or on the target's owner (`TriggerRegisterPlayerUnitEvent`) with a filter that is absent or returns true with `GetFilterUnit` answering the target. The firing context answers `GetTriggerUnit` and `BlzGetEventDamageTarget` (the target), `GetEventDamageSource`, `GetEventDamage`, `BlzGetEventIsAttack`, `BlzGetEventAttackType`, `BlzGetEventDamageType`, `BlzGetEventWeaponType`, `GetTriggeringTrigger` and `GetTriggerEventId`. It returns how many triggers ran their actions.

An action that deals damage dispatches again inside its own firing, with its own context, and the outer context is back when the inner dispatch ends: a damage handler that damages back re-enters as in the game. The game has no limit and the client crashes; the harness stops a dispatch nested more than 32 deep with the error `__stub_dispatch_damage: damage dispatch nested more than 32 deep`, so a loop the code under test fails to stop fails its test instead of exhausting the VM.

**The arguments of a call.** The call log renders a function as `<function>`. `__stub_args(name)` returns the arguments of every recorded call of the Native `name`, oldest first, one list per call with `n` its argument count (nil arguments included), each value the very object the Native was given. It is how a test checks which function a Native received, for instance that the handler `TimerStart` stored or the function `Condition` wrapped is, or is not, the one the test passed. Stored callbacks are also run by the firing helpers above: `__stub_fire_timer` runs the handler `TimerStart` stored, and `__stub_fire_trigger` evaluates the conditions and runs the actions a trigger holds.

```ts
const handler = () => {};
timer.start(1, false, handler);
const [call] = __stub_args("TimerStart");
expect(call[3]).toBe(handler);
```

#### Stub authoring rules

- Stubs are plain Lua 5.3 and must run on stock Lua without `debug`, `require`, `package` beyond `preload`, `io`, `collectgarbage`, `os.getenv` or `load`. The game lacks the first six.
- Every stub appends one readable line to the global call log, `Name(arg, arg)`, with handles rendered as `kind#id`. Use `__stub_record`.
- Handles are tables carrying a kind and a sequential id from a fixed base, so ids are deterministic. Use `__stub_new_handle`.
- A stub schedules nothing by itself: game time moves only on the test's order, and manual firing stays. A stub that holds a callback exposes a manual firing helper (`__stub_fire_timer`, `__stub_fire_trigger`), and one whose callback waits for game time arms it on the Game clock with `__stub_schedule(timeout, periodic, expire)`, which only `__stub_advance_time` runs.
- A stub keeps only the state its Natives were given and hands it back through the Natives that read it: enumerating a stored group (`ForGroup`), reading a stored inventory slot, a frame's parent or child, a frame by the name it was created under. What no Native reads back in the game (a sent sync packet, the strings a file was written with, a displayed message, the arguments of a call) is handed to the test through a helper (`__stub_sync_packets`, `__stub_preload_file`, `__stub_displayed`, `__stub_args`). It never simulates game rules: no inventory size or first-free-slot rule (`UnitInventorySize` answers 6 for every unit, and no Native caps the slots at it), no order, no frame layout. A timer is the one state that follows a rule of the game, its readings and `ResumeTimer` copied from what the Probes measured (above), and it still moves only on the test's order. An event happens only on the test's order, or inside a Native a Probe showed fires it synchronously in the game, damage being the first case: `UnitDamageTarget` and the Dispatching Natives dispatch theirs inside the call, and a chain of handlers is what a test of them observes.
- There is one stub file per Native family: players, timers, triggers, units, frames, as they are needed. The glue loads the shipped set, then the extra stub files a Map project lists in the `stubs` option.

### Integer width policy

The VM has 64-bit integers and the game has 32-bit integers. Tests must not depend on integer width:

- no overflow;
- no bit operations above 31 bits;
- no `math.maxinteger`.

A test that needs 32-bit semantics carries `[32-bit]` in its name, or in the name of an enclosing `describe`. The glue skips it until a 32-bit run is added; the first such test decides that addition.

```ts
it("wraps around at 2^31 [32-bit]", () => {
  // ...
});
```
