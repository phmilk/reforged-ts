# Diagrams are generated from structured sources and hand-written behind a convention test

The documentation draws the workspace as Mermaid diagrams for new Collaborators and their Agents: the packages, the development loop, an issue's life, the CI of a pull request, the release and a Patch's adoption. A diagram nobody keeps true misleads an Agent more than no diagram, since it reads the diagram as fact. We decide how each one stays true by where its facts come from. A diagram whose source is structured and in the repository (the packages' `package.json`, the workflows' jobs and `needs:`) is generated by `pnpm diagrams:generate` into marked regions of the doc it belongs to, and `pnpm diagrams:check`, a Drift check, fails on any difference; it runs in `pnpm check` and in `ci.yml`. A diagram whose source is prose, or lives outside the repository (the Agent skills of `mattpocock/skills`), is written by hand, and `test/conventions/diagrams.test.ts` checks that every identifier it cites exists (a workflow file, a root script, a package, an Agent skill) and that it shows every member of the set it declares it covers. Each diagram sits beside the prose that is its source of truth, with that prose and a table of its nodes next to it; the README's "Map" lists them all, and `AGENTS.md` points at the Map in one line.

## Considered options

- A rule in `AGENTS.md` and the Definition of done alone, "update the diagram in the same pull request". It costs a line of context on every turn, binds only an Agent that remembers it, never a person, and catches nothing; the convention test's failure message carries the same instruction at the moment it matters.
- Every diagram generated. The development loop, an issue's life and a Patch's adoption have no structured source: their order and their emphasis are a judgement, and the loop's skills are not in the repository CI checks out.
- Every diagram by hand, behind the convention test alone. It catches a renamed or missing name, but not a job moved in `needs:` or a dependency added between packages, which the structured sources state exactly; the missing `builtins:check` step of `ci.yml` (#667) is the drift a generated CI diagram shows.
- A central `docs/diagrams/` folder, one file per diagram. Easier to generate and to test, but a diagram away from the prose it summarises is a second place to keep true, and a reader of the prose never meets it.

## Consequences

- A hand-written diagram can draw a wrong edge between two names that exist; the test does not see it. That is the price of drawing what no file states.
- The published package READMEs carry no diagram: npm's rendering of Mermaid is unconfirmed, and a diagram there would cost a changeset and a release of the package on each change. They link the diagram instead.
- The docs site renders Mermaid (`@docusaurus/theme-mermaid`), since `CONTRIBUTING.md`, `CONTEXT.md`, the ADRs and the packages' `AGENTS.md` are collected into it; the Markdown copies of `llms.txt` keep the diagrams' source text, which an Agent reads.
- A new workflow, package or Agent skill fails `pnpm check` until the diagram that covers its set shows it.
