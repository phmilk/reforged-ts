# HiveWE: compatibility with a Map project, and features worth adopting

Research note for ticket [#471](https://github.com/phmilk/reforged-ts/issues/471), part of the map [#457](https://github.com/phmilk/reforged-ts/issues/457). Facts only, no decision. Written 2026-10-05.

Sources: the code of [stijnherfst/HiveWE](https://github.com/stijnherfst/HiveWE) at `cbfd6b3` (2026-09-22, the head of `main`), its tag `v0.10`, its issues, pull requests, releases and wiki (`e5cee50`, 2026-09-13). Permalinks below point to `cbfd6b3` unless they name another commit. The Template is read at the copy in the maintainer's workspace (`reforged-ts-template`, `scripts/`, `maps/reforged-ts-template.w3m`). Vocabulary from `CONTEXT.md`: **Rawcode**, **Object data** (the seven `war3map.w3*` files, their `war3mapSkin.w3*` counterparts and `war3map.wts`), **Built-in object**, **Custom object**, **Object Editor** (the World Editor's only), **Game data set**. Earlier findings this note builds on: [#460](https://github.com/phmilk/reforged-ts/blob/research/object-data-editors-and-libraries/docs/research/object-data-editors-and-libraries.md) (HiveWE's Object data writer) and [#461](https://github.com/phmilk/reforged-ts/blob/research/world-editor-open-object/docs/research/world-editor-open-object.md) (the World Editor rewrites the whole map folder on every save).

**HiveWE was not run.** It keeps its settings with Qt's `QSettings` in the default native format, which on Windows writes to the registry (`HKCU\Software\…`) as soon as a map folder is opened ([hivewe.cpp L448-L462](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/main_window/hivewe.cpp#L448-L462)), and the ticket forbids touching the registry. Running it would also show the wrong version. The only release, 0.10 (2026-05-18), predates 3.0 support (section 1.1). `main` has no binary: its CI has failed since April 2026, and a local build needs Visual Studio 17.14, vcpkg and a 15–20 minute Qt build. So everything below comes from the code, plus one run of the Template's own generator on a script shaped like HiveWE's output (section 2.2).

## Answer

**Compatibility costs little on the Template's build side and some data on the map side. Each break has a small fix on our side or upstream.**

What breaks when HiveWE saves a Map project's map folder:

1. **Only an unreleased HiveWE reads a 3.0.0 map.** Release 0.10 reads `war3map.w3i` version 39 and the version-13 `war3map.doo` / `war3mapUnits.doo` with their pre-3.0 layouts. It only prints "Unknown version" and carries on, misreading every field after the first change. `main` reads them since `9f04c14` (2026-09-20), but no release has it yet; the window title says 0.11.
2. **Even `main` drops 3.0 data when it saves.** It writes `war3map.doo` and `war3mapUnits.doo` as version 8, losing the 3.0 per-object group id, roll, pitch and lights. It stamps `war3map.w3i` as editor 6116 and game 2.0.3.22978 on top of a version-39 body. It moves every Object data field into `war3map.w3*` and leaves each `war3mapSkin.w3*` with the objects but zero modifications. It inlines edited strings instead of keeping `TRIGSTR_nnn`. It drops field ids missing from the install's metadata. It writes Custom objects with random Rawcodes (`qzxa`, `Qzxa` for heroes), not the editor's `h000`. It regenerates `war3map.lua` from the triggers.
3. **Template: the build still works, but `editor-globals.d.ts` silently loses types.** `war3map.lua` is still there (Lua mode is kept, the script is regenerated) and the bundle is still appended. Staging, composing and packing are unaffected, and `war3map.w3i` stays opaque to the packer. But HiveWE declares every scalar Variable Editor global `nil` and every array `__jarray("")`. The generator then types `udg_Score` as `unknown` and an integer array as `Record<number, string>`, a wrong type that compiles (measured, section 2.2). HiveWE also adds `hiveWE/terrain_pathing.json`, `hiveWE/map_info_extras.json` and a `war3map.imp` to the map folder, and `pack.ts` packs them into the archive.
4. **Object data readers.** A reader that follows the World Editor's layout (the name in `war3mapSkin.w3u` as a `TRIGSTR`, `h000` Rawcodes) misses HiveWE's layout (the name in `war3map.w3u` as a literal, random Rawcodes), and the reverse is also true. Reading both files, merging the skin over the base and resolving `TRIGSTR` when present covers both. `mdx-m3-viewer-th` skips the skin files (#460), so on a HiveWE save it happens to see everything.
5. **In game**, all-in-the-base-file is "a valid state" by HiveWE's own comment. That is still not verified, as in #460.

The other direction, Object data our tools write opening in HiveWE: HiveWE reads Object data versions 1–3 and both file families, the skin file overriding the base. It **exits the process** on a modification type other than 0–3. It reads only the first set of a version-3 object, so a set count above 1 misaligns the rest of the file. It throws on a Custom object whose base Rawcode is not in the game data. It **drops any field id the install's metadata does not know** and loses it at its next save: a WurstScript-style marker field such as `wurs` (#458) does not survive one HiveWE save. A writer that follows the World Editor's own split (version as read, one set, types 0–3, the `netsafe` split, no private fields) opens without loss. A writer that only writes into the build's staged copy (`dist/`), as WurstScript does, is never seen by HiveWE at all.

Taking turns: like the World Editor (#461), HiveWE never watches the map folder (an open pull request, [#139](https://github.com/stijnherfst/HiveWE/pull/139), would add a reload on change) and rewrites the whole folder on every save. It also has no command line at all, so no tool can open a map, let alone an object, in it. The World Editor, HiveWE and any external editor can share a map folder only by taking turns, each closing (or reloading) before another saves. HiveWE's Test Map saves and runs the map folder as is, without the Map project's code, as the World Editor's does.

## 1. What HiveWE reads and writes

### 1.1 Versions: release 0.10 against `main`

- Release **0.10** (tag `v0.10`, 2026-05-18, [release page](https://github.com/stijnherfst/HiveWE/releases/tag/v0.10)) reads `war3map.w3i` versions 15–33 and writes 33 ([v0.10 map_info.ixx L166, L178-L180](https://github.com/stijnherfst/HiveWE/blob/v0.10/src/base/map_info.ixx#L166-L180)). On another version it prints "Unknown war3map.w3i version" and goes on reading with the version-33 layout. The same holds for `war3mapUnits.doo` (accepts 7 and 8, [v0.10 units.ixx L120-L124](https://github.com/stijnherfst/HiveWE/blob/v0.10/src/base/units.ixx#L120-L124)).
- The Template's map folder, saved by the 3.0.0 World Editor, has `war3map.w3i` version **39** (bytes `27 00 00 00`, editor 7000, game 3.0.0.24268) and `war3map.doo` / `war3mapUnits.doo` version **13**. Release 0.10 would therefore misread both. Version 39 inserts fields early (`loading_screen_source` right after the loading screen number), so nearly every later field is read from the wrong offset.
- `main` gained 3.0 readers in [`9f04c14`](https://github.com/stijnherfst/HiveWE/commit/9f04c1473d119c41e170e12d75f408ce20501f1c) "Update map file parsers" (2026-09-20): `w3i` 39, doodads and units 13, regions, cameras. It has not been released; the title bar on `main` reads "HiveWE 0.11" ([hivewe.cpp L445](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/main_window/hivewe.cpp#L445)).

### 1.3 Object data in detail

From [modification_tables.ixx](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/utilities/modification_tables.ixx). #460 covered the same code; the points that matter for compatibility:

- **Load.** Versions 1–3; any other version prints a warning and goes on (L88-L91). For version 3 it reads one set count and one flag, and prints a message on a count above 1 without reading the other sets (L22-L28). A Custom object is created by copying its base row (L29-L31). `copy_row` assumes the base exists, and `base_data.at` throws when it does not ([slk.ixx L478-L496](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/file_formats/slk.ixx#L478-L496)). A modification type other than 0–3 calls `exit(1)` (L65-L67). The end marker is skipped unread (L69). A field id missing from the metadata is dropped ("Unknown mod id", L71-L74).
- **Save.** Version 3 (L14). Built-in objects go in the first table with a zero new id, Custom objects in the second with their base in the HiveWE-only `oldid` property (L103-L118). Set count 1, flag 0 ("1.33 fields not yet researched", L120-L122). The skin files get every object with zero modifications ("No changes in skin files and all in main ones is a valid state, but not nice", with a note that `netsafe` "is probably what vanilla uses", L124-L130). The stored type is recomputed from the metadata `type`: int, bool, `*Flags` and a few enums as 0, `real` as 1, `unreal` as 2, everything else as a string (L152-L162). Floats go through `std::to_string`, which keeps 6 decimals (L60, L190). The end marker is 0 (L195).
- **Order.** Objects and fields are kept in `ankerl::unordered_dense` maps ([unordered_map.ixx](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/utilities/unordered_map.ixx)), which iterate in insertion order. A save therefore keeps load order and appends new objects, but not the World Editor's own order.
- **Strings.** The table model shows `TRIGSTR_nnn` resolved through `war3map.wts` ([table_model.ixx L74-L81](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/models/table_model.ixx#L74-L81)), but an edit stores the literal text ([L236-L244](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/models/table_model.ixx#L236-L244)). The owner in [#126](https://github.com/stijnherfst/HiveWE/issues/126) (closed 2026-01): "HiveWE isn't TRIGSTR preserving at the moment so it will inline strings." The old string stays in `war3map.wts`, unreferenced.
- **New Rawcodes.** `get_unique_id` draws four random letters, the first upper-case for a hero (copying the base's case), and retries until no table of the seven kinds holds the id ([globals.ixx L40-L57](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/globals.ixx#L40-L57)). The World Editor numbers them `h000`, `h001`… (#461). An id is checked against the current install's game data only, so a later Patch could add a Built-in object with the same Rawcode (3.0.0 added 365 items, #459). The editor's digit pattern makes such a clash unlikely; four random letters do not.
- **Game data.** HiveWE loads the SLK, TXT and metadata files of the local install through CascLib ([map.ixx L180-L375](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/base/map/map.ixx#L180-L375)), with HD, teen, tileset and locale overrides ([hierarchy.ixx L89-L196](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/base/hierarchy.ixx#L89-L196)). It stores the map's Game data set (`game_data_set`, edited in its options dialog) but never selects the matching data. The defaults it shows are always those of the plain `war3.w3mod`, whatever set the map picks.

## 2. What breaks in the Template

The Template's pipeline ([README](https://github.com/phmilk/reforged-ts-template), `scripts/build.ts`): read `war3map.lua` from the map folder, copy the folder to `dist/staging/`, regenerate `src/generated/` (`env.ts`, `editor-globals.d.ts`, `editor-globals.lua`), compile the bundle, write `war3map.lua` + newline + bundle into the staged copy, pack the staged copy. The map folder is only read.

### 2.1 Build, compose, pack: works, with extra files

- `readEditorScript` needs `war3map.lua`. HiveWE writes it whenever the `w3i` Lua flag is set, which it keeps ([map.ixx L668-L673](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/base/map/map.ixx#L668-L673), [map_script.cpp L875-L899](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/base/triggers/map_script.cpp#L875-L899)). One trap applies only to release 0.10: misreading a version-39 `w3i` could misread the Lua flag. HiveWE would then write `war3map.j` through JassHelper and leave the old `war3map.lua` in place, which the Template would silently keep building on. This was not observed.
- `composeMapScript` appends the bundle byte for byte. HiveWE's script defines `main`, `config`, `InitGlobals`, `InitCustomTriggers` and `RunInitializationTriggers` unconditionally (L429-L452, `generate_main`, `generate_map_configuration`). Those are the globals the library's Init stages and entry points wrap (`packages/reforged-ts/src/init/stages.ts`, `entry-points.ts`), so the stages still fire. HiveWE's `main` calls `InitSounds`, `CreateRegions`, `CreateCameras`, `CreateAllDestructables`, `CreateAllItems` and `CreateAllUnits` itself (L743-L753).
- `packMapFolder` packs every file. After a HiveWE save the archive also holds `hiveWE/terrain_pathing.json` and `hiveWE/map_info_extras.json` (dead weight, harmless) and HiveWE's `war3map.imp`, which `OpaqueW3iMap.save` stores byte for byte. It lists `war3map.w3l`, `war3map.w3grp` and every file under `war3mapImported/` as imports. Whether the game or the World Editor minds those two 3.0 files in the import list was not checked (likely harmless; the World Editor's Import Manager may show them).
- `war3map.w3i` stays opaque to the packer (the `OpaqueW3iMap` override from reforged-ts#32), so HiveWE's `w3i` stamp breaks nothing in the build.
- `pnpm dev` watches the map folder, so a HiveWE save triggers a rebuild, as a World Editor save does.

### 2.2 `editor-globals.d.ts`: loses types without a warning

`scripts/editor-globals.ts` reads the header of `war3map.lua` (the lines before the first column-0 `function`) and types each `udg_` global from its initializer there. A `nil` handle global gets its type from a Native call in `InitGlobals`. The 3.0.0 World Editor writes literal initializers in the header (`udg_Score = 0`, `udg_Kills = __jarray(0)`, `udg_Timers = {}`; the generator's test fixture, `tests/pipeline/editor-globals.test.ts`). HiveWE's Lua output differs ([map_script.cpp L44-L52, L105-L148](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/base/triggers/map_script.cpp#L44-L148), [triggers.ixx L61-L71, L185-L206](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/base/triggers/triggers.ixx#L61-L206)):

- every non-array variable is declared `udg_X = nil` in the header, and every array `udg_X = __jarray("")`, whatever its type;
- `InitGlobals` then assigns each variable its initial value or its type's default from `TriggerData.txt`, indented with tabs, arrays in `for i=0,N do … end`.

The generator was run (Node 24, the Template's own `generateEditorGlobals`) on a script written to that shape: scalars `Score`, `Rate`, `Name`, `Flag`; arrays `Kills`, `Speeds`; a `Group`; a timer array `Timers`. Result:

```ts
declare let udg_Score: unknown;
declare let udg_Rate: unknown;
declare let udg_Name: unknown;
declare let udg_Flag: unknown;
declare let udg_Kills: Record<number, string>; // an integer array
declare let udg_Speeds: Record<number, string>; // a real array
declare let udg_Group: NonNullable<ReturnType<typeof CreateGroup>>;
declare let udg_Timers: Record<
  number,
  NonNullable<ReturnType<typeof CreateTimer>>
>;
```

No warnings. Handle globals keep their types (the Native call in `InitGlobals` still decides). Scalars lose theirs (`unknown` forces casts), and numeric arrays get a **wrong** element type that type-checks. The Lua stub for `reforged-test` inherits `__jarray("")`, so a test reading an unset index gets `""`. HiveWE's own runtime has the same quirk: an integer array read past its declared size returns `""`, not 0. The input was written by hand from the code above, not saved by HiveWE (HiveWE was not run).

Fix: in `initGlobalsNatives`, also collect literal assignments (`udg_X = 0`, `udg_X[i] = 0.0`) and let them type the global when the header holds `nil` or `__jarray("")`. Alternatively, read the variables' types from `war3map.wtg`, which both editors write in the same format version.

### 2.3 A reader of Object data

What a reader (#465) must accept to read maps from both editors:

- names and other skin (`netsafe`) fields in `war3mapSkin.w3*` (World Editor) **or** in `war3map.w3*` (HiveWE): read both, the skin file wins, as both editors' loaders do;
- a string field holding `TRIGSTR_nnn` (World Editor) **or** the literal text (HiveWE after an edit);
- objects listed in a skin file with zero modifications (HiveWE), which mean nothing;
- Custom object Rawcodes of any four characters: `h000` (World Editor), random letters (HiveWE), anything (other tools). A kind or "custom" flag must come from which file and table the object is in, never from the Rawcode's shape;
- object and field order that differs from the World Editor's.

`mdx-m3-viewer-th`'s `readModifications` ignores the skin files (#460). On a HiveWE save it happens to see every field. On a World Editor save it misses Custom object names.

### 2.4 How the game treats a HiveWE save

Not verified, here or in #460: a `war3map.w3u` holding skin fields with an empty `war3mapSkin.w3u`; a 3.0.0 map whose `w3i` claims game 2.0.3; version-8 `doo` files in a 3.0.0 map. HiveWE's own comment calls the first "a valid state". The wiki believes the skin files hold `netsafe` fields because they "aren't in map_crc" ([war3map(skin).w3*-Modifications](<https://github.com/stijnherfst/HiveWE/wiki/war3map(skin).w3*-Modifications>)). That would make them matter for multiplayer, not for single player. Checking needs HiveWE built from `main` and the game, on the maintainer's machine.

## 3. The other direction: Object data our tools write, opened in HiveWE

From the loader above. A file opens in HiveWE without loss when it:

1. has version 1, 2 or 3 and, for version 3, one set per object (a second set misaligns the reader);
2. uses modification types 0–3 only (anything else ends the HiveWE process);
3. derives every Custom object from a Rawcode the local install's game data holds (else an exception on load);
4. uses only field ids in the install's `*MetaData.slk` (others are dropped on load and gone after HiveWE's next save);
5. puts `TRIGSTR_nnn` references in strings only when `war3map.wts` holds them (HiveWE resolves them, and an unresolved reference shows as empty).

Consequences:

- A marker field for objects made in code, as WurstScript's `wurs` (#458), does not survive one HiveWE save. Provenance must live outside Object data: a manifest in the Map project, or objects generated only into `dist/staging/` on each build, which neither editor ever opens.
- A writer that follows the World Editor's split (`netsafe` fields to the skin file) loads correctly in HiveWE. HiveWE then rewrites it in its own layout on the next save. The World Editor's next save presumably restores its own layout; whether it re-splits fields found in the base file is not verified.
- If our tools write Object data only into the staged copy, as the Template does with the script, no HiveWE compatibility question arises at all.

## 4. HiveWE and the World Editor on the same map

- HiveWE does not watch the map folder: the only `QFileSystemWatcher` is in its model editor. A save rewrites the files listed in section 1.2 from memory, so an edit another program made meanwhile is lost, exactly as with the World Editor (#461). Open pull request [#139](https://github.com/stijnherfst/HiveWE/pull/139) (2026-07-04, unmerged) would reload the map 500 ms after any change in its folder, "so external tools … edit terrain/units and have HiveWE reflect the changes". That would discard HiveWE's own unsaved edits, unless the change adds a guard.
- HiveWE's `main` ignores its command line ([main.cpp L38, L87](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/main.cpp#L38-L87)). A map is opened only through a folder dialog ([hivewe.cpp L448-L483](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/main_window/hivewe.cpp#L448-L483)), so there is no equivalent of the World Editor's `-launch -loadfile` reload, and no way to open an object from outside. Internally `ObjectEditor::select_id(category, id)` already opens one ([object_editor.cpp L545](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/object_editor/object_editor.cpp#L545)). A small upstream contribution (a command-line flag or a local socket) would make "open in HiveWE" possible for #468, and invoking HiveWE as a separate program raises no licence question.
- HiveWE's Test Map saves, then starts `Warcraft III.exe -launch -loadfile <map folder>` plus user arguments ([hivewe.cpp L709-L726](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/main_window/hivewe.cpp#L709-L726)). Like the World Editor's, it runs the map folder without the Map project's code; `pnpm test:map` is the way to test.
- Taking turns works with the same rule as #461: one program has the map open for writing at a time. Each save by either editor rewrites the other's layout: Object data split, `w3i` stamp, `doo` versions, `wts` comments. A Map project's git history then shows layout churn on every switch, and the 3.0 `doo` fields lost by a HiveWE save do not come back.

## 5. Features, in more detail

All from `src/object_editor/`, `src/models/` and `src/asset_manager/` at `cbfd6b3`, and from the [0.10 release notes](https://github.com/stijnherfst/HiveWE/releases/tag/v0.10).

- **Explorer per kind** with a tree by race and category, icons, a search box (Ctrl+F), and a "Hide default" toggle that leaves only objects the map changed or added ([object_editor.cpp L129-L133, L509-L530](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/object_editor/object_editor.cpp#L509-L530); filter in [base_tree_model.ixx L507-L522](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/models/tree/base_tree_model.ixx#L507-L522)). Changed objects are drawn violet and each has the tooltip `ID: <Rawcode>` ([base_tree_model.ixx L320-L347](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/models/tree/base_tree_model.ixx#L320-L347)). The tree search matches the displayed name only.
- **Global search** (double Shift, from any window): one list over the seven kinds plus actions. It matches the Rawcode or the name with its editor suffix, shows the icon, and puts `units/<race>/<id>` in grey on the right ([global_search.h](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/object_editor/global_search.h), [unit_list_model.ixx L32-L60](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/models/list/unit_list_model.ixx#L32-L60)). It has case, whole-word and regular-expression toggles.
- **Object page**: one docked tab per object, several side by side. Rows are built from the metadata: categories and display names, one row per level (`repeat`, with `levels`/`numvar`/`maxlevel`), data columns (`DataA`…), and abilities' `useSpecific`/`notSpecific` ([single_model.cpp L186-L260](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/models/single_model.cpp#L186-L260)). The row label is `Category - Name - Level n (fieldId)` (L98-L131), and changed fields are violet. Editors are typed: spin boxes, `targetList` flags, unit, ability and upgrade lists with icons, an icon grid and a model picker with live previews (L321-L380, [icon_view.cpp](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/object_editor/icon_view.cpp), [model_view.cpp](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/object_editor/model_view.cpp)). The `minVal`/`maxVal` limits are commented out (L321-L343). There is no undo in the object editor (undo exists for terrain, doodads, units, regions and pathing only) and no reset ([#125](https://github.com/stijnherfst/HiveWE/issues/125), open).
- **Ability insights**: `data/warcraft/ability_insights.json` holds 342 entries keyed by Rawcode (name, tags, notes, last tested version, free text). They are parsed by `generate_ability_insights.py` from a community Google Doc and shown above an ability's fields with a link inviting fixes in that document ([object_editor.cpp L30-L31, L154-L190](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/object_editor/object_editor.cpp#L154-L190)). Last tested versions: 279 entries on 1.28.5, a handful on 1.31–1.36, one on 2.0. The repository is AGPL-3.0 and the file carries no other licence; its text is community-written. Showing it on hover in our tools needs the authors' permission or a link to the document, not a vendored copy.
- **Icon tags**: `data/warcraft/icon_tags.json` maps each icon path to the names of the objects that use it, which makes the icon picker searchable by name ([icon_view.cpp L161-L185](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/object_editor/icon_view.cpp#L161-L185)). Those names are Blizzard's enUS strings, so we would generate the same index locally (#459), not copy it.
- **New object**: a modal dialog with a searchable base tree, a read-only name, and an id field prefilled with a free Rawcode. The id is re-drawn upper-case when the base is a hero, and validated live: 4 characters, unused, an object (not a folder) selected ([object_editor.cpp L319-L476](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/object_editor/object_editor.cpp#L319-L476)). Remove works on a multi-selection of Custom objects only. Doodads have "Convert to destructible" (L271-L305).
- **Drag and drop** ([`7473a8d`](https://github.com/stijnherfst/HiveWE/commit/7473a8d), [base_tree_model.ixx L230-L300](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/models/tree/base_tree_model.ixx#L230-L300)): dropping objects on another folder rewrites the fields that place them there (race, category…), asking first when that changes existing objects. A copy-drop creates new Custom objects with fresh Rawcodes in the target folder.
- **Asset manager** (0.10): every imported file with the objects and files that use it (followable up a chain), unused files, sizes, and model validation with severities ([asset_tree_model.h](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/asset_manager/asset_tree_model.h), [unused_files.cpp](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/base/map/unused_files.cpp)). The usage index is built from the Object data fields that hold paths, which is the same shape as a "who references this Rawcode" index built from `unitList` and `abilityList` fields.
- **Export with protection**: strips editor-only files (its list includes `war3map.wtg`, `war3map.wct`, `war3mapUnits.doo`, `war3map.w3r` and `war3map.doo`), can minify the script, remove metadata and encrypt imports ([hivewe.cpp L595-L707](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/main_window/hivewe.cpp#L595-L707), [protection.ixx](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/base/map/protection.ixx)). This is a Template idea for `--mode release`, outside this map's tickets. Whether `war3map.doo` really is editor-only was not checked.
- **Owner's stance** on code integration: TypeScript support was requested in [#62](https://github.com/stijnherfst/HiveWE/issues/62) (closed). The owner replied there that HiveWE outputs a Lua map script that "can be used together with w3ts", and that "In the future I might add some kind of integration with w3ts specifically". Object data from code was requested in [#38](https://github.com/stijnherfst/HiveWE/issues/38) (closed): "Maybe in the future, but not a priority at the moment." [#111](https://github.com/stijnherfst/HiveWE/issues/111): HiveWE is "missing in some areas … but … better than the standard WE like the object editor".
