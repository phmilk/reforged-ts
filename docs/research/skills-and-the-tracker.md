## 1. Answer

Every skill reaches `docs/agents/issue-tracker.md` by one road only: `CLAUDE.md` is the single line `@AGENTS.md`, and `AGENTS.md` ends its "Issue tracker" paragraph with "See `docs/agents/issue-tracker.md`" (L69) and its "Triage labels" paragraph with "See `docs/agents/triage-labels.md`" (L73). Four skills count on that road (`to-spec` L9, `to-tickets` L11 and `wayfinder` L25 say the tracker "should have been provided to you", `triage` L43 says it of the label mapping; only `wayfinder` names a section of the doc, "Wayfinding operations") and open the doc when they need a `gh` command, which is before their first write; two are silent on the tracker altogether (`implement`, 16 lines, and `implement-spec`), so a sentence in the doc reaches them only by chance, and the `agents/openai.yaml` prompts of all six carry a display name, a short description and `allow_implicit_invocation: false`, nothing about the tracker. The first writes: `triage` posts a comment (the Agent Brief or the triage notes) and the role labels two to three seconds later; `to-spec` and `to-tickets` run `gh issue create` (the spec; each ticket, blockers first, with its sub-issue link and blocked-by edges), with no assignee because neither skill mentions one; `implement` commits to the current branch and never writes to the tracker; `implement-spec` opens a branch and a draft pull request "closing" the spec and every ticket (L23); `wayfinder` claims (`gh issue edit <n> --add-assignee @me`) as its first write in work mode (L123; doc L50) but in chart mode creates the map and the tickets and fires the research subagents without claiming their tickets (L115). Only `wayfinder` claims today, and the loop's `next_frontier` already treats any assignee as the Claim and the open ticket as its stop signal. The evidence on #381, #372 and #377 (all 2026-10-03) shows the gap in one shape: the Agent's first write was the brief, its pull request followed 9 s to 13 min 34 s later with an empty "open the branch" commit, the first real commit came 17 min to 3 h 13 min after that, and the only `assigned` event on each issue is a self-assignment by another login at 21:15:22–27Z, after all three pull requests were open and, on #377, 22 minutes before its first real commit; the map's Notes state this order the other way round. So the Claim must be written where every session reads it (`AGENTS.md`, Rules) with the detail in the tracker doc's conventions list, and three places need a skill's own text: `implement-spec`'s one pull request for a whole spec, `wayfinder`'s research subagents at charting, and the loop's stop, which leaves a Claim on an open ticket with nothing on the ticket to say so.

## 4. The loop (`wayfinder-loop.sh`)

- **The map is a constant.** `MAP=359` (L15), `OWNER_REPO=phmilk/reforged-ts` (L16): a run over another map edits the script.
- **`next_frontier` (L31-38)** lists the map's open sub-issues with `(.assignees | length) == 0`, `issue_dependencies_summary.blocked_by == 0` and neither `wayfinder:grilling` nor `wayfinder:prototype`, first in sub-issue order. It assumes: the assignee is the Claim, whoever and however old it is (no stale rule: a stale Claim hides its ticket until a human unassigns, and the loop then prints "Frontier empty (or only HITL tickets left)", L49, without saying why); `research` and `task` tickets are AFK and takeable; only a frontier ticket is takeable, which is the map's "a map ticket on its frontier".
- **The queue bypasses the filter.** `bash wayfinder-loop.sh 8 409` runs "#409 first, then the map's frontier" (L7-8, L42-45) with no assignee check on the named ticket; the session's Claim is `--add-assignee @me`, so a ticket of another login would get a second assignee and be worked (3.6 b).
- **A race window.** Between `next_frontier`, `git switch -q master && git pull` (L57) and the session's own Claim (skill L123) pass seconds to a minute in which another session can claim the same ticket; two sessions of one login are invisible to the assignee test, since one login counts once.
- **`UNATTENDED` (L27)** assumes the Claim twice. "If the ticket is already assigned to you with an open PR from an earlier loop session, continue from that PR instead of redoing the work": assignee plus open pull request is a live Claim, the stale rule's own clause. "Leave the ticket OPEN, say exactly what is pending and in what state you left the branch and PR, and end: an open ticket is how the loop knows to stop" (checked at L82-85): the stop signal is the ticket's state, the Claim stays, and "say exactly what is pending" goes to the session's result in the JSON log (L70, L76-80), not to the ticket. A stopped ticket therefore carries an assignee and possibly no comment and no pull request: after 3 days the stale rule reads it as abandoned while the human was told `claude --resume`. It also has the Agent merge its own pull request "once the required checks pass", so Done (closed) follows without a human move.
- **The login.** "You run it, so each /wayfinder is your own invocation" (L10-11): the loop claims as the human's login, the map's "Agent = the Collaborator's login".
- **Consistency.** The protocol as charted keeps every assumption the loop makes (assignee as Claim, unassigned frontier, open ticket as stop) and adds two it does not know: the stale takeover, which the loop never performs (right: a loop should not take another login's ticket silently) and would not notice, and the stop comment, which the `UNATTENDED` text must ask for.

## 6. The sentences the tracker doc needs

Three placements, so that every road into the doc passes the Claim: a bullet in "Conventions" (L5-12), the list every skill opens for a command; a `## Claim` section before "Pull requests as a triage surface"; and the two "When a skill says" sections (L34-40) and the "Wayfinding operations" Claim line (L50) pointing at it. Proposed wording, kept to the protocol as charted on the map:

```markdown
## Conventions

- **Claim an issue**: `gh issue edit <number> --add-assignee @me`, before any work on it and before any other write (see "Claim").

## Claim

A Claim marks an issue as taken by one login. It binds every Collaborator and every Agent a Collaborator runs: an Agent writes as the Collaborator's login, so its Claim is the Collaborator's.

- **First write.** Before working on an issue, assign yourself: `gh issue edit <n> --add-assignee @me`. It comes before the branch, the first commit, any comment and the pull request. Read the issue back: if it now has two assignees, the later one withdraws (`--remove-assignee @me`) and says so in a comment.
- **Claimable.** An open issue with no assignee that is `ready-for-agent` or `ready-for-human`, or a wayfinder ticket on its frontier (no open blocker). Not claimable: `needs-triage` and `needs-info` (triaged, not claimed), a `spec` (split with `to-tickets`, not claimed), a map. Triage and splitting are not claimed: their writes are the brief, the labels and the new issues. A bug you find and fix at once: open the issue and claim it in one gesture.
- **One login per issue.** An issue assigned to another login is theirs: do not add yourself, do not post a brief on it, do not open a pull request that closes it. A second assignee is added only by the first, for pairing.
- **One issue at a time.** A Claim means working now. Do not claim a spec or several tickets to reserve them; say what you will take next in a comment; the native blocked-by orders the tickets.
- **Create without an assignee.** An issue created by `to-spec`, `to-tickets`, triage or an issue form has no assignee; whoever starts it claims it then.
- **Stale.** A claimed issue with no open pull request and no comment for 3 days. Any Collaborator may take it over: comment first (what and why), then `gh issue edit <n> --remove-assignee <login> --add-assignee @me`. The maintainer may reassign at any time.
- **Stopping.** Leaving a claimed issue open (a question for the human, red CI, a check only the game can settle): comment what is pending and where the branch and the pull request stand. The comment keeps the Claim fresh and tells the next session what to resume.
- **A pull request** is opened by the assignee of every issue it closes.

## When a skill says "fetch the relevant ticket"

Run `gh issue view <number> --comments`, and read its assignee: an assigned issue is taken (see "Claim"). Claim it before working on it.
```
