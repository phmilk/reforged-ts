# Built-in objects per Patch: sources and licence

Research for [#459](https://github.com/phmilk/reforged-ts/issues/459), part of the wayfinder map [#457](https://github.com/phmilk/reforged-ts/issues/457). The question: where can the Built-in objects of a Patch (units, items, abilities, buffs, destructables, doodads, upgrades: Rawcode, enUS name, race, kind and the fields a TSDoc comment or an editor would show) be extracted from, and under what licence may they be distributed with `reforged-types`, `reforged-ts` or a new package.

The game files were inspected read-only on Build 3.0.0.24268, the Build `reforged-types` supports, on 2026-10-05. Nothing here is legal advice. It reads the licence texts and the practice of comparable projects so that the map can pick a risk level on purpose.

## Answer

**Sources, ranked:**

1. **The Patch's own files, read from a local install.** Object data is plain SLK and INI-like `.txt` files in the CASC storage under `War3.w3mod:Units/`, `War3.w3mod:Doodads/` and `War3.w3mod:_Locales/enUS.w3mod:`. Warcraft III's CASC root file is a plain-text list of `path|content key|locale|`, so a small reader can list every file and extract it. The source is exact for the installed Build. It needs a machine with the game (34 GB here), but no login and no running game.
2. **The same files from Blizzard's public CDN.** The CDN is anonymous HTTP and works headless, on Linux CI as well. On 2026-10-05 the `w3` product's live version was 3.0.0.24268, with the same build config and content keys as the local install. The CDN serves the live Build without extra work. Older Builds are reachable only while their configs stay on the CDN, by their build config hash. CascLib supports this "online storage" mode, and `casc-cdn` (TypeScript, MIT) supports it partly.
3. **Third-party extracts, for cross-checking only.** WurstStdlib2 (abilities regenerated for 3.0.0.24268 on 2026-09-28; unit ids last touched in 2018), `war3-objectdata-th` (2.0.3.23101), War3Net/War3Api (1.31 to 1.33), w3x2lni (metadata only, at most 1.32.8). None is licensed by Blizzard, and the open-source licence each one carries cannot cover Blizzard's content. All except Wurst's abilities are at least one Patch behind 3.0.0, which grew the item table from 283 to 648 rows.

**Licence position.** No Blizzard text grants a right to redistribute game data or icons:

- The current Blizzard EULA (revised 2024-03-21) licenses the game for "personal and non-commercial entertainment purposes only".
- It forbids copying it or creating "derivative works based on or related to the Platform".
- It claims ownership of "Characters: The names, likenesses ..." and "All data ... generated by, or occurring through, the Platform".
- The World Editor licence shipped inside the game today (`UI/WorldEditLicense.txt`) says the same in its 2002 wording.

What separates the options is how exposed each one is, not whether it is allowed:

- **Rawcodes** are four-character identifiers that code must name in order to work at all, the same interoperability ground on which every project ships the Natives' Typings.
- **Short names** are weakly protected by copyright (US law excludes words and short phrases), but Blizzard claims them by contract.
- **Tooltip prose and icon art** are plainly copyrighted expression.

**Safe distribution options, safest first:**

1. **Generate on the user's machine** from the user's own install, with a CLI or editor tooling that reads CASC. Nothing of Blizzard's is shipped, and the output always matches the user's Patch. The Map project commits the generated file if its CI has no game.
2. **Ship derived identifiers only**: Rawcode, kind, race and an identifier made from the enUS name, with no prose, no numbers and no icons. This is what WurstStdlib2 (Apache-2.0) and `war3-objectdata-th` (MIT) do. It is common practice, and no takedown of it was found, but the risk is not zero. The raw SLKs stay out of git: provenance pins them by CASC content key and sha256 instead of a vendored copy.
3. **Never ship** tooltip prose (`Tip`, `Ubertip`) or icons. An editor or hover tool shows them by reading the user's install at run time. Icon _paths_ are strings and may ship as derived data.

Shipping the full Object data (every field, tooltips included, as `war3-objectdata-th`'s JSON does) or vendoring the raw files (as w3x2lni, War3Net and `war3-objectdata` do) is common in the community. It is still the most exposed option, and this project already refuses the analogous jassdoc prose for want of a licence (`packages/reforged-types/AGENTS.md`, curation rules).

## Where the Built-in objects live in a Patch

### The storage layout (Build 3.0.0.24268)

The install keeps its data in CASC. `.build.info` names the Build (`3.0.0.24268`), the build config `3a9d8f26806936764d2d9ad526a65e04` and the installed text locales (`enUS`, `ptBR` on this machine). The suffix of the jass-history tag the repository vendors from, `Reforged-v3.0.0.24268-w3-3a9d8f2`, is the first seven characters of that build config hash.

The root file is plain text, one `path|content key|locale|` line per file, 174,908 lines. CascLib's source notes that Warcraft III storages reference a file from both an "index" and a "vfs-root" ([CascOpenStorage.cpp L862](https://github.com/ladislav-zezula/CascLib/blob/38a34665624b8775bb875274b36191b21c38d97b/src/CascOpenStorage.cpp#L862)). PyCASC's Warcraft III root parser expects three `|` fields, but 3.0.0 has four, so it needed a one-line fix before it could read this install.

Almost every path sits under `War3.w3mod:`, split into layers:

| Layer                                                        | Files                         | What it holds                                                                                                                                                                                                                                                               |
| ------------------------------------------------------------ | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `War3.w3mod:` (base)                                         | 22,165 outside the `_` layers | Object data (`Units/`, `Doodads/`), scripts (`Scripts/common.j`), SD art                                                                                                                                                                                                    |
| `_Locales/<locale>.w3mod:`                                   | 4,882 to 6,523 per locale     | Names and tooltips (`Units/*Strings.txt`), `UI/WorldEditStrings.txt`, sounds                                                                                                                                                                                                |
| `_Balance/Melee_V0`, `Custom_V0`, `Custom_V1` `.w3mod:`      | 28 to 38 each                 | Older data sets: `UnitData.slk`, `AbilityData.slk`, `ItemData.slk`, `*Func.txt`                                                                                                                                                                                             |
| `_HD.w3mod:`                                                 | 45,518                        | Reforged (HD) models and textures, icons as `.dds`                                                                                                                                                                                                                          |
| `_DE.w3mod:`                                                 | 44,999                        | A third art set, models and icons; warcraft.wiki.gg calls it the "Definitive Edition" icons ([Warcraft III icons](https://warcraft.wiki.gg/wiki/Warcraft_Wiki:Warcraft_III_icons)). It has no object-data SLK besides `Splats/LightningData.slk` and `TerrainArt/Water.slk` |
| `_Tilesets/<x>.w3mod:`, `_Teen.w3mod:`, `_Deprecated.w3mod:` | small                         | Tileset, teen-mode and retired overrides                                                                                                                                                                                                                                    |

What changed for Reforged, compared with the pre-1.31 MPQs (`war3.mpq`, `war3x.mpq`, `war3patch.mpq`, `war3xlocal.mpq`): the files are the same SLK and `.txt` formats under the same relative paths, but they are now layered as above. Locale strings moved out of the base into `_Locales/enUS.w3mod:` and art into `_HD`/`_DE`. HiveWE's file lookup shows the order a tool must resolve a path in: overrides, then imports, then for CASC `_hd` with tileset, locale and teen, then SD tileset, locale and teen, then base, then `_deprecated` ([hierarchy.ixx L84-L196](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/base/hierarchy.ixx#L84-L196)). HiveWE reads `_balance` and `_de` from neither path.

The `_HD` and `_DE` layers hold no object data. A generator for Built-in objects needs the base layer, the `_Balance` layers and `_Locales/enUS.w3mod:`.

### Data sets: a Patch has more than one set of Built-in objects

The base layer and the `_Balance` layers disagree:

- `UnitData.slk` has 928 rows in the base, 864 in `_Balance/Custom_V1` and 837 in `_Balance/Melee_V0`.
- The 64 units only in the base are mostly new content of `version` 2, the value the column takes for 3.0.0 content beside 0 and 1 (e.g. `Sswm` Sally Whitemane, `sfoo` Scarlet Crusade Footman, `Uput` Putress).
- `UnitBalance.slk` differs on 461 of 928 rows between base and `Custom_V1`.

Which set a map gets is a property of the map (its game data set), not of the Patch. Hence "the Built-in objects of a Patch" has to name its data set. The base layer is the newest set and the natural default.

Strings paths are under `_Locales/enUS.w3mod:`, the others under `War3.w3mod:`. Every column the World Editor's Object Editor shows has a row in a `*MetaData.slk`: its four-character field id, its SLK or profile column and its display name as a `WESTRING_*` key. For example `unam` is the `Name` field in the `Profile`, shown as `WESTRING_UEVAL_UNAM`, and `UI/WorldEditStrings.txt` resolves that key to "Name". These are the same files Wurst's ability generator and War3Api's generator read ([War3Api PathConstants.cs](https://github.com/Drake53/War3Api/blob/d53c6d4931adb5214370bb080cdcb6ed38ba753c/src/War3Api.Generator.Object/PathConstants.cs)).

The Footman, for example, is spread over four files:

- `UnitData.slk`: `unitID` `hfoo`, `race` `human`, `comment(s)` `Footman`.
- `HumanUnitFunc.txt`: `[hfoo] Buttonpos=0,0`.
- `UnitSkin.txt`: `[hfoo] Art=ReplaceableTextures\CommandButtons\BTNFootman.blp`.
- `_Locales/enUS.w3mod:Units/HumanUnitStrings.txt`: `[hfoo] Name=Footman`, `Tip=Train Footman`, `Ubertip="Versatile foot soldier. ..."`.

The `comment(s)` column is an internal English label, sometimes different from the enUS name: `Uarf` is "undead arthas w/ frostmourne". The player-facing name always comes from `*Strings.txt`.

Two more facts matter to the other tickets:

- **Rawcodes are unique across the seven kinds.** On 3.0.0.24268 no Rawcode appears in two kinds' tables, and none twice in one, so a literal `FourCC("hfoo")` resolves to exactly one Built-in object and kind. Upgrades all start with `R`, abilities mostly with `A` and buffs mostly with `B`. Units, items, destructables and doodads share first letters, so the kind cannot be guessed from the code alone. This was measured on Built-in objects only; it says nothing about Custom objects.
- **Patch 3.0.0 grew the tables.** `war3-objectdata` committed the files of 2.0.3.23101 ([commit 743df24](https://github.com/cipherxof/war3-objectdata/commit/743df24200)). Its `itemdata.slk` has 283 rows and 30 columns. The 3.0.0.24268 one has 648 rows and five more columns: `invulnerable`, `equipment`, `tag`, `teamColor`, `customTeamColor`. About 330 new items have Rawcodes beginning with `e`, equipment such as `ecgh` Guardsman Helmet. Built-in objects are per-Patch data, and a set taken from a third party goes stale.

### Icons

The icon an editor shows is the profile's `Art=` path, e.g. `ReplaceableTextures\CommandButtons\BTNFootman.blp`. The storage no longer holds most of those `.blp` files:

- The base layer's `ReplaceableTextures/CommandButtons/` has 324 `.blp` and 1,215 `.dds` files.
- `_HD` has 1,503 `.dds` files and `_DE` has 1,612.
- `BTNFootman` exists only as `BTNFootman.dds`, in the base, `_HD` and `_DE` layers.

The game resolves the `.blp` path to whichever texture the active art mode provides, and HiveWE likewise passes alternative extensions to its lookup ([hierarchy.ixx L90-L94](https://github.com/stijnherfst/HiveWE/blob/cbfd6b32d4dcaa5583c9f360d59617cb12531d10/src/base/hierarchy.ixx#L90-L94)). Icons can be extracted exactly like the SLKs. Showing one means decoding DDS (BC-compressed) and BLP. `mdx-m3-viewer` (MIT) has decoders for both. Icons are artwork, the clearest case of copyrighted content (see Licence).

### Verifying the vendored `common.j` against the install

`War3.w3mod:Scripts/common.j` from the install, with CRLF turned into LF, has sha256 `7561e8be...f8fbb`. That is exactly the hash `vendor/3.0.0.24268/provenance.json` records for the jass-history copy. jass-history is a faithful copy of the game file with LF line endings, and a provenance record could name the CASC content key next to the sha256.

The common pattern: tools that _edit_ maps read the user's install (HiveWE, w3x2lni). Libraries that _generate code_ run the generator on a maintainer's machine and ship the output: Wurst and War3Api.Object ship derived identifiers or code, `war3-objectdata-th` ships full data. Two repositories put raw Blizzard files in git under their own licence: w3x2lni (GPL-3.0) and War3Net and `war3-objectdata` (MIT). Those licences cannot cover the files.

It governs maps, not a code generator, but it applies to whatever a Map project builds with the library.

**Blizzard Legal FAQ** ([blizzard.com/legal](https://www.blizzard.com/en-us/legal/c1ae32ac-7ff9-4ac3-a03b-fc04b8697010/blizzard-legal-faq)): it allows fan sites to "use and display, for home, noncommercial and personal use only, one copy" of material downloaded from Blizzard's site, keeping notices and without the right to "sublicense, assign or otherwise transfer". It is the closest thing to a fan policy. It covers neither extracted game files nor redistribution in a package.

None of these texts permits shipping extracted game data or icons, or a tool built for that.

### Copyright versus contract

- **Facts and identifiers.** Copyright protects expression, not facts (_Feist Publications v. Rural Telephone Service_, [499 U.S. 340](https://supreme.justia.com/cases/federal/us/499/340/) (1991)). The US Copyright Office does not register "words and short phrases such as names, titles, and slogans" ([37 CFR 202.1(a)](https://www.ecfr.gov/current/title-37/chapter-II/subchapter-A/part-202/section-202.1)). Rawcodes, races, kinds and numbers are facts. "Footman" or "Archmage" alone are short names. The EU, however, adds a sui generis right in databases (Directive 96/9/EC) against extracting a _substantial part_ of a database, so a full table copied wholesale is more exposed there than a list of identifiers.
- **Expression.** `Tip`/`Ubertip` tooltips and the icon artwork are original expression, and Blizzard's DMCA notices on GitHub target exactly this kind of content: StarCraft assets in an HTML5 remake ([2015](https://github.com/github/dmca/blob/master/2015/2015-10-02-Blizzard.md)), extracted Warcraft race art ([2022](https://github.com/github/dmca/blob/master/2022/05/2022-05-24-blizzard.md)), game copies, server emulators and bots. A search of `github/dmca` found no notice against Warcraft III Object data or against any project in the table above.
- **Contract.** Whoever extracts the data has accepted the EULA, whose 1.C and 2 forbid copies and "any work based on the Platform" whether or not copyright reaches the item. The contract binds the person who extracts, not a downstream user who never extracted anything. Hence generating on the user's machine moves the act onto each user's own licensed install. Shipping a generated list makes the project's maintainer the one who copied.
- **The repository's precedent.** `vendor/<Build>/common.j`, `blizzard.j` and `common.ai` are Blizzard files committed in git, from jass-history, which has no licence. The npm package of `reforged-types` excludes `vendor/` (`files` in `package.json`) and ships only declarations generated from them. Those declarations are the interface map scripts must call, an interoperability case every comparable project ships (War3Api, w3ts's typings). Built-in objects' names and tooltips are game _content_, not interface, so the same argument covers Rawcodes but not tooltips or icons. The repository already refuses jassdoc's prose because it has no licence (`packages/reforged-types/AGENTS.md`, `CONTRIBUTING.md`), and Blizzard's tooltip prose would be the same case.

No trademark notice exists in the repository today (no "not affiliated with Blizzard" line in any README or LICENSE). Any package that names Built-in objects should add one.
