Wurst's object-data code is changing fast: the fixes and features cited here are from March to September 2026. A claim about behaviour holds at these commits, not necessarily later.

## Answer

**What to copy**

1. **Mark generated objects; never guess which ones you own.** Every Custom object Wurst creates from code carries an extra field, `wurs` = 42. Each build first deletes every Custom object so marked, then runs the code that creates them again. Objects without the mark, the World Editor's, are kept. Generation is idempotent, and an object deleted from code leaves the map on the next build ([§2](#2-where-generated-object-data-goes)).
2. **Never write the map the World Editor owns.** The build writes into a copy under `_build/`. The World Editor's map is only read, and each build starts from the source map's Object data, not from the previous build's output. Starting from the previous output made objects and fields pile up, fixed in September 2026 ([§2](#2-where-generated-object-data-goes)).
3. **Gate every write on a round trip.** The VS Code object editor serialises, parses the bytes back, compares object and field counts, and refuses to save on a mismatch. The compiler keeps each file's format version as it found it ([§2](#2-where-generated-object-data-goes), [§4](#4-what-the-vs-code-extension-offers)).
4. **Two layers of object-editing API.** Raw natives take a file type, Rawcodes and four-character field ids (`createObjectDefinition("w3u", newId, baseId)`, `def.setString("unam", name)`). On top sit typed wrappers per base object, generated from the game's metadata SLKs (`new AbilityDefinitionFireBolt(id)..setDamage(1, 200)`). A Map project author never has to look up field ids ([§1](#1-compile-time-object-editing)).
5. **Object data to code.** `-exportobjects` turns a map's Object data into Wurst source that recreates it, a way to move World Editor objects into code ([§2](#2-where-generated-object-data-goes)).
6. **Built-in object data extracted from the installed game, checked in, refreshed per Patch.** A Node script reads the game's CASC storage and writes a JSON knowledge base of every Built-in object and field schema. It was last refreshed from Build 3.0.0.24268, the Patch reforged-ts targets. The compiler and the VS Code editor both read that one file ([§5](#5-built-in-object-data)).
7. **An external editor as a VS Code custom editor.** wurst4vscode opens `war3map.w3u/.w3t/.w3a/.w3b/.w3d/.w3h/.w3q` in a webview editor with undo, backup, Rawcode resolution, icons, base values and a Rawcode generator. It works on the files of a folder-mode map. This is the "web technology on the Node toolchain" kind of external editor the map's notes prefer, and it exists and is maintained ([§4](#4-what-the-vs-code-extension-offers)).

**What to avoid**

1. **Rawcodes are plain `int`.** The lexer reads `'hfoo'` as an integer literal. The stdlib constants (`UnitIds.footman`) are untyped `static constant`s. `UnitDefinition(int, int)` and `createUnit(player, int)` take any integer. Nothing stops an item's Rawcode where a unit's is expected, so Wurst offers no design for distinct Rawcode types (#463) ([§3](#3-how-rawcodes-look-in-code)).
2. **Ids generated by a counter in execution order.** `constant MY_UNIT_ID = compiletime(UNIT_ID_GEN.next())` counts up from `'x000'`, and nothing records which object got which id. Adding or moving an object shifts the ids of the objects created after it. The manual leaves the execution order unspecified between packages that import each other ([§1](#1-compile-time-object-editing)).
3. **A code-made object with a World Editor object's Rawcode silently replaces it.** Only a Rawcode made twice in code is an error. Clashes are avoided only by prefixes (`x`, `HM`, `AM`, `BM`, `IM`, `RM`), and a test asserts the replacement as intended ([§1](#1-compile-time-object-editing)).
4. **Generated objects never reach the World Editor.** They exist only in the build output, so the World Editor cannot place a generated unit type or show it in its Object Editor. The manual still describes an "import the generated file" route, but the code that wrote that file is commented out ([§2](#2-where-generated-object-data-goes)).
5. **Lossy write-back.** The compiler merges `war3mapSkin.*` into `war3map.*` and deletes the skin file from the output. It also replaces every `TRIGSTR_` reference with the inline string from `war3map.wts` ([§2](#2-where-generated-object-data-goes)).
6. **No Rawcode tooling in code.** The language server's hover on any integer literal, `'hfoo'` included, says "integer constant". It offers no go to definition and no completion for Rawcodes. The extension's only hover in source code previews image paths. Rawcodes are resolved to names and icons only inside the binary-file viewers ([§4](#4-what-the-vs-code-extension-offers)).
7. **Neither object-data library can be reused.** The compiler uses the Java library `inwc3/wc3libs`. The extension's parser and serialiser (`parseObjMod`/`serializeObjMod`) live in `casc-ts`, which its own AGENTS.md calls a private sibling package; public CI builds against a mock whose parsers throw ([§2](#2-where-generated-object-data-goes), [§4](#4-what-the-vs-code-extension-offers)).
8. **One Built-in snapshot, no enUS object names.** The knowledge base holds the latest Patch only; older Patches live on stdlib branches (`pre1.24`, `pre1.29`). Its unit, item and ability records hold SLK fields and editor comments (`comment(s)`: "Footman") but no `Name` from the game's string files. The stdlib's `UnitIds` constants were written by hand in 2018 and have not changed since ([§5](#5-built-in-object-data)).

## 1. Compile-time object editing

**Running code at compile time.** Wurst has an interpreter. A function annotated `@compiletime` runs during the build, and `compiletime(expr)` evaluates an expression during the build and puts the result into the map script. The constant `compiletime` tells the two worlds apart ([SITE `_doc/manual.md` L2244–L2308](https://github.com/wurstscript/wurstscript.github.io/blob/e77547848fdd1e4b26cab416e38f8338bf2f2772/_doc/manual.md#L2244-L2308)). Execution order: "from top to bottom inside a package. Imported packages are executed before the importing package if the import-relation is one directional. Otherwise the execution order is not specified" ([L2336–L2340](https://github.com/wurstscript/wurstscript.github.io/blob/e77547848fdd1e4b26cab416e38f8338bf2f2772/_doc/manual.md#L2336-L2340)).

**The natives.** `ObjEditingNatives` declares `@compiletimenative` functions with dummy bodies. `createObjectDefinition(string fileType, int newId, int deriveFrom)` returns an `ObjectDefinition` handle, and `setInt`, `setString`, `setReal`, `setUnreal` and their `Lvl` and `LvlData` variants take a four-character field id, a level and a data pointer ([STD `wurst/objediting/ObjEditingNatives.wurst` L19–L64](https://github.com/wurstscript/WurstStdlib2/blob/110252dd8b19fe683505bfbbbd6b6a1f9f4dfd9e/wurst/objediting/ObjEditingNatives.wurst#L19-L64)). The compiler implements them in `CompiletimeNatives` on top of wc3libs' `ObjMod` ([WS `CompiletimeNatives.java` L53–L178](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstio/intermediateLang/interpreter/CompiletimeNatives.java#L53-L178)):

- `newId != baseId` creates a Custom object. The compiler first removes any object with that id from the store, then adds the new one and marks it with the field `wurs` = 42 ([L53–L86](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstio/intermediateLang/interpreter/CompiletimeNatives.java#L53-L86)).
- `newId == baseId` edits the Built-in object in place, "melee override", added in March 2026 ([WurstScript#1157](https://github.com/wurstscript/WurstScript/pull/1157)). It reuses the entry the map already has for that Built-in object, if any, and adds no mark.
- A field write replaces every earlier value of the same field, level and data pointer, and keeps the object's other fields ([L160–L178](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstio/intermediateLang/interpreter/CompiletimeNatives.java#L160-L178)). When code overrides a Built-in object the World Editor also edited, the two merge field by field and the code wins on each field it sets.

**The wrappers.** One class per object kind and per base ability: `W3UDefinition(int newId, int baseId)` with `setName`, `setHotkey` and so on ([STD `UnitObjEditing.wurst` L9–L48](https://github.com/wurstscript/WurstStdlib2/blob/110252dd8b19fe683505bfbbbd6b6a1f9f4dfd9e/wurst/objediting/UnitObjEditing.wurst#L9-L48)), and `AbilityObjEditing.wurst`, 44,905 lines generated from `abilitydata.slk`, `abilitymetadata.slk` and `WorldEditStrings.txt` by `HelperScripts/GenAbilities.java` ([WS `HelperScripts/GAMEDATA.md`](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/HelperScripts/GAMEDATA.md)). Multi-level fields get `setX(level, value)` and `presetX(lvl -> value)`. The manual's example ([SITE `manual.md` L2364–L2386](https://github.com/wurstscript/wurstscript.github.io/blob/e77547848fdd1e4b26cab416e38f8338bf2f2772/_doc/manual.md#L2364-L2386)):

```wurst
@compiletime function myThunderBolt()
	new AbilityDefinitionMountainKingThunderBolt("A005")
	..setName("Wurst Bolt")
	..presetDamage(lvl -> 400. + lvl * 100)
```

**Ids for new objects.** `ObjectIdGenerator` holds one counter per kind: units from `'x000'`, heroes `'HM00'`, abilities `'AM00'` (`@configurable`), buffs `'BM00'`, items `'IM00'`, upgrades `'RM00'`. `next()` counts the last characters up through `0-9`, `a-z` and a few symbols ([STD `presets/ObjectIdGenerator.wurst` L7–L58](https://github.com/wurstscript/WurstStdlib2/blob/110252dd8b19fe683505bfbbbd6b6a1f9f4dfd9e/wurst/objediting/presets/ObjectIdGenerator.wurst#L7-L58)). The documented pattern ([SITE `_news/bestofthewurst3.md` L83–L93](https://github.com/wurstscript/wurstscript.github.io/blob/e77547848fdd1e4b26cab416e38f8338bf2f2772/_news/bestofthewurst3.md#L83-L93)):

```wurst
constant MY_UNIT_ID = compiletime(UNIT_ID_GEN.next())
@compiletime function createUnit()
    new UnitDefinition(MY_UNIT_ID, 'ewsp')
```

The blog calls these "safe IDs inside a range that isn't used by standard units". Stability across builds rests only on the code running in the same order. No id is persisted, so inserting a `next()` call before another changes that other object's Rawcode, and with it any saved reference to it.

**Clashes with the World Editor's ids.** The prefixes are the only guard. The compiler reports a Rawcode created twice in code ("Object definition with id … is defined more than once"). A Rawcode that matches an existing World Editor Custom object is not reported; that object is replaced. The test `differentIdsObjectDefinitionOverwritesExistingMapObject` asserts the replacement, and `createObjectDefinitionDoesNotReportExistingMapObjectAsError` asserts that no error is raised ([WS `CompiletimeNativesTest.java` L131–L194](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/test/java/tests/wurstscript/tests/CompiletimeNativesTest.java#L131-L194)).

## 2. Where generated Object data goes

**Into the map's `war3map.w3*`, merged with the World Editor's, in a copy of the map.** For each object file type, `ProgramStateIO.getDataStore` reads `war3map.<ext>` and `war3mapSkin.<ext>` from the map, merges the skin into the main file, resolves `TRIGSTR_` strings from `war3map.wts` and deletes every object marked `wurs` = 42 ([WS `ProgramStateIO.java` L206–L314](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstio/intermediateLang/interpreter/ProgramStateIO.java#L206-L314)). The compile-time code then adds its objects to that store. `writeBack` writes the whole file, World Editor objects and generated ones together, back into the MPQ when `-injectobjects` is set. The VS Code build always sets it, with `-runcompiletimefunctions` ([WS `WurstCommands.java` L122](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstio/languageserver/WurstCommands.java#L122)).

The MPQ written is never the source map. `MapRequest` copies the source map, or packs a folder-mode map, into `_build/cache/`, compiles into that copy, then copies it to the build output and strips Wurst's own cache files from it ([WS `MapRequest.java` L540–L562, L788–L797](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstio/languageserver/requests/MapRequest.java#L540-L562)). When it compiles against the cached copy, it reads the base Object data from the source map ([L162–L165](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstio/languageserver/requests/MapRequest.java#L162-L165)). Before [WurstScript#1311](https://github.com/wurstscript/WurstScript/pull/1311) (2026-09-24) it read from the cache: "Melee overrides … kept their object from the previous run … fields were appended again each run", and "overrides removed from code" stuck around.

**What happens to the World Editor's own edits.** The World Editor never sees generated objects; they exist only in `_build`. Its Custom objects pass through untouched unless code reuses their Rawcode ([§1](#1-compile-time-object-editing)). Its edits to a Built-in object merge field by field with the code's override of the same object. The manual says Wurst writes "object files next to your map" for the Object Editor's import ([SITE `manual.md` L2259–L2264](https://github.com/wurstscript/wurstscript.github.io/blob/e77547848fdd1e4b26cab416e38f8338bf2f2772/_doc/manual.md#L2259-L2264)). The `.w3o` writer that did that is commented out in `writeBack` ([WS `ProgramStateIO.java` L457–L458](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstio/intermediateLang/interpreter/ProgramStateIO.java#L457-L458)). What each build does write next to the map, in `objectEditingOutput/`, is `WurstExportedObjects_<ext>.wurst.txt`: Wurst source that recreates every object in the merged file ([L492–L518](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstio/intermediateLang/interpreter/ProgramStateIO.java#L492-L518)).

**Object data to code.** `-exportobjects <map file or folder>` ([WS `RunArgs.java` L133–L134](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstscript/RunArgs.java#L133-L134)), added in July 2026 ([WurstScript#1200](https://github.com/wurstscript/WurstScript/pull/1200)), writes the same `.wurst` files from any map ([WS `ObjectExportService.java`](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstio/objectreader/ObjectExportService.java)). The exporter emits the high-level wrapper class when `stdlib-obj-mappings.json` knows the base object, with a `// TODO no wrapper:` raw call for each unmapped field. Otherwise it falls back to raw `createObjectDefinition` and setters, "so no object data is lost on re-export" ([WS `ProgramStateIO.java` L563–L688](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstio/intermediateLang/interpreter/ProgramStateIO.java#L563-L688)). It picks the hero wrapper when the new Rawcode starts with an upper-case letter ([L629–L632](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstio/intermediateLang/interpreter/ProgramStateIO.java#L629-L632)).

**The library and its round-trip fidelity.** Reading and writing go through `com.github.inwc3:wc3libs`, pinned to commit `0542c41400` from JitPack, with `inwc3:JMPQ3` for the MPQ ([WS `build.gradle` L158–L159](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/build.gradle#L158-L159)). What the code does about fidelity:

- It writes each file `AS_DEFINED`, in the format version it was read with. [WurstScript#1317](https://github.com/wurstscript/WurstScript/pull/1317) (2026-09-27) extended that to hashing and the `.w3o` export for "Reforged 3".
- It merges `war3mapSkin.<ext>` into the main file and deletes the skin file from the output map ([`ProgramStateIO.java` L222–L231](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstio/intermediateLang/interpreter/ProgramStateIO.java#L222-L231)).
- It replaces `TRIGSTR_n` values with their text from `war3map.wts` before writing ([L278–L300](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstio/intermediateLang/interpreter/ProgramStateIO.java#L278-L300)).
- If an object file in the map cannot be read, it keeps that file unchanged and makes it a compile error to add generated objects of that type, because writing the store "would replace the map's objects of this type with only the generated ones" ([L404–L412](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstio/intermediateLang/interpreter/ProgramStateIO.java#L404-L412)).
- It skips rewriting a file whose hash matches both a manifest (`wurst_object_cache.txt`, inside the MPQ) and the MPQ's current content ([L390–L471](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstio/intermediateLang/interpreter/ProgramStateIO.java#L390-L471)).

The commit history of `ProgramStateIO.java` reads as a run of fidelity fixes: "fix writing empty objmod files" and "ugly fix for skin files" (2022), "Fix objmod output" and "More objediting fixes" (June 2026), then #1311 and #1317 (September 2026). Wurst has the problem ADR 0006 records for `war3-transformer`, and is still fixing it.

## 3. How Rawcodes look in code

- **Literal.** `'hfoo'` is a character literal that the lexer folds into the `INT` token: `INT: [0-9]+ | HexInt | CharInt` ([WS `Wurst.g4` L624–L627](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/antlr/de/peeeq/wurstscript/antlr/Wurst.g4#L624-L627)). Its type is `int`.
- **Constants.** `UnitIds`, `AbilityIds`, `ItemIds`, `BuffIds` are classes of `static constant`s with no declared type, so they infer `int`: `static constant footman = 'hfoo' // model: Footman` ([STD `_wurst/assets/UnitIds.wurst` L288](https://github.com/wurstscript/WurstStdlib2/blob/110252dd8b19fe683505bfbbbd6b6a1f9f4dfd9e/wurst/_wurst/assets/UnitIds.wurst#L288)), `static constant blizzard = 'AHbz'` ([`AbilityIds.wurst` L86](https://github.com/wurstscript/WurstStdlib2/blob/110252dd8b19fe683505bfbbbd6b6a1f9f4dfd9e/wurst/_wurst/assets/AbilityIds.wurst#L86)). The names are lower-case or camelCase English, and the only documentation is a trailing line comment; hover shows only a leading `/** */` comment ([WS `AttrWurstDoc.java` L8–L47](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstscript/attributes/AttrWurstDoc.java#L8-L47)). `UnitIds.wurst` was last changed in 2018. `AbilityIds.wurst` is merged with generated additions on each game-data refresh ([WurstStdlib2#491](https://github.com/wurstscript/WurstStdlib2/pull/491)).
- **Parameters.** Every Rawcode parameter is `int`: `createUnit(player p, int unitId)` ([STD `_handles/Unit.wurst` L47](https://github.com/wurstscript/WurstStdlib2/blob/110252dd8b19fe683505bfbbbd6b6a1f9f4dfd9e/wurst/_handles/Unit.wurst#L47)), `W3UDefinition(int newId, int baseId)`. `ObjectIds` converts at run time: `int.toRawCode()` and `string.fromRawCode()` ([STD `ObjectIds.wurst` L10–L40](https://github.com/wurstscript/WurstStdlib2/blob/110252dd8b19fe683505bfbbbd6b6a1f9f4dfd9e/wurst/objediting/ObjectIds.wurst#L10-L40)).
- **No generated constants for Custom objects.** Wurst generates no package of constants for a map's Object data. A code-made object's Rawcode is whatever constant the author declared, usually from `compiletime(UNIT_ID_GEN.next())`. A World Editor object is reached by its literal.

## 4. What the VS Code extension offers

**From the language server (WurstScript).** Hover on any integer literal returns the text "integer constant" ([WS `HoverInfo.java` L372–L374](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstio/languageserver/requests/HoverInfo.java#L372-L374)). Semantic tokens colour it as a number. Hover on a constant such as `UnitIds.footman` describes the variable like any other. The language server has no Rawcode-aware hover, definition, completion or diagnostic: nothing under `languageserver/` reads Object data or the knowledge base.

**From the extension (wurst4vscode).** The README lists object data under "Warcraft III inside VS Code": "Inspect and edit `.w3u`, `.w3t`, `.w3a`, `.w3b`, `.w3d`, `.w3h`, and `.w3q`", and "Object-data editors resolve rawcodes, game metadata, icons, base values, and trigger strings while keeping custom overrides editable" ([VSC `README.md`](https://github.com/wurstscript/wurst4vscode/blob/65bd213c234dc1fe0ce4b7cb4c9400b9cc22d19e/README.md)). In the code:

## 5. Built-in object data

- **Source:** the installed game, read through CASC. `HelperScripts/extract-wc3-gamedata.mjs` opens `C:/Program Files (x86)/Warcraft III` with `casc-ts` and pulls 51 files: the unit, ability, buff, item, destructable and upgrade data and metadata SLKs, the `*func.txt`/`*skin.txt` profiles, `miscdata.txt` and enUS `WorldEditStrings.txt`. It refuses missing or ambiguous paths ([WS `extract-wc3-gamedata.mjs`](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/HelperScripts/extract-wc3-gamedata.mjs); [`GAMEDATA.md`](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/HelperScripts/GAMEDATA.md)). The list holds no `*strings.txt`, so object display names are not extracted.
- **Output, checked in:** `generate-obj-mappings.ts` (Deno) writes two compiler resources. `wc3-knowledge-base.json` (16.6 MB, `schemaVersion` 1) holds `heroBaseIds`, `buildingBaseIds`, `fieldSchemas` per kind and `objects` per kind: 992 units, 1,910 abilities, 1,941 buffs, 653 items, 349 destructables, 91 upgrades. `stdlib-obj-mappings.json` maps base ids and fields to wrapper classes and setters for the exporter. The Java generator also regenerates the ability wrappers ([WS `src/main/resources/`](https://github.com/wurstscript/WurstScript/tree/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/resources)).
- **Per Patch:** one snapshot, replaced on refresh. [WurstScript#1327](https://github.com/wurstscript/WurstScript/pull/1327) (2026-09-28) "extracted all 51 required inputs from the installed Warcraft III 3.0.0.24268 CASC data". Three days earlier, #1317 had recorded that "the available checked-in game-data inputs predate 3.0, and no CASC extractor was available". `GAMEDATA.md` says old Patch-only ids and classes "are not carried into the Reforged stdlib; their patch-specific branches retain them", and the stdlib has `pre1.24` and `pre1.29` branches.
- **Names:** a unit record carries `comment(s)` ("Footman"), the lower-case SLK `name` ("footman") and `Art`, but no `Name` key. No unit, item or ability record has one ([the knowledge base](https://github.com/wurstscript/WurstScript/blob/405a796f67fe29a3143f7cbcc23efd3dfd0c6dc5/de.peeeq.wurstscript/src/main/resources/wc3-knowledge-base.json), counted at this commit).
- **Consumers:** the compiler packs it into its jar. The VS Code editor reads it from the installed compiler jar, then from a bundled copy synced by `scripts/sync-wc3-knowledge-base.js` ([VSC `preview/compilerKnowledgeBase.ts` L77–L110](https://github.com/wurstscript/wurst4vscode/blob/65bd213c234dc1fe0ce4b7cb4c9400b9cc22d19e/src/features/preview/compilerKnowledgeBase.ts#L77-L110)). It falls back to reading the metadata SLKs from the user's game install through CASC ([VSC `objModPreview.ts` L1340–L1486](https://github.com/wurstscript/wurst4vscode/blob/65bd213c234dc1fe0ce4b7cb4c9400b9cc22d19e/src/features/objModPreview.ts#L1340-L1486)). Labels come from `WorldEditStrings.txt` either way, and icons and models from the game install.

## What this means for the map's tickets

- **#463, distinct Rawcode types:** Wurst has none to copy. Its Rawcodes are `int` from literal to native, and the only per-kind information is which class a constant sits in (`UnitIds`, `ItemIds`). Its knowledge base does record each Built-in object's kind, plus `heroBaseIds` and `buildingBaseIds`, which is what typed constants would need.
- **#467, authoring Object data:** all three ways exist in Wurst's ecosystem today: the World Editor, objects in code, and a VS Code custom editor over the map folder's binary files. Wurst does not reconcile them: code-made objects are invisible to both editors, the extension's Rawcode generator cannot see them, and a shared Rawcode silently goes to the code's object. Objects in code with ownership by marker would fit ADR 0006's optional package, if its writer is correct. Wurst's history shows the writer is where the bugs live. Neither of its libraries is reusable from Node: Java wc3libs, and a private `casc-ts`.
- **#468, hover tooling:** Wurst gives no precedent. A literal Rawcode in code gets "integer constant", and Rawcodes resolve only inside the binary viewers. A Rawcode→name/icon catalogue built from the game install and the map's own `war3map*.w3?` is the part to copy, and it lives in the extension, not the language server. Names need the game's enUS `*strings.txt`, which Wurst's knowledge base does not extract.
- **ADR 0006:** Wurst bears out the ADR's warning. Eleven days before this research, its injected Object data still grew with every build. Any reforged-ts writer of `war3map.w3*` needs Wurst's two guards, a mark on owned objects and a build that reads the source map and writes a copy, plus the extension's round-trip gate.
