# From a Rawcode in code to its object, in any editor

Research for [#462](https://github.com/phmilk/reforged-ts/issues/462), part of the map [#457](https://github.com/phmilk/reforged-ts/issues/457). The question: how a tool takes a developer from a Rawcode in code (a generated constant, a literal `FourCC("hfoo")`) to its object, in any editor where viable and in VS Code at the least, and what the tool needs from the Typings, the library or generated data. Sources are the TypeScript, VS Code and LSP documentation and source code, the docs of other editors, and the code of WurstScript, wurst4vscode and typescript-to-lua; each claim links to the source that owns it. Two throwaway experiments against TypeScript 6.0.2 (the version the Template pins) back the claims marked _verified_; they are described in [Experiments](#experiments). Date: 2026-10-05.

## Answer

| Mechanism                                                                                  | What it gives                                                                                                                                                                                                                                                                                                                            | Where it works                                                                                                                                                                                                                                                                                                                                  | What it needs from generated data                                                                                                                                                      |
| ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Generated declarations, no tool**: constants with TSDoc (#464), or overloads of `FourCC` | Hover on a constant shows its TSDoc; go to definition lands on the generated declaration. Per-Rawcode overloads of `FourCC` also give, on a literal call, the object's TSDoc when hovering `FourCC`, a jump to that overload, and completion of known Rawcodes inside `FourCC("…")` (_verified_). No hover on the string literal itself. | Every editor and every TypeScript, including `tsc` and the TypeScript 7 language server, because it is plain TypeScript.                                                                                                                                                                                                                        | A `.d.ts` (or `.ts`) per Patch for Built-in objects and per Map project for Custom objects, with name, kind and race in the TSDoc.                                                     |
| **TypeScript language service plugin** (a tsserver plugin)                                 | Hover on the literal `"hfoo"` in `FourCC("hfoo")` with any text, and go to definition from the literal to the generated constant (_verified_). The hover may carry `http(s):` and `file:` links; VS Code blocks `command:` links from tsserver.                                                                                          | Wherever the JavaScript tsserver of TypeScript ≤ 6 runs: VS Code (workspace TypeScript, or any TypeScript when a VS Code extension contributes the plugin), Neovim (`ts_ls`, `vtsls`), Zed (`vtsls`), other `typescript-language-server` clients; WebStorm loads tsconfig plugins. Not `tsc`, not ESLint, not the TypeScript 7 language server. | A machine-readable index (JSON) from Rawcode to name, kind, race, origin (Built-in object or Custom object) and the generated constant's name; the plugin re-reads it when it changes. |
| **Language server** of its own (LSP)                                                       | Hover, `textDocument/documentLink` (a click target on the literal) and `window/showDocument` with `external: true` (open a browser page), independent of the TypeScript version.                                                                                                                                                         | Any LSP client that runs a second server next to the TypeScript one (Neovim 0.12 follows document links with `gx`); a separate binary and per-editor setup.                                                                                                                                                                                     | The same JSON index.                                                                                                                                                                   |
| **VS Code extension**                                                                      | Its own `HoverProvider` with trusted Markdown and `command:` links, a `DocumentLinkProvider` whose target is a `command:` URI, a `CustomEditor` or `Webview` for the object, and the tsserver plugin contributed without editing `tsconfig.json`.                                                                                        | VS Code (and its forks through Open VSX). Its own hover and links keep working under the TypeScript 7 language server; the contributed tsserver plugin does not.                                                                                                                                                                                | The same JSON index, plus the map folder's Object data files if it hosts an external editor.                                                                                           |

- **Click to open the object**: editor-agnostic only as an `http://localhost` link (in a tsserver plugin's hover or an LSP document link) to a page a Node process serves, or as go to definition into a generated file. Opening a VS Code custom editor on the object is VS Code only: a `command:` document link or extension hover runs a command that calls `vscode.openWith` on `war3map.w3u` and posts the Rawcode to the webview, which is what wurst4vscode does for cross-references inside its object editor.
- **Hosting an external editor**: one web UI can be hosted both ways: in a VS Code `CustomEditorProvider` over the map folder's `war3map.w3u/.w3t/.w3a/.w3b/.w3d/.w3h/.w3q` (wurst4vscode ships exactly that, editable), or as a local page served by Node that any editor's `http://` link reaches. Either one that saves Object data writes `war3map.w3*`, which ADR 0006 reserves for an optional package.
- **Data**: Built-in objects come once per Patch (enUS names), Custom objects per Map project from the map folder's Object data and `war3map.wts` (names are often `TRIGSTR_` references). The Template already has the pattern: `scripts/editor-globals.ts` regenerates `src/generated/editor-globals.d.ts` from the map folder on every install, build and `pnpm dev` watch, and `mdx-m3-viewer-th`, already a devDependency, parses `w3u`/`w3d`/`wts`. Generation should emit both a `.d.ts` (for TypeScript) and a JSON index (for a plugin, server, extension or external editor) from one model. tsserver picks up a changed `.d.ts` by itself; a plugin reading JSON must watch it.
- **The TypeScript 7 caveat**: TypeScript 7.0 (GA 2026-07-08) has no programmatic API and its language server loads no tsserver plugins; 7.1 is to ship "a new (and different) API". The Toolchain stays on TypeScript 6 for now because typescript-to-lua 1.37.1 pins its peer dependency to `typescript` 6.0.2, so a tsserver plugin works in Map projects today, but a developer who turns on VS Code's TypeScript 7 extension loses it. Keep the plugin a thin adapter over a shared lookup module, so the same lookup can move into a language server or a VS Code `HoverProvider`.
- **Suggested layering**: (1) the generated data, which everything needs; (2) TSDoc on generated constants as the floor that works everywhere; (3) a tsserver plugin for hover on literals, enabled in the Template's `tsconfig.base.json`; (4) a VS Code extension that contributes the plugin, adds `command:` links and hosts the external editor if authoring picks one. A language server of its own pays off only if TypeScript 7 makes the plugin route unusable outside VS Code.

## 1. Generated declarations, with no tool

TypeScript shows a declaration's TSDoc on hover and jumps to the declaration on go to definition in every editor, so constants generated with TSDoc (#464) give hover on a constant and navigation into the generated file with no plugin at all, under `tsc`, every editor's TypeScript server and TypeScript 7.

A literal `FourCC("hfoo")` gets something too, because `FourCC` is a global function (`declare function FourCC(id: string): number;` in `packages/reforged-types/lua-runtime.d.ts`) and global function declarations merge as overloads across files. A generated `.d.ts` that declares one overload per Rawcode, each with TSDoc, and keeps the `string` overload last, gave in the experiment (_verified_, TypeScript 6.0.2, no plugin):

- hover on `FourCC` in `FourCC("hfoo")`: `function FourCC(id: "hfoo"): UnitRawcode (+2 overloads)` with the overload's TSDoc, `Footman: human unit (Built-in object).`;
- go to definition on `FourCC`: the exact overload's line in the generated file;
- completions inside `FourCC("")`: the generated Rawcodes;
- hover on the literal `"hfoo"` itself: nothing (`No content available.`).

A single generic signature over a lookup interface (`declare function FourCC<K extends keyof RawcodeTable>(id: K): RawcodeTable[K]`) gave the same completions but no TSDoc on hover and a jump to the generic signature only.

Overloads cost check time linearly in their number: 6000 overloads and 2000 calls took 4.25 s of `tsc` check time, 200 calls 0.51 s, against 0.14 s for 2000 calls with one overload (about 2 ms per call at 6000 overloads). Splitting by kind (one function per kind, as #463 might) divides that. Removing the `string` fallback would turn an unknown Rawcode into a type error, the lint rule's job in #369; that only holds once every Custom object is generated too.

## 2. TypeScript language service plugin

### API and enabling

A plugin decorates tsserver's `LanguageService`: its factory receives `create(info: ts.server.PluginCreateInfo)` and returns a proxy that overrides methods such as `getQuickInfoAtPosition` (hover) or `getDefinitionAndBoundSpan` (go to definition); its `tsconfig.json` entry reaches it as `info.config` ([TypeScript wiki](https://github.com/microsoft/TypeScript/wiki/Writing-a-Language-Service-Plugin)). A project enables one with `"compilerOptions": { "plugins": [{ "name": "<npm package>" }] }`, and "This name can only be an NPM package name" (same page).

The wiki is explicit that plugins "aren't loaded during normal commandline typechecking or emitting, (so are not loaded by `tsc`)". So a plugin can never produce a build error; diagnostics it adds appear in the editor only.

The `LanguageService` has no document-link method, so a plugin can offer hover, definition, completions, diagnostics and code fixes, but not a `documentLink`.

### Verified behaviour

The throwaway plugin in [Experiments](#experiments) overrides two methods. Driven over tsserver's stdio protocol, as an editor drives it:

- hover inside `"hfoo"` of `FourCC("hfoo")` returned `"hfoo"` with documentation `Footman (human unit, Built-in object)` and a Markdown link line, spanning exactly the literal; the same worked for a single-quoted `'Hpal'`;
- go to definition inside the literal returned the generated constant `FOOTMAN` in `generated/units.ts`;
- without the plugin, tsserver answers `No content available.` on a string literal, so the plugin owns that hover entirely.

To limit false positives, the plugin should answer only for a literal that is an argument of `FourCC` or, once #463 types Rawcodes, a literal whose contextual type (`checker.getContextualType`) is a Rawcode type; a bare four-character string elsewhere is not necessarily a Rawcode.

### Links inside the hover

VS Code renders tsserver's hover documentation as Markdown with `isTrusted = { enabledCommands: ['_typescript.openJsDocLink'] }` ([`textRendering.ts`](https://github.com/microsoft/vscode/blob/main/extensions/typescript-language-features/src/languageFeatures/util/textRendering.ts)), so a plugin's hover cannot run an arbitrary `command:`; its `{@link}` parts with a target become `_typescript.openJsDocLink` links that open a file at a position. Untrusted Markdown allows `http`, `https`, `mailto`, `file` and a few internal schemes, but not `vscode:` ([`markdownRenderer.ts`](https://github.com/microsoft/vscode/blob/main/src/vs/base/browser/markdownRenderer.ts), `getDomSanitizerConfig`). A plugin's hover can therefore link to `http://localhost:<port>/object/hfoo` or to a `file:` URI, but not into an extension's command.

### Where it loads

- **VS Code, workspace TypeScript**: a tsconfig plugin is found only when VS Code runs the workspace TypeScript ("Use Workspace Version"), or through a path to the module ([TypeScript wiki](https://github.com/microsoft/TypeScript/wiki/Writing-a-Language-Service-Plugin)). The Template's `.vscode/settings.json` already sets `"js/ts.tsdk.path": "./node_modules/typescript/lib"` and `"js/ts.tsdk.promptToUseWorkspaceVersion": true`, so a developer who accepts the prompt gets the plugin; one who declines does not.
- **VS Code, through an extension**: an extension's `contributes.typescriptServerPlugins` loads a plugin "for all JavaScript and TypeScript files when the user is using VS Code's version of TypeScript", and for workspace versions too when it sets `"enableForWorkspaceTypeScriptVersions": true` ([contribution points](https://code.visualstudio.com/api/references/contribution-points#contributes.typescriptServerPlugins)). The extension can pass configuration with the TypeScript extension's `getAPI(0).configurePlugin(pluginId, configuration)` ([`api.ts`](https://github.com/microsoft/vscode/blob/main/extensions/typescript-language-features/src/api.ts)). typescript-to-lua does exactly this: [`vscode-typescript-to-lua`](https://github.com/TypeScriptToLua/vscode-typescript-to-lua/blob/master/package.json) contributes [`typescript-tstl-plugin`](https://github.com/TypeScriptToLua/typescript-tstl-plugin) (TypeScriptToLua diagnostics in the editor) with `enableForWorkspaceTypeScriptVersions: true`; both repositories were last pushed in 2022.
- **pnpm**: tsserver resolves tsconfig plugins from the directory of the TypeScript it runs (`…/typescript/lib/typescript.js/../../..`). VS Code's issue [#232406](https://github.com/microsoft/vscode/issues/232406) (open) reports plugins not found when pnpm resolves TypeScript outside the project folder. In a single-package pnpm repository like the Template, TypeScript sits under the project's own `node_modules/.pnpm/`, and Node's upward resolution from there reaches the project's `node_modules`, so the plugin is found (_verified_: tsserver logged `Loading rawcode-hover-plugin from …/node_modules/.pnpm/typescript@6.0.2/node_modules/typescript/lib/typescript.js/../../..` and the hover worked). The Template's real install has the same layout (`node_modules/typescript` resolves to `node_modules/.pnpm/typescript@6.0.2/node_modules/typescript`).
- **Global plugins**: tsserver's `--globalPlugins <name> --pluginProbeLocations <dir>` load a plugin with no tsconfig entry (_verified_); this is what VS Code passes for contributed plugins, and what `typescript-language-server`'s `plugins` initialization option (`{ name, location }`, [configuration](https://github.com/typescript-language-server/typescript-language-server/blob/master/docs/configuration.md)) and `vtsls.tsserver.globalPlugins` ([vtsls](https://github.com/yioneko/vtsls)) map to.
- **Neovim, Helix, Emacs and others**: through `typescript-language-server` (`ts_ls` in nvim-lspconfig) or `vtsls`, both of which wrap tsserver; a tsconfig plugin loads when they run the workspace TypeScript ([vtsls](https://github.com/yioneko/vtsls): "Ensure the plugin is also specified in `compilerOptions.plugins`", "Switch to workspace version of tsserver … `vtsls.autoUseWorkspaceTsdk`").
- **Zed**: uses vtsls by default ([Zed docs](https://zed.dev/docs/languages/typescript)), so the vtsls rules apply; Zed's page says nothing about plugins.
- **WebStorm**: runs tsserver and loads tsconfig plugins (its tracker has [WEB-67907](https://youtrack.jetbrains.com/issue/WEB-67907/TypeScript-plugins-do-not-work-with-yarn-pnp), "TypeScript plugins do not work with yarn pnp"), but takes much of its hover and navigation from its own engine ([JetBrains blog](https://blog.jetbrains.com/webstorm/2024/01/everything-you-ve-always-wanted-to-know-about-typescript-s-integration-in-webstorm/)); whether a plugin's quick info reaches its Quick Documentation popup is not verified here.
- **ESLint**: the Template's lint uses typescript-eslint's project service, which skips plugins unless `loadTypeScriptPlugins` is set ("We stop loading any TypeScript plugins by default", [`createProjectService.ts`](https://github.com/typescript-eslint/typescript-eslint/blob/main/packages/project-service/src/createProjectService.ts)), so a plugin adds nothing to `pnpm lint`.
- **typescript-to-lua**: reads `compilerOptions.plugins` for its own transformers and skips every entry without a `transform` key ([`transformers.ts`](https://github.com/TypeScriptToLua/TypeScriptToLua/blob/master/src/transpilation/transformers.ts): `if (!("transform" in transformerImport)) continue;`), so a `{ "name": … }` entry does not disturb the build.
- **TypeScript 7**: "TypeScript 7.0 is made … without any programmatic API", tools that embed TypeScript "can only currently rely on TypeScript 6.0", and "We expect TypeScript 7.1 to ship with a new (and different) API" ([announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)). The typescript-go README lists the API as "not ready" ([README](https://github.com/microsoft/typescript-go)), and VS Code now warns when an extension contributes a tsserver plugin while the native preview is on ([typescript-go#3848](https://github.com/microsoft/typescript-go/issues/3848)). Installing the TypeScript 7 VS Code extension makes it "the default experience" (announcement), so a plugin silently stops for that developer.

### How a Map project enables it

The plugin entry belongs in `compilerOptions.plugins` of the Template's `tsconfig.base.json`, which `tsconfig.json` (the map) and `tests/lua/tsconfig.json` extend; `extends` replaces an array rather than merging it, so a Map project adding its own plugin must repeat the entry. The Node side (`tsconfig.scripts.json`) needs none. The plugin package is a devDependency. In VS Code the workspace TypeScript must be chosen (the Template already prompts) unless a VS Code extension contributes the plugin.

## 3. Language server of its own

An LSP server offers, for any client: `textDocument/hover` (Markdown content), `textDocument/definition`, `textDocument/documentLink` with a `target` URI that may be resolved later through `documentLink/resolve`, and since 3.16 `window/showDocument`, whose `external: true` "Indicates to show the resource in an external program", for example "the default WEB browser" ([LSP 3.17](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#window_showDocument), [document link](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#textDocument_documentLink)). Client support varies: Neovim 0.12 added `textDocument/documentLink`, followed by `gx` ([news-0.12](https://neovim.io/doc/user/news-0.12/)).

Such a server runs next to the editor's TypeScript server, so its hover is a second hover on the same position, and each editor needs its own configuration to start it. It needs no TypeScript API (it can find `FourCC("…")` with a tokenizer or the `typescript` parser alone), so it survives TypeScript 7. Neither Wurst nor typescript-to-lua ships one for this purpose; Wurst's server exists because WurstScript is its own language (section 7).

## 4. VS Code extension

What only an extension gets ([VS Code API](https://code.visualstudio.com/api/references/vscode-api)):

- `languages.registerHoverProvider`: its own hover, with a `MarkdownString` whose `isTrusted` (or `{ enabledCommands: [...] }`) enables `command:` links, arguments passed as `encodeURIComponent(JSON.stringify(args))` ([command URIs](https://code.visualstudio.com/api/extension-guides/command#command-uris)). It does not depend on tsserver, so it keeps working with the TypeScript 7 language server.
- `languages.registerDocumentLinkProvider`: an underlined, Ctrl+click target on the literal, whose `target` may be a `command:` URI. wurst4vscode does this for asset paths in code ([`assetLinks.ts`](https://github.com/wurstscript/wurst4vscode/blob/master/src/features/assetLinks.ts): ``link.target = vscode.Uri.parse(`command:wurst.openAssetFromString?…`)``).
- `contributes.customEditors` with `registerCustomEditorProvider`: a webview editor "used in place of VS Code's standard text editor" for files matching a `filenamePattern`; `CustomEditorProvider` is the binary-file variant where "your extension brings its own document model" and implements save and backup, `CustomReadonlyEditorProvider` the read-only one ([custom editors guide](https://code.visualstudio.com/api/extension-guides/custom-editors)).
- `contributes.typescriptServerPlugins`: the tsserver plugin of section 2 without editing `tsconfig.json`.
- `env.openExternal`: open an `http://localhost` page in the browser.

Its cost: VS Code only (Open VSX for VSCodium and other forks), and a release cycle next to the four packages, which the map lists as not yet specified.

## 5. Click to open the object, and hosting an external editor

| Click path                                                                                  | Reaches                                                 | Editors                                                                       |
| ------------------------------------------------------------------------------------------- | ------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Go to definition (generated constant or overload; a plugin redirecting from a literal)      | The generated declaration in a `.d.ts`/`.ts` file       | All (the plugin redirect: wherever the plugin loads)                          |
| `http://localhost:<port>/object/<rawcode>` link in a tsserver plugin's hover or an LSP link | A page served by a Node process                         | All that render Markdown links in hovers or follow document links             |
| `file:` link in a tsserver plugin's hover                                                   | A file, opened by VS Code's opener                      | VS Code; other editors vary. Not verified whether it honours a custom editor. |
| Extension `command:` link (its hover or document link) → `vscode.openWith(uri, viewType)`   | A VS Code custom editor on `war3map.w3u`, at the object | VS Code only                                                                  |

Selecting one object inside a custom editor is the extension's own protocol: wurst4vscode's object editor jumps to a cross-referenced object by calling `vscode.commands.executeCommand('vscode.openWith', found.uri, 'wurst.objModPreview')` and, when the panel is already open, `panelWebview.postMessage({ type: 'selectObject', key })`, otherwise storing a pending selection the panel applies when it opens ([`objModPreview.ts`](https://github.com/wurstscript/wurst4vscode/blob/master/src/features/objModPreview.ts), `openObjectReference`). A link from code would call the same command with the Rawcode.

Hosting one web UI both ways is feasible: the UI is a static web app; a VS Code `CustomEditorProvider` loads its assets through `webview.asWebviewUri` and talks to it with `postMessage`/`onDidReceiveMessage`; a Node process (the Map project's `pnpm` script) serves the same app on localhost and reads or writes the map folder directly. The local page needs the process running and a known port, so the generated data or the plugin's config must carry the port; a link to a stopped server is dead. Either host that saves Object data writes `war3map.w3*`, the boundary ADR 0006 draws (the World Editor owns Object data; compile-time object editing waits for an optional package with a correct object-data library). A read-only view crosses no boundary.

## 6. Data the tools read and keeping it current

**What each Rawcode needs**: name (enUS for a Built-in object; whatever the map's Object data holds for a Custom object, resolving `TRIGSTR_` references through `war3map.wts`), kind (unit, hero, building, item, ability, buff, destructable, doodad, upgrade), race, origin (Built-in object or Custom object), the base Rawcode of a Custom object, the generated constant's name (go to definition; the plugin can find its position through the program rather than storing offsets) and, for "open", the Object data file that holds it.

**Two outputs from one model**: a `.d.ts` (constants with TSDoc, perhaps `FourCC` overloads) that TypeScript reads in every editor, and a JSON index that a plugin, a language server, an extension or an external editor reads without loading a TypeScript program. A plugin should not parse `war3map.w3u` itself: it would carry a binary parser into the tsserver process for every keystroke's session.

**Built-in objects**: once per Patch, shipped in a package next to the Typings (which package is #464's and the `new-patch` skill's call). wurst4vscode instead reads the developer's game install through CASC at run time ([`objectCatalog.ts`](https://github.com/wurstscript/wurst4vscode/blob/master/src/features/preview/objectCatalog.ts), `cascStorage.ts`), which needs the game installed and a configured path; per-Patch generated data needs neither and matches how `reforged-types` vendors one Patch's files.

**Custom objects**: per Map project, from the map folder. The Template already does the same for the World Editor's globals: `scripts/editor-globals.ts` regenerates `src/generated/editor-globals.d.ts` from `war3map.lua` "on every install, build and watch", and `.vscode/settings.json` marks `src/generated/**` read-only. `mdx-m3-viewer-th`, already a devDependency for packing, has parsers for `w3u` (units, items, destructables, buffs), `w3d` (doodads, abilities, upgrades, with levels) and `wts`. Reading Object data writes nothing, so it stays inside ADR 0006.

**Staying current while the World Editor saves**: `pnpm dev` watches the source and map folders (`scripts/dev.ts`, `watchFolders`, which also survives an editor deleting and recreating the folder on save) and would regenerate on each save. tsserver watches every file of its program, so a regenerated `.d.ts` reaches hover with no help. A plugin that reads JSON must watch it; `info.serverHost.watchFile` is available to plugins (used in the experiment; a live change was not exercised). Without `pnpm dev`, the data is as fresh as the last install or build; a VS Code extension could run the generation itself on a `createFileSystemWatcher` over `maps/**/war3map.w3?`, as wurst4vscode watches the files its object editor has open ([`objModPreview.ts`](https://github.com/wurstscript/wurst4vscode/blob/master/src/features/objModPreview.ts), `watchExternalChanges`).

## 7. Prior art

- **WurstScript language server**: hover on a Rawcode literal says only `integer constant` ([`HoverInfo.java`](https://github.com/wurstscript/WurstScript/blob/master/de.peeeq.wurstscript/src/main/java/de/peeeq/wurstio/languageserver/requests/HoverInfo.java), `case_ExprIntVal`); it looks up no Object data. Wurst names Built-in objects through generated standard-library constants with a line comment, `static constant footman = 'hfoo' // model: …` ([`UnitIds.wurst`](https://github.com/wurstscript/WurstStdlib2/blob/master/wurst/_wurst/assets/UnitIds.wurst)), the counterpart of #464.
- **wurst4vscode** (pushed 2026-10-04): custom editors for every Object data file (`wurst.objModPreview`, "WC3 Object Data", on `*.w3u … *.w3q`, priority `default`, [`package.json`](https://github.com/wurstscript/wurst4vscode/blob/master/package.json)), an editable `CustomEditorProvider` with add-object, generated Rawcodes, save, undo and external-change detection; names and icons of Built-in objects from the game install through CASC; cross-references between objects opened with `vscode.openWith` plus `postMessage`; document links on asset paths with `command:` targets. It has no hover from a Rawcode in code to its object. It is the closest existing external editor built with web technology on Node, and its object editor is the reference for the authoring tickets of #457.
- **typescript-to-lua**: a tsserver plugin plus a VS Code extension that contributes it ([`typescript-tstl-plugin`](https://github.com/TypeScriptToLua/typescript-tstl-plugin), [`vscode-typescript-to-lua`](https://github.com/TypeScriptToLua/vscode-typescript-to-lua)), the delivery pattern this page recommends, unmaintained since 2022.
- **Other games**: [Blockception's Minecraft Bedrock extension](https://marketplace.visualstudio.com/items?itemName=BlockceptionLtd.blockceptionvscodeminecraftbedrockdevelopmentextension) gives hovers, completions and diagnostics for a pack's ids through a language server of its own, the route of section 3 for a format no TypeScript server owns.

## Experiments

Both ran on Windows with Node 24.14 and pnpm 12.9 in a scratch directory, outside the repository; nothing from them is committed.

1. **tsserver plugin.** A CommonJS package `rawcode-hover-plugin` (about 90 lines) proxying the `LanguageService`, overriding `getQuickInfoAtPosition` and `getDefinitionAndBoundSpan`, reading a `rawcodes.json` named by `info.config.data` and watching it with `info.serverHost.watchFile`. A project installed `typescript@6.0.2` and the plugin (`file:` dependency) with pnpm and listed it in `compilerOptions.plugins`. A Node script spawned `node_modules/typescript/lib/tsserver.js` over stdio, opened `src/main.ts` and sent `quickinfo` and `definitionAndBoundSpan` inside `FourCC("hfoo")` and `FourCC('Hpal')`. Results: section 2. The same project without the tsconfig entry got no hover; with `--globalPlugins rawcode-hover-plugin --pluginProbeLocations <dir>` it got the same hover and definition.
2. **Plain TypeScript.** Without a plugin, a generated `.d.ts` declared per-Rawcode `FourCC` overloads with TSDoc, a `string` fallback, and a generic lookup variant; the same driver asked for quick info, definition, completions and diagnostics. A generator produced N overloads and M calls for timing with `tsc --extendedDiagnostics`. Results: section 1.
