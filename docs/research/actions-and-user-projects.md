# Driving a user-owned project and the pull-request check from GitHub Actions

Research for ticket [#521](https://github.com/phmilk/reforged-ts/issues/521), a child of the map [#518](https://github.com/phmilk/reforged-ts/issues/518). Facts and sources only; no decision.

Everything below was read on 2026-10-06 from docs.github.com, the public GraphQL schema (`https://docs.github.com/public/fpt/schema.docs.graphql`, confirmed by introspection with `gh api graphql`), the `action.yml` and README of `actions/add-to-project` and `actions/create-github-app-token` on github.com, the `gh` manual, the data files of the `github/docs` repository that generate its "permissions required" reference pages, and this repository's own files, named inline. Nothing was run against a project or a pull request: where the docs are silent, section 6 says so.

Vocabulary: **user-owned project** = a Projects (v2) board at `https://github.com/users/<owner>/projects/<n>`; **the App** = the repository's GitHub App of [#48](https://github.com/phmilk/reforged-ts/issues/48), whose installation token `.github/actions/app-token` mints; **the check** = a workflow job that reads the issues a pull request closes and acts on them.

## Answer

`GITHUB_TOKEN` can neither read nor write a project of any owner: GitHub's Projects automation page says it "is scoped to the repository level and cannot access projects", and the `permissions` key of a workflow has no Projects scope at all. The App cannot either, as far as the docs reach: the only Projects (v2) permission a GitHub App can hold is an *organization* permission, which applies only when the App is installed on an organization account, and the REST reference says of every user-owned project endpoint that it "does not work with GitHub App user access tokens, GitHub App installation access tokens, or fine-grained personal access tokens"; the App's owner here is a user account. Fine-grained personal access tokens are documented as unable "to access Projects owned by a user account". That leaves one documented token for a user-owned project: a personal access token (classic) with the `project` scope, which the docs recommend for user projects and which is one person's long-lived secret to store and rotate by hand. The pull-request check needs none of that: with `GITHUB_TOKEN` alone a job can read `closingIssuesReferences` on the pull request (GraphQL), assign an issue (`issues: write`), comment (`pull-requests: write`) and fail; for a pull request from a fork the `pull_request` token is read-only and has no secrets, so acting (rather than only failing) needs `pull_request_target`, which runs the base branch's workflow with a write token and must never check out the pull request's code; a `pull_request_target` job can be a required check, added to `.github/rulesets/master.json` as one more `{ "context": "<job name>" }`. Two parts of the Status driving need no token at all: the project's built-in workflows set Status to Done on close and on merge, and auto-add can add a repository's new issues; nothing built in reacts to an assignment.

## 1. `GITHUB_TOKEN`

What it is. "When you enable GitHub Actions, GitHub installs a GitHub App on your repository. The `GITHUB_TOKEN` secret is a GitHub App installation access token." "The token's permissions are limited to the repository that contains your workflow." "The `GITHUB_TOKEN` expires when the job finishes or after its effective maximum lifetime." (GitHub Docs, [GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token), read 2026-10-06.)

Projects. "`GITHUB_TOKEN` is scoped to the repository level and cannot access projects. To access projects you can either create a GitHub App (recommended for organization projects) or a personal access token (recommended for user projects)." ([Automating Projects using Actions](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/automating-projects-using-actions), 2026-10-06.) The `permissions` key offers `actions`, `artifact-metadata`, `attestations`, `checks`, `code-quality`, `contents`, `deployments`, `discussions`, `id-token`, `issues`, `packages`, `pages`, `pull-requests`, `security-events` and `statuses`; none names Projects, and the page does not contain the string `repository-projects` ([Workflow syntax, `permissions`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions), 2026-10-06). "If you specify the access for any of these permissions, all of those that are not specified are set to `none`." (same page.)

The two scopes the check uses. `issues`: "Work with issues. For example, `issues: write` permits an action to add a comment to an issue." `pull-requests`: "Work with pull requests. For example, `pull-requests: write` permits an action to add a label to a pull request." (same page.)

Forks. "Workflows don't run in forked repositories by default." "With the exception of `GITHUB_TOKEN`, secrets are not passed to the runner when a workflow is triggered from a forked repository. The `GITHUB_TOKEN` has read-only permissions in pull requests from forked repositories." ([Events that trigger workflows, `pull_request`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request), 2026-10-06.) "You can use the `permissions` key to add and remove read permissions for forked repositories, but typically you can't grant write access. The exception to this behavior is where an admin user has selected the **Send write tokens to workflows from pull requests** option in the GitHub Actions settings." and "When a workflow is triggered by the `pull_request_target` event, the `GITHUB_TOKEN` is granted read/write repository permission, even when it is triggered from a public fork." ([Workflow syntax, `permissions`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions), 2026-10-06.)

What the token's own actions trigger. "When you use the repository's `GITHUB_TOKEN` to perform tasks, events triggered by the `GITHUB_TOKEN` will not create a new workflow run", with the exceptions of `workflow_dispatch` and `repository_dispatch`, and of `pull_request` runs for a pull request the token creates or updates, which start "in an **approval-required** state"; "If you do want to trigger a workflow from within a workflow run, you can use a GitHub App installation access token or a personal access token instead of `GITHUB_TOKEN`." ([Triggering a workflow from a workflow](https://docs.github.com/en/actions/how-tos/writing-workflows/choosing-when-your-workflow-runs/triggering-a-workflow#triggering-a-workflow-from-a-workflow), 2026-10-06.) Consequence for the check: an assignment it makes with `GITHUB_TOKEN` raises no `issues: assigned` run, so a project workflow listening to that event would not fire; with an App or PAT token it would.

`gh` in a job. "For each step that uses GitHub CLI, you must set an environment variable called `GH_TOKEN` to a token with the required scopes." ([Using GitHub CLI in workflows](https://docs.github.com/en/actions/how-tos/writing-workflows/choosing-what-your-workflow-does/using-github-cli-in-workflows), 2026-10-06.) GraphQL accepts "a personal access token, GitHub App, or OAuth app" ([Forming calls with GraphQL, Authenticating](https://docs.github.com/en/graphql/guides/forming-calls-with-graphql#authenticating-with-graphql), 2026-10-06); `GITHUB_TOKEN` is an App installation token (above), and the Projects docs' own workflow examples run `gh api graphql` with `GH_TOKEN` set.

## 2. The GitHub App

Local facts. `.github/actions/app-token/action.yml` mints "A short-lived installation token of the repository's GitHub App, scoped to this repository (or to another one of its owner the App is installed on) and to the permissions given" through `actions/create-github-app-token` (pinned at v3.2.0, the latest release on 2026-10-06), with the inputs `permission-contents`, `permission-pull-requests` and `permission-issues` only. `docs/release.md` ("Prerequisites outside this repository"): the App is "installed on this repository with contents write, pull requests write and issues write" and "on the Template (`phmilk/reforged-ts-template`) with contents write"; the setup wizard installs it with "Only select repositories, this one and the Template". The owner account is a user account, not an organization (`gh api users/<owner>` returns `"type": "User"`, 2026-10-06).

The three permission groups. "Repository permissions allow your app to access resources related to repositories that are owned by the account where the app is installed." "Organization permissions allow your app to access resources related to the organization where the app is installed, if it is installed on an organization account." "Account permissions allow your app to access resources related to a user if the user has also authorized your app." For GraphQL there is no permission reference: "For GraphQL requests, you should test your app to ensure that it has the required permissions for the GraphQL queries and mutations that you want to make." ([Choosing permissions for a GitHub App](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app), 2026-10-06.)

Where Projects (v2) sits. Only under 'Organization permissions for "Projects"', whose endpoints are the thirteen `/orgs/{org}/projectsV2...` routes; no 'User permissions for "Projects"' exists, and the `/users/{username}/projectsV2...` routes appear under no permission at all ([Permissions required for GitHub Apps](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps), 2026-10-06). The data behind that page says the same: in `github/docs`, `src/github-apps/data/fpt-2026-03-10/server-to-server-permissions.json` and the `fpt-2022-11-28` twin map exactly 13 `projectsV2` paths, all `/orgs/`, to the key `organization_projects`, and no account-level key mentions projects (raw files read 2026-10-06). `actions/create-github-app-token` exposes the same two inputs and no third: `permission-organization-projects` ("to manage organization projects and projects public preview (where available)") and `permission-repository-projects` ("to manage repository projects, columns, and cards", the classic kind) ([action.yml](https://github.com/actions/create-github-app-token/blob/main/action.yml), 2026-10-06).

The REST reference states the consequence under each user-owned project endpoint, "List projects for user", "Get project for user", "List items for a user owned project", "Add item to user owned project" and "Update project item for user": "This endpoint does not work with GitHub App user access tokens, GitHub App installation access tokens, or fine-grained personal access tokens." The organization twins say instead: "This endpoint works with the following fine-grained token types: GitHub App user access tokens, GitHub App installation access tokens, Fine-grained personal access tokens. The fine-grained token must have the following permission set: "Projects" organization permissions (write)". ([REST, Projects](https://docs.github.com/en/rest/projects/projects) and [REST, Project items](https://docs.github.com/en/rest/projects/items), 2026-10-06.)

The documented App route is therefore an organization-owned project: "Create a GitHub App or choose an existing GitHub App owned by your organization." "Give your GitHub App read and write permissions to organization projects." "You must give permission to read and write organization projects; permission to read and write repository projects will not be sufficient." "Install the GitHub App in your organization. Install it for all repositories that your project needs to access." ([Automating Projects using Actions](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/automating-projects-using-actions), 2026-10-06.) The GraphQL guide names token kinds without naming owners: "The token can be a personal access token (classic) for a user or an installation access token for a GitHub App." ([Using the API to manage Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects), 2026-10-06.) Whether an installation token of an App installed on a user account reaches that user's projects through GraphQL is stated nowhere; the REST statement above is the closest the docs come. The project-access page describes inviting users as collaborators with Read, Write or Admin and says nothing about apps ([Managing access to your projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/managing-your-project/managing-access-to-your-projects), 2026-10-06).

Installation on a user account versus an organization. "Anyone can install GitHub Apps on their personal account. Organization owners can install GitHub Apps on their organization." ([Installing a GitHub App from a third party](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party), 2026-10-06.) "You can install a GitHub App that you created on the account that owns the app", choosing "All repositories" or "Only select repositories"; "The app will always have at least read-only access to all public repositories on GitHub." ([Installing your own GitHub App](https://docs.github.com/en/apps/using-github-apps/installing-your-own-github-app), 2026-10-06.) On a user account the installation carries the repository permissions; the organization permissions, Projects among them, exist only "if it is installed on an organization account"; account permissions need the user's authorization, that is a user access token rather than the installation token the action mints.

Lifetimes. "The installation access token will expire after 1 hour." ([Generating an installation access token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app), 2026-10-06.) The action revokes it in its `post` step unless `skip-token-revoke` is set ([create-github-app-token README](https://github.com/actions/create-github-app-token#readme), 2026-10-06). "Private keys do not expire and instead need to be manually revoked." "You can create up to 25 private keys for an app." "You should use multiple keys in order to rotate keys without downtime in the event of a key compromise." ([Managing private keys for GitHub Apps](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/managing-private-keys-for-github-apps), 2026-10-06.)

## 3. A personal access token

Classic. The scopes `project` ("Grants read/write access to user and organization projects.") and `read:project` ("Grants read only access to user and organization projects.") ([Scopes for OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps), 2026-10-06). The API guide: "replace `TOKEN` with a token that has the `read:project` scope (for queries) or `project` scope (for queries and mutations)"; for the CLI, "`gh auth login --scopes "project"`" ([Using the API to manage Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects), 2026-10-06). The Actions guide's PAT route: "Create a personal access token (classic) with the `project` and `repo` scopes." "Save the personal access token as a secret in your repository or organization." ([Automating Projects using Actions](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/automating-projects-using-actions), 2026-10-06.) `actions/add-to-project`: "For **Tokens (classic)** include the `project` scope; for private repos you will also need `repo` scope." ([add-to-project README](https://github.com/actions/add-to-project#readme), 2026-10-06.)

Fine-grained. Among the listed limitations: "Using fine-grained personal access token to access Projects owned by a user account." ([Managing your personal access tokens, "Fine-grained personal access tokens limitations"](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#fine-grained-personal-access-tokens-limitations), 2026-10-06.) The fine-grained permission that does exist is the organization one: "For **Fine-grained tokens**, you must first select the appropriate _owner_ and associated _repositories_. Then select _Organization permissions -> `projects` `read & write`_, and _Repository permissions -> `issues` `read-only`_ and _`pull requests` `read-only`_." (add-to-project README, 2026-10-06); the fine-grained PAT reference and its data file (`fine-grained-pat-permissions.json`, both API versions) map the Projects endpoints to `organization_projects` only ([Permissions required for fine-grained personal access tokens](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens), 2026-10-06), and the user-owned REST endpoints say the token kind does not work (section 2).

Lifetime. Fine-grained: "Under **Expiration**, select an expiration for the token. Infinite lifetimes are allowed but may be blocked by a maximum lifetime policy set by your organization or enterprise owner." Classic: "To give your token an expiration, select **Expiration**, then choose a default option or click **Custom** to enter a date." Both: "To provide additional security, we highly recommend adding an expiration to your personal access tokens." and "As a security precaution, GitHub automatically removes personal access tokens that haven't been used in a year." Also "Personal access tokens (classic) are less secure." and "When using a personal access token in a GitHub Actions workflow, consider whether you can use the built-in `GITHUB_TOKEN` instead." ([Managing your personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens), 2026-10-06.)

Cost, in this repository's terms. A classic PAT is one person's credential: it carries that account's access to the project and the repositories, lives in a repository secret set by hand (as `docs/release.md` has the wizard do for `APP_PRIVATE_KEY` with `gh secret set`), and nothing in Actions renews it: at expiry, or at revocation, a person makes a new token and updates the secret; with "no expiration" the only rotation is manual, plus the year-of-disuse removal. The App's cost is one private key with no expiry and hourly tokens the job mints (section 2); that comparison is moot for a user-owned project, which the App reaches by no documented permission.

## 4. The mechanics

### 4.1 `actions/add-to-project`

"Use this action to automatically add the current issue or pull request to a GitHub project." (README.) `action.yml` (v2.0.0, released 2026-05-04, the latest on 2026-10-06): the inputs `project-url` ("URL of the project to add issues to"; the README's form is `https://github.com/orgs|users/<ownerName>/projects/<projectNumber>`), `github-token` ("A GitHub personal access token with write access to the project"; README: "is a personal access token with `repo` and `project` scopes"), `labeled` and `label-operator` (`AND`, `OR`, `NOT`); one output, `itemId` ("The node ID of the project item that was added. If the issue or pull request belongs to a different owner than the project, a draft issue is created and this is the ID of that draft item. This value will be empty if the item was already present in the project."); runs on `node24`. "Currently this action supports the following `issues` events: `opened`, `reopened`, `transferred`, `labeled` and the following `pull_request` events: `opened`, `reopened`, `labeled`". It adds and sets no field: the Status after an add is whatever the project's "item added" built-in workflow sets (4.3) or a mutation of 4.2. The README documents neither an App token nor `GITHUB_TOKEN`; the token it names is a PAT. ([action.yml](https://github.com/actions/add-to-project/blob/main/action.yml), [README](https://github.com/actions/add-to-project#readme), 2026-10-06.)

### 4.2 The GraphQL mutations

From the schema (`schema.docs.graphql`, 2026-10-06; the reference pages are [Mutations](https://docs.github.com/en/graphql/reference/mutations) and [Input objects](https://docs.github.com/en/graphql/reference/input-objects)):

- `addProjectV2ItemById(input: AddProjectV2ItemByIdInput!): AddProjectV2ItemByIdPayload`: "Links an existing content instance to a Project." Input: `projectId: ID!` ("The ID of the Project to add the item to."), `contentId: ID!` ("The id of the Issue or Pull Request to add."; possible types `DraftIssue`, `Issue`, `PullRequest`), `clientMutationId`. Payload: `item: ProjectV2Item` ("The item added to the project.").
- `updateProjectV2ItemFieldValue(input: UpdateProjectV2ItemFieldValueInput!): UpdateProjectV2ItemFieldValuePayload`: "This mutation updates the value of a field for an item in a Project. Currently only single-select, multi-select, text, number, date, and iteration fields are supported." Input: `projectId: ID!`, `itemId: ID!` ("The ID of the item to be updated."), `fieldId: ID!` (a `ProjectV2Field`, `ProjectV2IterationField`, `ProjectV2MultiSelectField` or `ProjectV2SingleSelectField`), `value: ProjectV2FieldValue!` ("The values that can be used to update a field of an item inside a Project. Only 1 value can be updated at a time."; for Status, `singleSelectOptionId: String`, "The id of the single select option to set on the field."). Payload: `projectV2Item: ProjectV2Item` ("The updated item.").
- The docs' rule: "You cannot add and update an item in the same call. You must use `addProjectV2ItemById` to add the item and then use `updateProjectV2ItemFieldValue` to update the item." ([Using the API to manage Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects), 2026-10-06.)
- The IDs: `user(login:) { projectV2(number:) { id } }` (`User.projectV2`: "Find a project by number."); `ProjectV2.field(name:)` ("A field of the project"), which on a `ProjectV2SingleSelectField` gives `id` and `options { id name }` ("The option's ID.", "The option's name."); `repository(owner:, name:) { issue(number:) { id } }`. The docs page shows each as a `gh api graphql` call.

REST, the documented alternative since the 2025-09-11 changelog "A REST API for GitHub Projects" ([GitHub changelog](https://github.blog/changelog/2025-09-11-a-rest-api-for-github-projects-sub-issues-improvements-and-more/), 2026-10-06): `POST /users/{username}/projectsV2/{project_number}/items` ("Add an issue or pull request item to the specified user owned project."; body `type` = `Issue`, `PullRequest` or `DraftIssue`, with `id` or `owner`, `repo` and `number`) and `PATCH /users/{username}/projectsV2/{project_number}/items/{item_id}` ("Update a specific item in a user-owned project."; body `fields: [{ id, value }]`: "For single select and iteration fields, provide the ID of the option or iteration. To clear the field, set this to null."), with numeric ids rather than node IDs ([REST, Project items](https://docs.github.com/en/rest/projects/items), 2026-10-06). Its token statement is section 2's: for a user-owned project neither an installation token nor a fine-grained PAT works, which leaves the classic PAT here as in GraphQL.

### 4.3 The events

`issues`: the activity types `opened, edited, deleted, transferred, pinned, unpinned, closed, reopened, assigned, unassigned, labeled, unlabeled, locked, unlocked, milestoned, demilestoned, typed, untyped, field_added, field_removed`; `GITHUB_SHA` "Last commit on default branch", `GITHUB_REF` "Default branch"; "This event will only trigger a workflow run if the workflow file exists on the default branch." `pull_request`: `opened, edited, closed, reopened, synchronize, ...`; "By default, a workflow only runs when a `pull_request` event's activity type is `opened`, `synchronize`, or `reopened`."; a merge is a close: "To run a workflow when a pull request merges, use the `pull_request` `closed` event type along with a conditional that checks the `merged` value of the event" (`if: github.event.pull_request.merged == true`); "Workflows will not run on `pull_request` activity if the pull request has a merge conflict." No `projects_v2_item` workflow event exists on the page. ([Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), 2026-10-06.) The ticket's list (`issues: opened, assigned, unassigned, labeled, unlabeled, closed, reopened`; `pull_request: opened, closed`) maps one-to-one onto documented activity types; each handler then needs the project token of section 3 for its mutation, except what the project does by itself:

Built-in, no token. "Projects includes built-in workflows that you can use to update the Status of items based on certain events. For example, you can automatically set the status to Todo when an item is added to your project, close issues when the issue's status in your project is changed, or set the status to Done when an issue is closed. When your project initializes, two workflows are enabled by default: When issues or pull requests in your project are closed, their status is set to Done, and when pull requests in your project are merged, their status is set to Done." ([Using the built-in automations](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-built-in-automations), 2026-10-06.) Auto-add: "configure your project's built-in workflows to automatically add new items as they are created or updated in a repository", filtered by `is`, `label`, `reason`, `assignee` and `no`; "When you enable the auto-add workflow, existing items matching your criteria will not be added."; the page's table allows 1 auto-add workflow on GitHub Free, 5 on Pro and Team, 20 on Enterprise ([Adding items automatically](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/adding-items-automatically), 2026-10-06). Neither page names an assignment, or a pull request opening, as a trigger: `assigned` and `unassigned` reach the Status only through Actions, with a token.

### 4.4 `gh project item-edit`

"Work with GitHub Projects." "The minimum required scope for the token is: `project`. You can verify your token scope by running `gh auth status` and add the `project` scope by running `gh auth refresh -s project`." ([gh project](https://cli.github.com/manual/gh_project), 2026-10-06.) `gh project item-add <number> --owner <login> --url <issue-or-pull-request-url>` ("Add a pull request or an issue to a project"; [gh project item-add](https://cli.github.com/manual/gh_project_item-add), 2026-10-06). `gh project item-edit` ("Edit a draft issue or a project item") takes names, `--owner`, `--url` and `--field "Status" --value "In Progress"` ("`--url` is the issue or pull request URL, not a project URL, so its owner may differ from the project's; `--owner` selects the project"), or node IDs, `--id <item-id> --project-id <project-id> --field-id <field-id> --single-select-option-id <option-id>` (also `--text`, `--number`, `--date`, `--iteration-id`, `--clear`) ([gh project item-edit](https://cli.github.com/manual/gh_project_item-edit), 2026-10-06). From a workflow it is the same call as 4.2 with `GH_TOKEN` set (section 1); `project` is an OAuth scope, so that token is the classic PAT. The manual does not say whether an App installation token, which has permissions and no scopes, passes the scope requirement; for a user-owned project the question does not arise.

## 5. The pull-request check with `GITHUB_TOKEN` only

### 5.1 Reading the issues a pull request closes

GraphQL `PullRequest.closingIssuesReferences(...)`: "List of issues that may be closed by this pull request", an `IssueConnection`, with `userLinkedOnly: Boolean = false` ("Return only manually linked Issues") and `excludeUserLinked: Boolean = false` ("Exclude manually linked Issues") beside the pagination arguments (schema, 2026-10-06; [Objects, PullRequest](https://docs.github.com/en/graphql/reference/objects#pullrequest)). It covers both ways of linking: the keywords `close, closes, closed, fix, fixes, fixed, resolve, resolves, resolved` as `KEYWORD #ISSUE-NUMBER` or `KEYWORD OWNER/REPOSITORY#ISSUE-NUMBER`, and manual links ("You can manually link up to ten issues to each pull request."); "The special keywords in a pull request description are interpreted only when the pull request targets the repository's *default* branch. If the pull request targets *any other branch*, then these keywords are ignored, no links are created, and merging the PR has no effect on the issues."; "When you merge a linked pull request into the **default branch** of a repository, its linked issue is automatically closed." ([Linking a pull request to an issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue), 2026-10-06.) REST has no such field: the pull-request endpoints are eleven, none returns linked issues, and "Get a pull request" carries only `issue_url` ([REST, Pulls](https://docs.github.com/en/rest/pulls/pulls), 2026-10-06). Parsing `github.event.pull_request.body` oneself is the undocumented alternative; the GraphQL field returns what GitHub parsed.

Which `GITHUB_TOKEN` permission the field needs is itemized nowhere (GraphQL has no permission reference, section 2); the repository-level reads are `pull-requests: read` and `issues: read` (the fine-grained reference lists `GET /repos/{owner}/{repo}/pulls/{pull_number}` under "Pull requests" (read) and `GET /repos/{owner}/{repo}/issues/{issue_number}` under "Issues" (read); [Permissions required for fine-grained personal access tokens](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens), 2026-10-06). Because the keywords live in the description, the check must also run on `edited`, which is not a default activity type (4.3).

### 5.2 Assigning an issue

`POST /repos/{owner}/{repo}/issues/{issue_number}/assignees`: "Adds up to 10 assignees to an issue. Users already assigned to an issue are not replaced." "Only users with push access can add assignees to an issue. Assignees are silently ignored otherwise." ([REST, Assignees](https://docs.github.com/en/rest/issues/assignees), 2026-10-06.) The fine-grained reference lists it under Repository permissions "Issues" (write) and "Pull requests" (write): `issues: write` for `GITHUB_TOKEN`. Who can be assigned: "yourself, anyone who has commented on the issue or pull request, anyone with write permissions to the repository, and organization members with read permissions to the repository" ([Assigning issues and pull requests to other GitHub users](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/assigning-issues-and-pull-requests-to-other-github-users), 2026-10-06): a fork contributor who never commented on the issue is not, and `GET /repos/{owner}/{repo}/assignees/{assignee}` ("Check if a user can be assigned", 204 or 404) tells beforehand. `gh issue edit <n> --add-assignee <login>` is the CLI form.

### 5.3 Commenting on the pull request

`POST /repos/{owner}/{repo}/issues/{issue_number}/comments`: "You can use the REST API to create comments on issues and pull requests. Every pull request is an issue, but not every issue is a pull request." ([REST, Issue comments](https://docs.github.com/en/rest/issues/comments), 2026-10-06.) Listed under "Issues" (write) and "Pull requests" (write): `pull-requests: write`. `gh pr comment <n> --body ...` is the CLI form.

### 5.4 Failing the job

A non-zero exit of a `run` step; no permission.

### 5.5 `pull_request` versus `pull_request_target` for a fork

`pull_request` from a fork: a read-only token and no secrets (section 1), so the job can read and fail, but neither assign nor comment, and cannot mint the App token, whose private key is a secret. "When a first-time contributor submits a pull request to a public repository, a maintainer with write access may need to approve running workflows on the pull request." (events page, 2026-10-06); "By default, all first-time contributors require approval to run workflows." ([Managing GitHub Actions settings for a repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository), 2026-10-06.)

`pull_request_target`: "Runs your workflow in the context of the default branch of the base repository, rather than in the context of the merge commit, as the `pull_request` event does." "This prevents execution of unsafe code from the head of the pull request that could alter your repository or steal any secrets you use in your workflow." "Avoid using this event if you need to build or run code from the pull request." Warning: "Running untrusted code on the `pull_request_target` trigger may lead to security vulnerabilities. These vulnerabilities include cache poisoning and granting unintended access to write privileges or secrets." `GITHUB_SHA` "Last commit on default branch", `GITHUB_REF` "Default branch"; the same default activity types as `pull_request` ([Events that trigger workflows, `pull_request_target`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request_target), 2026-10-06). A write token even from a public fork (section 1). "Workflows triggered by `pull_request_target` events are run in the context of the base branch" and "workflows triggered by these events will always run, regardless of approval settings." (Actions settings page, 2026-10-06.) Secure use: "Avoid using the `pull_request_target` workflow trigger if it's not necessary." "Workflows that use these triggers must not explicitly check out untrusted code, including from pull request forks or from repositories that are not under your control." For inline scripts, "the preferred approach to handling untrusted input is to set the value of the expression to an intermediate environment variable." ([Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use), 2026-10-06.) The check checks nothing out: it needs the pull request's number and author, and the API.

### 5.6 The required check and the ruleset

`.github/rulesets/master.json` is "the JSON body of GitHub's rulesets API", applied by `pnpm repo:settings` with the maintainer's `gh` authentication (`release/src/repo-settings.ts`; `docs/release.md`, step 7 of the repository-setup wizard). Its `required_status_checks` rule lists `{ "context": "ci (ubuntu)" }` and `{ "context": "ci (windows)" }` with `strict_required_status_checks_policy: false`; `CONTRIBUTING.md` ("Pull requests", item 4) and the comment on the `ci` job in `ci.yml` call the names a contract. The rule's schema: `required_status_checks[]` with `context` (required, "The status check context name that must be present on the commit.") and `integration_id` (optional, "The optional integration ID that this status check must originate from."); `strict_required_status_checks_policy` (required, "Whether pull requests targeting a matching branch must be tested with the latest code. This setting will not take effect unless at least one status check is enabled."); `do_not_enforce_on_create` ([REST, Rules](https://docs.github.com/en/rest/repos/rules), 2026-10-06). "When you add a required status check rule, you can select an app as the expected source of status updates." ([Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-status-checks-to-pass-before-merging), 2026-10-06.) A new required check is one more `{ "context": "<job name>" }` entry, the job's displayed name (the `ci` job's matrix is what makes `ci (ubuntu)`), committed and applied.

Which runs count. "For checks created by workflow jobs to be evaluated for a pull request, the workflow run must be triggered by one of these events: `push`, `pull_request`, `pull_request_review`, `pull_request_target`, `deployment`, `deployment_status`"; "if a workflow is triggered by `workflow_dispatch` on a pull request's head branch, checks reported by its jobs do not appear in the pull request's checks section." Skips: "A workflow is skipped by path filtering, branch filtering, or a commit message | Associated checks stay in a 'Pending' state and block merging | Avoid requiring workflows that can be skipped."; "A job is skipped by a conditional | The job reports 'Success'". ([Troubleshooting required status checks](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/defining-the-mergeability-of-pull-requests/troubleshooting-required-status-checks), 2026-10-06.) So a `pull_request_target` job can be the required check, provided no `paths` filter can skip it for a pull request to `master`; a `pull_request` job from a fork satisfies it only by passing, never by acting.

### 5.7 Sketch

Not tested; the calls are the documented ones above, their composition is not.

```yaml
# Sketch, not tested. Fails a pull request to master that closes no issue and
# assigns the issues it closes to its author. pull_request_target: the base
# branch's workflow, a write GITHUB_TOKEN and no checkout, so a fork's pull
# request is handled too. `edited`: the closing keywords live in the body.
name: pr-issue
on:
  pull_request_target:
    types: [opened, reopened, synchronize, edited]
    branches: [master]
permissions:
  contents: read
  issues: write # the assignment
  pull-requests: write # the comment
jobs:
  pr-issue: # the context a ruleset entry would name: { "context": "pr-issue" }
    name: pr-issue
    runs-on: ubuntu-latest
    timeout-minutes: 5
    env:
      GH_TOKEN: ${{ github.token }}
      # Event values reach the script through env, never inline (secure use).
      PR: ${{ github.event.pull_request.number }}
      AUTHOR: ${{ github.event.pull_request.user.login }}
    steps:
      - name: Issues this pull request closes
        run: |
          gh api graphql \
            -F owner="${GITHUB_REPOSITORY%/*}" -F name="${GITHUB_REPOSITORY#*/}" -F pr="$PR" \
            -f query='query($owner: String!, $name: String!, $pr: Int!) {
              repository(owner: $owner, name: $name) {
                pullRequest(number: $pr) {
                  closingIssuesReferences(first: 10) { nodes { number } }
                }
              }
            }' --jq '.data.repository.pullRequest.closingIssuesReferences.nodes[].number' > issues.txt
      - name: Comment and fail, or assign
        run: |
          if [ ! -s issues.txt ]; then
            gh pr comment "$PR" --body 'This pull request closes no issue: add `Closes #<n>` to its description.'
            exit 1
          fi
          while read -r n; do
            # 204 means assignable; otherwise the add would be silently ignored.
            if gh api "repos/$GITHUB_REPOSITORY/assignees/$AUTHOR" --silent; then
              gh issue edit "$n" --add-assignee "$AUTHOR"
            fi
          done < issues.txt
          # With GITHUB_TOKEN this assignment raises no `issues: assigned` run;
          # a project Status change belongs here, with the project token of §3.
```

## 6. What the docs do not say

- Whether an installation token of an App installed on a *user* account can touch that user's projects through GraphQL. No App permission names user projects, the REST reference says installation tokens do not work on the user-owned endpoints, and the GraphQL guidance is "test your app". Not tested here.
- Whether a GitHub App, or its bot user, can be made a collaborator on a user-owned project: the access page describes inviting users only.
- Which `GITHUB_TOKEN` permission `closingIssuesReferences` needs: GraphQL has no permission reference.
- Whether `gh project` accepts an App installation token for an organization project, since the manual speaks of the `project` scope and installation tokens have permissions, not scopes.
- Whether `actions/add-to-project` runs on `pull_request_target`: its README lists `pull_request` events only.
- The old table of `GITHUB_TOKEN` permissions with a "maximum access for pull requests from public forks" column could not be located on the current docs (the `github_token-reference` URL lands on the workflow-syntax page); the fork statements above come from the events page and the `permissions` section of that page.
- Nothing above was exercised: no project, pull request or token was touched.
