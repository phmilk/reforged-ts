# A packed map and a browser page from the Creation CLI

What the Creation CLI would need to read a packed map (`.w3x`/`.w3m`) and to serve a browser page while still being run by Node alone, researched for [#1050](https://github.com/phmilk/reforged-ts/issues/1050). Sources, read on 2026-11-27: this workspace's code and ADRs, the Template's `scripts/pack.ts`, the published tarballs of `mdx-m3-viewer-th@5.13.4` and `reforged-studio@1.0.0-alpha.9`, StormLib's sources (`src/StormLib.h`, `src/SFileOpenArchive.cpp`, `src/SBaseFileTable.cpp` on `master`), Node's `child_process` and `http` documentation, and the `xdg-open` script and man page of xdg-utils 1.1.3 (Ubuntu's package). zezula.net (StormLib's format page) and developer.mozilla.org could not be reached from this session, so nothing below rests on them. Each claim is marked **Source** (read in the file or page cited), **Inferred** (follows from the sources, not stated by them) or **Unconfirmed** (not checked: no game, no World Editor, no browser in this session).

## TL;DR

- **A 3.0 map is an MPQ read as format version 1** (Source, StormLib): Warcraft III's `Storm.dll` ignores the header's format version and the MPQ user data, so HET/BET tables (format 3 and later) play no part; a reader needs the 32-byte header, the encrypted hash and block tables, sector decoding, decryption by file name, and the `(listfile)` to know names. Which compressions and flags the 3.0.1 World Editor actually writes when it saves a packed map is **Unconfirmed**: no packed map saved by it was read here.
- **`mdx-m3-viewer-th` 5.13.4 already has a reader** (Source): `parsers/mpq` reads version-1 archives, decrypts, decodes zlib (through `pako`) and PKWARE implode, and throws on Huffman, ADPCM and bzip2. The Template uses the same module as its writer and its tests open what it packs with it (`openArchive`).
- **A read-only reader written in-house is small** (Inferred): the MPQ part of `mdx-m3-viewer-th` is 1,620 lines of compiled JavaScript with its writer, and a reader over `node:zlib` needs neither `pako` nor the writer; the CLI already holds a dependency-free tar reader (160 lines) and the Studio a CASC/BLTE reader over `node:zlib`, the same pattern.
- **The Studio's server is `node:http` alone; its page is React plus `mdx-m3-viewer-th`, built by Vite into static files** (Source): 584,725 bytes of JavaScript and 11,696 of CSS in the published tarball, served from `dist/page/` with a CSP that keeps it to its own origin. It opens the browser by spawning `cmd /c start "" <url>`, `open` or `xdg-open` (`cmd.exe` under WSL), detached, errors ignored.
- **"Node alone runs it" is tested as two facts** (Source): an empty `dependencies` and the bin running from the tarball's files with no `node_modules`. Nothing in ADR 0018, the README or the tarball test forbids code from another workspace package compiled into `dist/` at build time (Inferred); what does stand in the way is the tarball test's allow-list for this package, `^dist/[^/]+\.js$` (flat JavaScript only, so no `index.html`, CSS or `assets/` folder), and the build, which is `tsc` alone.
- **With no browser, `xdg-open` can fall back to a text browser in the terminal** (Source, xdg-open): with neither `DISPLAY` nor `WAYLAND_DISPLAY` it tries `$BROWSER`, then `www-browser:links2:elinks:links:lynx:w3m`, and exits 3 or 4 when none works. In a container without xdg-utils the spawn fails with an `'error'` event (Source, Node). Printing the URL every time is the only path that works over SSH (Inferred).

## 1. Packed maps

### What the game reads

- **Format version 1, whatever the header says** (Source). StormLib, `SBaseFileTable.cpp`: "Reason: Storm.dll in Warcraft III ignores format version value", and it forces `MPQ_FORMAT_VERSION_1` for `MapTypeWarcraft3`. `SFileOpenArchive.cpp`: "W3x Map Protectors use the fact that War3's Storm.dll ignores the MPQ user data, and ignores the MPQ format version as well." So the extended header fields of format 2 (the high words of the table positions) and the HET and BET tables of formats 3 and 4 (`HET_TABLE_SIGNATURE` `'HET\x1a'`, `BET_TABLE_SIGNATURE` `'BET\x1a'`, `StormLib.h`) are never read for a map (Inferred).
- **The header** (Source, StormLib): the signature `MPQ\x1A` on a 512-byte boundary (the scan steps by `0x200`), and "STORM.dll from Warcraft III actually tests the MPQ header size. It must be at least 0x20 bytes" (`MPQ_HEADER_SIZE_V1` = `0x20`). A map may start with a 512-byte `HM3W` header before it; `mdx-m3-viewer-th`'s `isArchive` checks for `HM3W`, and the Template's writer never writes one, since "3.0 maps do not have one" (`scripts/pack.ts`).
- **The tables** (Source, StormLib): a hash table and a block table of 16-byte entries, encrypted with the keys `MPQ_KEY_HASH_TABLE` `0xC3AF3770` and `MPQ_KEY_BLOCK_TABLE` `0xEC83B3A3`. Protected maps put out-of-range block indexes there, which StormLib masks with `0x0FFFFFFF` ("Malformed MPQ maps may contain block indexes like 0x40000001").
- **File flags a map may carry** (Source, `MPQ_FILE_VALID_FLAGS_W3X`): implode (`0x100`), compress (`0x200`), encrypted (`0x10000`), key v2, the offset-adjusted key (`0x20000`), delete marker, sector CRC (`0x4000000`), signature and exists (`0x80000000`). Single unit (`0x1000000`) is not in the Warcraft III mask.
- **Compression types** (Source, `StormLib.h`): Huffman `0x01` ("used on WAVE files only"), zlib `0x02`, PKWARE `0x08`, bzip2 `0x10` ("added in Warcraft III"), ADPCM mono `0x40` and stereo `0x80`; sparse `0x20` and LZMA `0x12` were added in StarCraft II.
- **Internal files** (Source, `StormLib.h`): `(listfile)`, `(attributes)` and `(signature)`. The hash table stores only hashes of names, so a file is named only by the listfile or by a caller who knows the name; the decryption key is derived from the name (Source, `mdx-m3-viewer-th` `crypto.js`, `computeFileKey`). A map whose listfile is gone keeps its `war3map.*` files readable by their known names but its imports anonymous (Inferred).
- **Encrypted whole maps** (Source, `StormLib.h`): `STREAM_PROVIDER_W3XE`, "A Warcraft III map encrypted by AES-ECB". Where these come from and whether 3.0 writes or reads them is **Unconfirmed**.
- **What the 3.0.1 World Editor writes** when it saves a packed map (its sector size, its compressions, whether it writes `(attributes)` or encrypts files) is **Unconfirmed**: it takes a save in the World Editor and a dump of the tables, which stays for a human ([`probe/README.md`](../../probe/README.md#what-stays-for-a-human)). The game opens the Template writer's archives (Source: `probe/src/pack.ts` records that 3.0.1 opens a packed map and not a folder, #642), which shows what the game accepts, not what the editor writes.

### What the Template's writer and `mdx-m3-viewer-th` cover

- **The Template's writer** (Source, `reforged-ts-template/scripts/pack.ts`): `OpaqueW3iMap` over `mdx-m3-viewer-th/dist/cjs/parsers/w3x/map.js`, deep-imported "because the package root pulls in the WebGL viewer". It sizes the hash table, imports every file of the map folder, keeps the editor's `war3map.imp`, and saves. `openArchive` reads an archive back with the same class, in read-only mode; `tests/pipeline/pack.test.ts` uses it.
- **Its writer's output** (Source, `mdx-m3-viewer-th` `archive.js`, `file.js`): a 32-byte header with version 0 and sector size 4096, a `(listfile)` it builds, `(attributes)` deleted, every file in sectors deflated with `pako` when that is smaller (mask byte `2`), nothing encrypted, no `HM3W`.
- **Its reader** (Source, the same files): finds the header on a 512-byte boundary, reads the hash and block tables (capping the block count to the hash count), ignores the format version (as the game does), reads the listfile to name files, and decodes stored, single-unit and sectored files, encrypted ones included (offset-adjusted key too). It decodes zlib (`pako.inflate`) and implode (its own `explode.js`, 322 lines), and throws on bzip2, Huffman and both ADPCMs ("compression type 'huffman' not supported").
- **Its gaps against StormLib** (Source, read side by side): `searchHeader` keeps the _last_ `MPQ\x1A` it finds rather than the first; it does not check the header size of at least `0x20`; it does not mask block indexes; it reads no sector CRC. Huffman with ADPCM is how WAVE files are compressed (StormLib's comment above), so a map whose imported sounds were saved that way would fail on those files (Inferred; whether the 3.0 editor compresses sounds so is **Unconfirmed**).
- **Its weight** (Source): its runtime `dependencies` are `fengari`, `file-saver`, `gl-matrix`, `pako` and `tga-js`; the MPQ parser alone needs `pako` and a few `common/` helpers. Its licence is MIT (the Studio's `NOTICES.md` carries it). ADR 0014 notes its other parsers misread 3.0 data (the Skin files, `w3i` version 39, the 1.31+ `wtg`), so only its MPQ layer is of use here.
- **Nothing in this workspace reads a packed map** (Source): no package under `packages/` imports an MPQ module; `reforged-map` and the Studio read map folders only (ADR 0006, ADR 0015).

### What a reader would cost

- **Bundling `mdx-m3-viewer-th`'s MPQ parser** (Inferred): the deep import of `parsers/mpq` plus `pako` compiled into the CLI's `dist/`, with its MIT notice in the tarball. It brings its gaps above, a writer the CLI does not need, and a pinned dependency the CLI would carry as a dev dependency only.
- **Writing one** (Inferred): a read-only version-1 reader over `node:zlib`'s `inflateSync`, the pattern of the CLI's `tar.ts` ("A tar reader for the Template's archive, with no dependency", over `gunzipSync`) and the Studio's `casc/blte.ts` (`inflateSync`). Its parts: the crypt table and the name hash (`mdx-m3-viewer-th`'s `crypto.js` is 101 lines), the header scan, the two tables, the file key, sector decoding with zlib, and an error naming any other compression. PKWARE implode is another 300 lines or so if the 3.0 editor ever writes it (**Unconfirmed**); bzip2 has a decoder in `node:zlib`'s neighbours only through a dependency (Node has none built in; Inferred from `node:zlib` offering gzip, deflate, Brotli and Zstd only, not verified against its docs here). Its tests can round-trip the Template writer's archives, which the Template already builds.

## 2. The page

### Serving it with `node:http`

- **The Studio's pattern** (Source, `packages/reforged-studio/src/server/listen.ts`, `page.ts`, `events.ts`): bind `127.0.0.1` only, on 5476 or the next free port up to 100 above it (port 0 for any); serve the built files with `content-security-policy: default-src 'self'; …` and `nosniff`; push state to the page through one Server-Sent Events stream (`GET /api/events`); on stop, `server.close()` then `server.closeAllConnections()`.
- **Node's API** (Source, nodejs.org `http`): `server.closeAllConnections()` (added v18.2.0) "Closes all established HTTP(S) connections … including active connections", and the docs recommend calling it _after_ `server.close`; since v19.0.0 `server.close` "closes idle connections before returning". A `ServerResponse`'s `'close'` event "Indicates that the response is completed, or its underlying connection was terminated prematurely". The CLI's `engines.node` is `>=22.13`, so all of it is there.

### Ending when the page confirms or the author closes it

- **Confirm** (Inferred): a `POST` from the page, after which the server answers, closes and the command goes on; the Studio's JSON API is that shape.
- **Close** (Inferred): the SSE response's `'close'` event fires when the tab's connection ends, but a reload or a navigation ends it too, and `EventSource` reconnects on its own; ending only after no stream has been open for a few seconds separates a close from a reload. The behaviour of the browsers' back-forward cache and of a tab put to sleep on this connection is **Unconfirmed** (MDN was not reachable; no browser in this session).
- **A terminal fallback** (Inferred): the command should keep stdin's Ctrl+C and, with a terminal, accept the same answer typed, so that it never waits on a page nobody can open; the CLI already asks only "when standard input is a terminal" (`cli.ts`, `process.stdin.isTTY`).

### Opening the default browser

- **What the Studio does** (Source, `packages/reforged-studio/src/studio.ts`, `openBrowser`): `cmd /c start "" <url>` on Windows, `open <url>` on macOS, `cmd.exe /c start "" <url>` under WSL (`isWsl`: `WSL_DISTRO_NAME`, else `microsoft` in `/proc/version`, `install.ts`), `xdg-open <url>` elsewhere; spawned `detached`, `stdio: "ignore"`, `unref()`, and an `'error'` listener that drops the error.
- **Node** (Source, `child_process`): "`.bat` and `.cmd` files are not executable on their own" on Windows and need `cmd.exe`; the `shell` option is not recommended (DEP0190). With `detached`, on Windows "The child process will have its own console window"; `unref()` lets the parent exit. The `'error'` event is emitted when "The process could not be spawned".
- **`cmd /c start`** (Inferred): `cmd` reads `&`, `^` and `|` in its command line, so a URL with a query string of several parameters needs them escaped; the Studio's `/objects` carries none. Not tried on Windows here.
- **`xdg-open`** (Source, xdg-utils 1.1.3): with a desktop it hands the URL to the desktop's opener; in its generic path it tries `$BROWSER`, then, with a display, `x-www-browser:firefox:…:google-chrome`, and in every case `www-browser:links2:elinks:links:lynx:w3m`. Exit codes: 3 "A required tool could not be found", 4 "The action failed". The exit code is the only sign of failure the CLI gets; the Studio ignores it (Source, above).

### With no browser

- **SSH** (Inferred from xdg-open above): no `DISPLAY`, so `xdg-open` may start a text browser, which, spawned with `stdio: "ignore"` as the Studio does, has no terminal to draw on; otherwise it exits 3 or 4. Even when a browser opens elsewhere, `127.0.0.1` on the remote machine is not the author's; only a printed URL plus a port forward (`ssh -L`) reaches it.
- **WSL** (Source, Studio): `cmd.exe /c start` opens the Windows browser. Whether Windows reaches a server bound to `127.0.0.1` inside WSL 2 depends on WSL's localhost forwarding, which is on by default (**Unconfirmed**: not checked here, and the Studio's walk ran its server on Windows, [`studio-walk.md`](studio-walk.md)).
- **A container** (Inferred): usually no `xdg-open` (this session's container has none), so the spawn fails with `ENOENT` through `'error'`; and a server bound to `127.0.0.1` inside it is not reachable through a published port, which needs `0.0.0.0`. The CLI cannot tell a headless machine apart reliably, so it prints the URL and keeps a non-browser way to answer (Inferred).

## 3. The Studio's stack, and bundling it into the CLI

- **Server** (Source): `node:http`, `node:fs`, `node:child_process` and the Studio's own modules; 6,462 lines under `src/server/` and `src/cli/`. At run time it imports `reforged-map` (13 modules of `src/` do; a required peer, `workspacePeers: { "reforged-map": false }` in `test/tarballs.test.ts`), and `reforged-map` has peers of its own (`reforged-types`, optional `reforged-builtins` and `typescript`).
- **Page** (Source): React 19 and `react-dom`, `mdx-m3-viewer-th` for model previews (patched by `page/mdx-1800.ts`), built by `vite build page --outDir ../dist/page` into `index.html`, one hashed JavaScript file and one CSS file; these are dev dependencies, and `NOTICES.md` carries the licences of what the page bundles. Published size: `dist/page/` 596 KB of 1,069,932 bytes unpacked (Source, `npm view` and the tarball).
- **Into `create-reforged-map`** (Inferred): the page's stack can be bundled without a runtime dependency, since Vite already turns it into static files; a server like the Studio's needs only `node:http`. What it costs: Vite (or another bundler) in the CLI's build, which is `tsc -p tsconfig.json` today; a page of a few hundred kilobytes in a package of 60,504 bytes unpacked (Source, `npm view create-reforged-map@next`); a `NOTICES.md` for what it bundles; and a change to the tarball test's allow-list, whose `allowed: [/^dist\/[^/]+\.js$/]` refuses an HTML file, a CSS file or an `assets/` folder (or the page embedded in a `.js` module as strings). A plain page with no framework, written for the one question it asks, avoids all but the server (Inferred).
- **Reusing the Studio's server code itself** (Inferred): it reads and writes Object data through `reforged-map`, which the CLI has no use for before the project exists; `listen.ts` and `page.ts` are the parts worth copying, about 150 lines.

## 4. The rule: "Node alone runs it"

- **The README** (Source, `packages/create-reforged-map/README.md`): "It has no runtime dependency: Node alone runs it."; the Template gate "runs the packed command with Node alone, since the package has no dependency" (`docs/release.md`); and "The workspace's tarball test runs the packed command with Node alone."
- **What the test holds** (Source, `test/tarballs.test.ts`, `runsAlone`): `dependencies` equal to `{}`, and each bin, copied out of the tarball with no `node_modules`, answers `--no-such-option` with its usage and exit code 2. Its `workspacePeers` is `{}` and its files `^dist/[^/]+\.js$`, with `dist/cli.js`, `dist/create.js` and `dist/tar.js` required.
- **ADR 0018** (Source) decides that the CLI "embeds no Template file" and keeps no copy of the maintenance list, so that nothing "is copied twice and nothing drifts"; it says nothing about runtime dependencies or about bundling code.
- **So** (Inferred): code from another workspace package (or a third-party one) compiled into `dist/` at build time keeps both tested facts, and no written rule forbids it. Two things weigh against it in the ADR's own terms: a copy of a workspace package's code in the CLI is a second copy that can drift from its source (the reason the ADR gives for embedding no Template file), unless the CLI's build takes it from the workspace on every release; and the tarball test's allow-list and the `tsc`-only build would both change. A maintainer's decision, not a fact, settles which reading holds.

## Not settled here

- What the 3.0.1 World Editor writes in a packed save: sector size, compressions (zlib only, or implode, bzip2, Huffman with ADPCM for sounds), `(attributes)`, encryption. It needs a save at the World Editor, which stays for a human, and a table dump.
- Whether the game, rather than StormLib's account of `Storm.dll`, still ignores the format version and user data in 3.0.1: StormLib's comments describe older `Storm.dll` builds.
- Browser behaviour when a tab closes, sleeps or enters the back-forward cache with an open `EventSource`; WSL 2's localhost forwarding; `cmd /c start` with `&` in the URL; `open`'s exit code on a Mac with no browser. None was tried.
- Node's `node:zlib` lacking bzip2 was not checked against Node's documentation in this session.
